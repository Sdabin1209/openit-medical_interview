# 0021. 서비스 TLS 종단은 영역 게이트웨이가 한다

## 상태
승인(2026-11-11, 통합 담당, 사용자 결정 2026-11-10 '표준적인 선택'). 변경 요청 survey-service-006, model-runtime-003 7번을 닫는다. 계약 9.0.0 에 반영했다. platform ADR 0007(영역 게이트웨이)이 구현을 정한다.

## 맥락
계약은 영역 서비스에 `OPENIT_TLS_CERTIFICATE_FILE`·`OPENIT_TLS_PRIVATE_KEY_FILE` 을 필수로 주고 서비스 주소를 `https://<영역 이름>` 으로 정한다(C14·D127·D129). 실제 구현은 갈렸다. survey-service 는 평문 HTTP 로 듣고 TLS 입력을 쓰지 않았고, model-runtime 은 TLS 를 끝내고 클라이언트 인증서를 요구했다. 인증서는 사설 CA(step-ca)가 7일 수명으로 ACME 로 발급하고(ADR 0014) 갱신해야 한다. uvicorn 은 인증서를 시작할 때 한 번 읽으므로 서비스가 TLS 를 끝내면 갱신마다 다시 시작해야 하고 서비스마다 ACME 클라이언트가 필요하다. 계약 `device_mtls` 는 서비스가 게이트웨이와의 연결에서만 `X-Forwarded-Client-Cert` 를 믿는다고 했으나 서비스가 그 연결을 확인할 방법이 없었다. 워크스페이스 규칙(D128)은 영역마다 게이트웨이가 있고 들어오는 쪽 TLS 를 그 게이트웨이가 끝낸다고 정한다.

## 결정
- 서비스 영역마다 영역 게이트웨이(Caddy, 공식 이미지 digest 고정)가 서비스 이름으로 ACME 인증서를 받아 갱신하고 TLS 를 끝낸다. 클라이언트 인증서를 요구해 신뢰 목록으로 검증한다(`area_mtls`).
- 서비스 컨테이너는 영역 전용 내부 네트워크(`internal: true`)에서 평문 HTTP 로 `OPENIT_LISTEN_PORT` 를 듣는다. 그 네트워크에는 그 영역의 게이트웨이와 DB 만 있다. 서비스 이름의 네트워크 별칭은 게이트웨이만 갖는다. 그래서 서비스에 닿는 것은 게이트웨이뿐이고 `X-Forwarded-Client-Cert` 를 믿는 근거가 네트워크 구성이다. 게이트웨이는 입구(Envoy)의 클라이언트 인증서(SAN `gateway`)로 온 요청에서만 그 머리글을 넘기고 나머지에서는 지운다.
- `OPENIT_TLS_*_FILE` 은 서비스가 이웃을 부를 때 보이는 클라이언트 인증서·키로 남긴다(나가는 호출은 입구의 CONNECT 터널 위에서 서비스가 TLS 를 하므로, D128). 같은 인증서(서비스 이름, 사설 CA 가 serverAuth·clientAuth 로 발급)를 게이트웨이의 인증서 에이전트가 영역 안 공유 tmpfs 볼륨에 두고 서비스가 읽기 전용으로 마운트해 갱신을 따라간다.
- 영역 안 감시는 TLS 와 별개의 평문 포트 9100 으로 상태 경로(`/healthz`, `/readyz`, `/metrics`)만 서비스에 이어 준다(`backend` 내부 네트워크에서만 닿고 입구로 나가지 않는다).

## 왜
- 사이드카 프록시가 TLS 를 끝내고 앱은 평문으로 두는 것은 서비스 메시(Envoy, Linkerd 등)의 표준 배치다. 인증서 갱신·클라이언트 인증 같은 보안 코드를 영역마다 두지 않고 기성품 한 곳에 둔다(구조 규칙 1·4).
- 계약이 Caddy 를 따로 정하지 않았으나 ADR 0014 가 ACME 클라이언트를 Caddy 로 정했고 입구 인증서 에이전트와 레지스트리가 같은 방식으로 이미 돌아간다.
- 네트워크 분리는 Docker 의 표준 기능(사용자 정의 브리지, `internal`)이다.

## 검토한 대안과 버리는 이유
- **서비스가 TLS 를 끝낸다(계약 원문):** 갱신마다 재시작하거나 서비스 안에 ACME 클라이언트를 둔다. 서비스 코드가 보안 설정을 갖게 된다.
- **같은 `backend` 네트워크에서 서비스를 평문으로 노출:** 같은 네트워크의 아무 컨테이너가 헤더를 위조해 서비스를 부를 수 있다.
- **게이트웨이가 나가는 호출의 TLS 도 맡는다(완전한 사이드카):** 나가는 길은 platform 의 CONNECT 터널(ADR 0003)로 이미 정해졌고 CONNECT 는 TLS 를 투과한다. 바꾸려면 platform 의 터널 구조를 새로 정해야 한다. 서비스가 클라이언트 인증서를 읽는 쪽을 택했다.

## 결과
- **얻는 것:** 서비스는 TLS·ACME 를 모른다. 인증서 갱신이 서비스를 다시 시작하지 않는다.
- **감수하는 것:** 서비스마다 컨테이너 하나가 더 돈다. 영역 게이트웨이와 서비스 사이는 같은 영역 네트워크의 평문이다(같은 영역 안의 구간이고 게이트웨이와 DB 외에는 닿지 못한다). 서비스가 읽는 인증서 볼륨에는 게이트웨이의 ACME 계정 키도 있다(같은 영역 안이다. 입구 에이전트와 입구가 인증서 볼륨을 나누는 것과 같은 수준이다).
- 영역 게이트웨이는 서비스를 서비스 이름이 아니라 영역 네트워크 전용 별칭(`<영역>-app`)으로 부른다. 서비스 이름은 게이트웨이의 backend 별칭이라 같은 이름이 겹치면 게이트웨이가 자기 자신으로 풀 수 있다(통합 확인에서 만났다, platform 작업자가 샌드박스에서도 재현).
- 이 환경 한 곳에서만 확인했다(결과는 `deploy/docs/INTEGRATION.md`).

## 되돌리는 조건
Envoy 가 ACME 를 내장하거나 서비스 메시를 도입하면 게이트웨이를 그 표준에 맞춘다. 영역 서비스를 서버 여러 대로 나누어 영역 안 구간이 서버 밖을 지나게 되면 그 구간에도 TLS 를 건다.
