# 0025. E2E 실행 규약과 두 모드

## 상태
승인(2026-11-11, 헤드 판단). ADR 0004·0013·0023 을 이어 `./deploy e2e` 의 규약을 정한다. 워크스페이스 결정 D81(프로파일별 기반 모델)·D123(시험은 샌드박스)·D125(시간 상한)를 따른다.

## 맥락
`./deploy e2e` 는 대상 없음(종료 코드 3)으로 비어 있었다. 영역 시험(가짜 이웃)과 platform 샌드박스(가짜 상류)는 있지만, 실제 영역 이미지와 실제 추론 엔진(vLLM)이 입구를 지나 한 건의 문진을 끝까지 내는지는 본 적이 없다(INTEGRATION.md '확인하지 못한 것'). 학습된 어댑터는 24GB급 GPU 에서만 서빙할 수 있고(D81) 이 개발 PC 는 12GB 다. 그래서 학습된 어댑터 없이 경로만 확인하는 모드와, 학습된 어댑터로 값까지 확인하는 모드가 둘 다 필요하다.

## 결정
- **샌드박스(D123):** 제품 구성(`deploy/compose.yaml`, 설치 설정)을 바꾸지 않는다. 리포의 `deploy/`·`platform/`·`contracts/` 와 영역 폴더의 Dockerfile 을 `.e2e/work/openit-e2e-<무작위>/`(작업 트리 안 git 제외)에 복사하고 그 사본의 `./deploy bootstrap` 으로 두 번째 설치를 만든다. compose 프로젝트 이름은 `openit-e2e-<무작위>` 다. 영역 이미지는 이 엔진에 빌드되어 있어야 한다(없으면 시작 전에 멈춘다). 끝나면 이 프로젝트만 프로파일 포함 `down -v --remove-orphans` 하고 컨테이너·볼륨·네트워크가 0개인지 본다. 실패하면 상태와 로그(`.e2e/logs/<프로젝트>/`)를 먼저 남기고 정리한다.
- **샌드박스에서만 만드는 것:** 시험용 기기 CA 와 기기 인증서(허용 목록 포함), 기계 호출자 표에 병원 시스템(`result-reader`) 한 줄, Keycloak 시험 계정(직원·의사·문항 작성자·승인자)과 기계 클라이언트. 비밀번호는 실행마다 무작위이고 출력하지 않는다. 추론 엔진은 설치 설정 `OPENIT_INFERENCE_ENGINE_LOCAL=false` 로 `./deploy up` 이 띄우지 않게 하고, compose 조각 `compose.e2e.yaml`(샌드박스 사본에만 있다)이 제품 정의의 인자 뒤에 GPU 에 맞는 크기 인자를 더하고 모델 캐시와 어댑터를 마운트해 따로 띄운다. 같은 조각이 게시 도구 서비스(영역 이미지의 `package-publish`)를 둔다.
- **모드(인자):** `--mode pipeline` 은 D81 의 `gpu-12g`(기반 Qwen3-1.7B)와 중립 어댑터(`tools/neutral-adapter`, B 행렬 0)다. `--mode product --adapters-a <폴더> --adapters-b <폴더> --profile <프로파일>` 은 학습된 어댑터다. 어댑터 폴더 형식은 PEFT 어댑터(`adapter_config.json`, `adapter_model.safetensors`)와 학습에 쓴 시스템 프롬프트 `system_prompt.txt` 다. product 의 기반 모델은 어댑터의 `base_model_name_or_path` 이고(A·B 가 같아야 한다) 프로파일과의 일치는 model-runtime 이 활성화에서 확인한다(영역 내부 표를 deploy 가 읽지 않는다, model-runtime ADR 0007).
- **시나리오(한 건의 문진, 모두 입구를 지나는 실제 HTTP, 호스트에서 게시 포트로만):** ① 어댑터 게시(`package-publish`, 엔진이 평가) ② 승인자가 `getModelPackage`·`listModelPackages` 확인 뒤 `activateModelPackage`, `getModelStatus` 로 READY 대기 ③ 작성자가 문항 세트 올리기·활성화 ④ 직원이 `issueStartCode` ⑤ 키오스크(기기 인증서)가 `startSessionStream`·`submitTurnStream` 여러 번·`endSession`(응답 문장 스트림의 머리글·이벤트 스키마·끝맺음을 보고, product 모드는 delta 가 하나 이상 와야 한다. 계약 9.2.0, 2026-11-11) ⑥ 의사가 결과 조회·확인 표시 ⑦ 병원 시스템(기계 토큰)이 `getResult`·`getResultFhir` 로 당겨 감 ⑧ 직원 호출 알림(둘째 세션의 `requestStaffCall`, 알림 목록과 세션 PAUSED 확인).
- **문항 세트:** 정본에 문항 은행 원본(DB 파일)이 이 리포에 없으므로 `contracts/inputs/SQL.md` 5.1~5.3 의 표로 만든다(`questionnaire.py`). 문항 31개와 칸 52개, 질문 문장은 원문이고 '대상'이 있는 문항은 원문의 '다음과 같은 질병'(Q1)·'다음 질환'(Q2)을 대상 이름(조사를 붙여)으로 바꾼다. 순서표는 문항 순서와 `labels.py` 의 `next_after` 의 건너뛰기 여섯 가지다. 시험이 이 결과를 model-runtime 의 시험 자료(실제 참조 DB 에서 만든 문항 은행)와 대조한다.
- **발화 대본과 기대 값:** `script.py`. `IO_SPEC.md` 의 예(5.2 정상, 5.3 건너뛰기, 5.9 끝)와 `PIPELINE_LOGIC.md` 의 운동 40분, 같은 형식으로 쓴 나머지다. 서비스가 알려 주는 지금 문항(`current_item_id`)의 발화를 보내고 25턴이면 문진이 끝(ENDED_COMPLETE)난다. 학습 서버의 데이터를 읽지 못해 발화가 학습 분포 안인지는 확인하지 않았다.
- **판정:** 모든 호출은 계약 파일(OpenAPI 3.1과 공유 값 정의)로 검증한다. 보내는 본문이 요청 스키마를 지키는지, 응답 상태가 계약에 있고 기대한 것인지, 응답이 그 상태의 스키마를 지키는지(format 단언 켬). pipeline 은 모든 단계가 계약대로 응답하는지와 실패 처리를 본다: 연속 실패 1·2번째는 실패 신호이고 저장된 답·지금 문항이 불변, 3번째(계약 9.3.0 `TurnFailureLimit`)는 실패 신호 없이 안내 문장과 다음 문항이며, 같은 turn_id 재전송은 연속 실패 수를 올리지 않고, 결과(⑥)에 빈칸 원인 `FAILURE_LIMIT`, FHIR(⑦)에 data-absent-reason `error` 가 남는다. 실패 신호가 하나도 관측되지 않으면 그것을 기록에 적는다(실패 경로가 시험되지 않았다). product 는 더해 문진이 끝까지 가고(ENDED_COMPLETE) 대본의 기대 값이 결과에 모두 저장되고 어떤 턴도 실패 신호를 내지 않아야 한다. product 에서 연속 실패 한도로 건너뛴 문항이 있으면 실패로 보지 않고 기록에 문항을 적는다. 실패한 호출은 다시 보내지 않는다. 기다림은 상태를 보는 것(적재 상태)뿐이고 상한 안에서만 한다.
- **값(근거와 측정 여부):** 모두 실패 판정 상한이고 목표(SLO)가 아니다(D125).

| 값 | 근거 | 측정 |
|---|---|---|
| 요청 대기 65초 | 계약 `KioskRequestLimitSeconds` 60초(D125)보다 조금 길게. 서버·게이트웨이 상한(55+1초)이 먼저 상태 코드로 드러난다 | 안 함 |
| 적재 완료 대기 180초 | 계약 9.1.0 의 `TimeBudgetTable.model_load`(ModelLoadLimitSeconds) 값을 읽는다 | 안 함 |
| 상태 조회 간격 2초 | 계약 `SessionStatePollSeconds` | 안 함 |
| 엔진 기동 대기 780초 | 제품 compose 가 엔진에 준 건강 확인 창(120초 + 15초×40 = 720초)에 1분 | 안 함 |
| model-runtime 준비 대기 120초 | 엔진이 건강해진 뒤 `/readyz` 가 엔진의 모델 목록을 확인하는 시간. 계약에 상한 없음 | 안 함 |
| `gpu-12g` 엔진 크기 인자 `--gpu-memory-utilization 0.7 --max-model-len 8192` | 이 GPU(12GB, 화면 출력이 1.5GB 사용)에서 vLLM 기본값(메모리 90%, 최대 길이 40960)은 시작하지 못한다. 첫 시도값이다 | 안 함 |
| pipeline 의 턴 수 6 | 학습되지 않은 어댑터로는 문진이 끝까지 가지 않으므로 둔 상한이다 | 안 함 |

## 왜
- 제품에 시험용 문을 두지 않고 별도 설치를 시험하는 것이 D123 이다. platform 샌드박스가 같은 방식이고 compose 사본 방식이 이미 검증되어 있다. 엔진 크기 인자는 제품 정의를 고치지 않고 조각으로 더한다.
- 입구를 지나는 실제 HTTP 만 쓰고 내부 포트를 부르지 않아야 입구의 인증·라우트 생성·영역 게이트웨이 mTLS 까지 시험에 들어간다.
- 계약 파일로 직접 검증하면 영역이 생성 타입을 잘못 만들어도 영역 시험이 통과시킨 차이를 잡는다.
- 중립 어댑터(B=0)는 학습 없이 적재·추론 경로를 지나게 하고, 출력이 기반 모델과 같다는 것을 PEFT 의 정의가 보증한다. 형식 통과 이상의 모델 품질은 pipeline 이 판정하지 않는다.
- 기반 모델 가중치는 이름 있는 도커 볼륨(`openit-e2e-hf-cache`)에 두고 다음 실행이 다시 쓴다. 엔진 컨테이너는 내부 네트워크라 허브에 닿지 않으므로(`HF_HUB_OFFLINE=1`) 받는 일은 인터넷에 닿는 일회용 컨테이너(같은 vLLM 이미지)가 한다. 이 볼륨은 프로젝트 밖이라 `down -v` 가 지우지 않는다.

## 검토한 대안과 버리는 이유
- **제품 compose 에 시험 프로파일·포트를 더한다:** D123 이 금지한다.
- **`./deploy up` 이 엔진을 띄운다(LOCAL=true):** 제품 정의의 기본 크기로는 이 GPU 에서 시작하지 못하고 모델 캐시가 없어 허브에 닿지 못한다. 크기를 위해 제품 정의를 고치면 서버 배치(서빙 GPU 서버)에도 영향이 간다.
- **게시를 호스트에서 한다:** 평가에 엔진이 어댑터를 같은 경로로 읽어야 하고 레지스트리는 안쪽 네트워크 이름으로만 닿는다. 영역 이미지의 도구를 안쪽 네트워크에서 돌리는 것이 어디서나 같다(ADR 0013 이 crane 을 그렇게 돌린다).
- **영역 생성 타입으로 검증한다:** 영역이 낸 타입이 계약과 어긋나도 같이 틀리므로 E2E 의 판정이 약해진다.
- **전체 가중치로 중립 어댑터를 만든다:** 수 GB 를 받아야 한다. 모델 구성 파일(config.json) 하나와 PEFT 로 층 이름·모양을 얻을 수 있다.

## 결과
- **얻는 것:** `./deploy e2e --mode pipeline` 한 명령이 설치부터 정리까지 하고 종료 코드로 판정한다. 결과는 `deploy/docs/E2E_RESULTS.md` 한 곳에 실행 시각·모드·환경(GPU 이름)·단계별 결과로 쌓인다.
- **감수하는 것:** 한 번에 수십 분이 걸린다(설치, 엔진 기동). 이 환경(WSL2 한 곳)의 결과이고 깨끗한 두 번째 환경 확인은 아니다. 학습되지 않은 어댑터는 값을 만들지 못해 턴 대부분이 실패할 수 있다(pipeline 은 실패 1·2번째의 상태 불변과 3번째마다의 건너뛰기를 계약대로 판정한다). product 모드는 24GB급 GPU 와 학습된 어댑터가 필요하고 이 환경에서 돌려 보지 못했다.
- **계약의 빈 곳:** 모델 적재 완료 상한은 계약 9.1.0 에서 `TimeBudgetTable.model_load` 로 채웠다(변경 요청 model-runtime-007).

## 되돌리는 조건
계약이 적재 완료 상한을 정하면 값을 그 표로 바꾼다. 서버 여러 대 배치(`DeploymentLayout`)를 deploy 가 읽게 되면 엔진을 따로 띄우는 조각 대신 서버별 구성을 쓴다.
