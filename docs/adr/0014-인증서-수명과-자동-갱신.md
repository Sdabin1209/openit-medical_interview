# 0014. 인증서 수명과 자동 갱신

## 상태
승인(2026-11-10, 헤드 위임. ADR 0008의 step-ca 구성을 구체화)

## 맥락
ADR 0008은 step-ca를 띄우되 "인증서 발급 흐름은 계약이 정해진 뒤"로 미뤘다. 사설 CA가 있어도 리프 인증서를 손으로 발급·교체하면 만료가 사고가 된다. 수명, 갱신 방법, 만료 경보를 정해야 한다.

## 결정
- **리프는 ACME(RFC 8555)로 자동 발급·갱신한다.** step-ca에 ACME provisioner `acme`를 둔다(`deploy/pki.py`가 `ca.json`을 설정에서 만든다). ACME 클라이언트는 Caddy(레지스트리 앞단, ADR 0013)이며 갱신도 스스로 한다. 인증서마다 별도 갱신 스크립트나 cron을 두지 않는다. 검증 방식은 http-01·tls-alpn-01이고 CA와 서비스가 같은 compose 네트워크에 있다.
- **발급 범위:** step-ca의 x509 정책(`allow`)이 `OPENIT_CA_ALLOWED_DNS`·`OPENIT_CA_ALLOWED_IPS`에 있는 이름만 발급하게 한다. 이 밖의 이름은 거부한다(ADR 0015).
- **수명(모두 `deploy/env.example`의 값이고 설치처가 덮어쓴다):**

  | 대상 | 기본값 | 근거 |
  |---|---|---|
  | 리프 | 168h(7일) | 자동 갱신을 전제로 짧게 둔다. Let's Encrypt가 6일 인증서를 내는 것과 같은 자릿수다. Caddy는 남은 수명이 1/3이 되면(56h) 갱신하므로 CA가 갱신 시점 이후 2.3일간 멈춰도(주말) 만료되지 않는다. **측정한 값이 아니다.** |
  | 리프 하한 | 5m | step-ca의 `minTLSCertDuration` 기본값. 이보다 짧으면 step-ca가 거부한다. 갱신 시험에 이 값을 쓴다. |
  | 중간 CA | 26280h(3년) | 루트보다 짧게 두어 교체 절차를 루트보다 자주 연습하게 한다. 3년은 **근거가 되는 표준이 없는 선택값**이다. |
  | 루트 | 87600h(10년) | 루트는 신뢰 목록을 모든 기기에 배포해야 바꿀 수 있어 길게 둔다. 10년은 **표준이 아니라 선택값**이다. |

  하위 인증서는 상위보다 오래 살 수 없다(RFC 5280 6.1.3 경로 검증). 설정 검증이 `리프 < 중간 CA < 루트`를 강제하고, 중간 CA를 새로 만들 때 수명은 루트의 남은 수명을 넘지 않게 자른다.
- **루트·중간 CA는 자동 갱신하지 않는다.** 만료 전 경보와 교체 절차를 둔다.
  - `./deploy ca status`: 루트, 중간 CA, 리프, 추가 신뢰 루트, 키오스크 클라이언트 CA의 남은 기간을 보인다. 기준 미만이거나 사슬 검증이 실패하면 rc=1이다. 기준은 `OPENIT_CA_WARN_ROOT`(4320h = 180일), `OPENIT_CA_WARN_INTERMEDIATE`(2160h = 90일), `OPENIT_CA_WARN_LEAF`(24h)이다. 루트·중간의 기준은 **근거가 되는 표준이 없는 선택값**(교체 절차를 두 분기 이상 여유 있게 밟을 시간)이고 측정하지 않았다.
  - Prometheus 인증서 만료 경보(아래). 리프의 24h는 갱신이 시작되는 56h보다 아래이므로, 24h 아래로 내려왔다면 갱신이 한나절 넘게 실패한 것이다. 이 값은 규칙 파일과 `env.example`이 같아야 하며 `tools/checks`의 시험이 확인한다.
  - `./deploy ca rotate`: 중간 CA 교체. `self`는 루트 키로 새 중간 CA를 만들어 검증(루트가 서명, CA 확장, 키 짝, 유효 기간)한 뒤 `deploy/pki/archive/<시각>/`에 이전 파일을 보관하고 설치하며 step-ca를 다시 만든다. 이미 나간 리프는 만료까지 이전 중간 CA 사슬로 유효하고, 새로 발급·갱신되는 리프는 새 중간 CA로 서명된다. `institution`은 새 키와 서명 요청(CSR)을 만들고 `./deploy ca install`로 이어 간다. 절차는 `deploy/docs/CA.md`.
- **감시:** blackbox_exporter(Apache-2.0)가 TLS로 접속해 인증서를 신뢰 목록으로 검증하고 `probe_ssl_earliest_cert_expiry`(서버가 내놓은 사슬에서 가장 이른 만료 시각)를 잰다. Prometheus(Apache-2.0)가 규칙 두 개를 평가한다: `OpenitCertificateExpiresSoon`(ACME로 받는 리프의 남은 시간이 24h 미만이 5분 지속), `OpenitTlsProbeFailed`(검증·접속 실패가 5분 지속). 규칙은 `promtool test rules`로 시험하고(`./deploy doctor`가 돌린다) 알림 전달(Alertmanager)은 설치처가 정한다. 감시 대상은 `./deploy bootstrap`이 설정에서 만든다.
  - step-ca 자신의 서버 인증서는 step-ca가 24시간 수명으로 스스로 갱신해 남은 시간이 늘 24h 아래다(시험에서 확인). 같은 규칙을 걸면 항상 경보이므로 `renewal` 라벨로 구분해 접속·검증 성공만 본다.

## 왜
- 짧은 수명과 자동 갱신은 인증서 폐기(CRL, OCSP)에 기대지 않고 유출 피해를 수명 안으로 묶는 업계 방식이다(ACME의 목적).
- step-ca는 ACME 서버를 내장한 사설 CA이고(Apache-2.0), ACME는 표준(RFC 8555)이라 클라이언트를 바꿀 수 있다. Caddy는 ACME 클라이언트를 내장해 갱신 상태 관리가 필요 없다.
- 갱신 점검 주기 `renew_interval 1m`은 Caddy 기본값(10분)보다 짧다. 갱신이 실패해도 1분마다 다시 시도해 수명의 1/3 여유를 덜 쓴다. 점검은 로컬 상태만 읽는다. 측정하지 않았다.
- Prometheus `scrape_interval 1m`, `storage.tsdb.retention.time 15d`: 만료는 시간·일 단위로 변하므로 1분이면 충분하다고 보았다. 보존 15일은 Prometheus 기본값이다. 둘 다 측정하지 않았다.

## 검토한 대안과 버리는 이유
- **step CLI로 직접 발급하고 cron으로 갱신:** 서비스마다 갱신 스크립트와 재시작 순서를 직접 관리해야 한다.
- **certbot, lego, acme.sh:** 같은 ACME 클라이언트이지만 서비스의 TLS 종단(재적재)을 따로 이어야 한다. Caddy는 종단과 갱신이 한 프로세스다.
- **긴 수명 리프(1년 이상):** 유출·오발급 피해 기간이 길고, 갱신을 손으로 하게 된다.
- **Alertmanager를 기본 구성에 넣기:** 알림 수신처(메일, 메신저)는 설치처마다 다르다. 규칙만 두고 수신처는 설정으로 둔다.

## 결과
- **얻는 것:** 리프는 사람 손 없이 갱신된다. 이 환경에서 5분 수명으로 시험해 약 1분마다 새 인증서가 발급됨을 확인했고, 중간 CA를 교체한 뒤에 갱신된 리프가 새 중간 CA로 서명되었음을 확인했다. 만료 경보 규칙은 `promtool test`로 통과하고, 감시가 실제로 리프 만료를 읽는 것을 확인했다.
- **감수하는 것:** 루트·중간 CA는 사람이 교체한다. 루트·중간의 남은 기간은 Prometheus가 아니라 `./deploy ca status`로만 본다(blackbox는 서버가 내놓은 사슬만 본다). `ca status`를 정기적으로 돌리는 일은 deploy의 스케줄러가 정한다(워크스페이스 규칙). 루트 교체는 절차 문서만 있고 명령으로 만들지 않았다.

## 되돌리는 조건
ACME를 쓸 수 없는 서비스(클라이언트 인증서를 쓰는 기기 등)가 생기면 그 용도의 발급 방식을 새 ADR로 정한다. 측정으로 갱신 지연이 확인되면 기준값을 바꾼다.
