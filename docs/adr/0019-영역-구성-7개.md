# 0019. 영역 구성 7개

## 상태
승인(2026-11-10, 사용자 결정). ADR 0002·0003 의 영역 목록(12개)을 대체한다.

## 맥락
v7 계약은 결정 기록의 영역 12개를 그대로 옮겼다. 상시 HTTP 서비스가 10개, 계약 작업이 98개, 스키마가 424개였고, 영역 경계마다 게이트웨이·나가는 호출 선언·mTLS·잡 선언이 붙었다. 문진을 실제로 돌리는 경로는 survey-service 와 model-runtime 뿐이고 나머지는 모델 제작과 운영 주변이었다. 시스템 전체의 소유자는 한 명이다. 실제 학습과 문항 작성은 다른 담당자가 하며, 이 시스템의 학습 파이프라인은 그 담당자의 학습 작업을 따라 하는 것이다. 문항 작성은 따라 할 필요가 없고, 만든 문항 세트를 시스템에 올릴 수만 있으면 된다.

## 결정
| 구분 | 영역 | 맡는 일 |
|---|---|---|
| 상시 서비스 | survey-service | 문진 진행, 결과, 턴 기록과 업무 로그 수집, 실패 사례 검토, 문항 세트 올리기와 활성화 |
| 상시 서비스 | model-runtime | 모델 서빙, 모델 출력 검증, 모델 패키지 적재와 활성화·롤백 |
| 상시 서비스 | platform | 인증(사람·기기·서비스), 입구, 사설 CA, 감시 |
| 학습 파이프라인(잡) | model-lab | 데이터셋 가져오기, 학습 데이터 준비, 학습, 평가, 모델 패키지 게시 |
| 화면 | kiosk-frontend | 환자용 키오스크 |
| 화면 | admin-console | 직원·의사·관리자용(결과, 문항 세트 올리기, 실패 사례 검토, 모델 활성화 승인·롤백) |
| 도구 | deploy | 배포 기반 |

- 없애는 영역: question-authoring(작성은 시스템 밖, 올리기는 survey-service), synthetic-data(model-lab 의 준비 단계), release-gate(승인은 admin-console, 활성·롤백은 model-runtime), ops-feedback(survey-service 의 컴포넌트).
- 학습 파이프라인과 서빙은 모델 저장소로만 만난다. 모델 패키지는 사설 레지스트리(ADR 0013)에 OCI 아티팩트로 올리고 model-runtime 이 digest 로 받는다.
- 서비스와 모델 통신의 책임선: 모델의 입력·출력과 계약 규칙만으로 판단할 수 있는 것은 model-runtime, 세션 진행 상태가 있어야 판단할 수 있는 것은 survey-service 가 맡는다. 값은 낸 쪽이 한 번만 검증한다(R7).
- 모델 입출력 규칙의 정본은 데이터셋 담당의 `labels.py` 이고 계약은 그것을 따른다. 이 경계는 model-runtime 한 곳에만 닿는다.

## 왜
- 서비스를 나누는 이유는 독립 배포, 서로 다른 팀 소유, 따로 늘려야 하는 부하, 다른 보안 경계다. 이유가 없으면 한 서비스 안의 모듈로 둔다(Sam Newman, *Building Microservices* 2판 2장; Martin Fowler, "MonolithFirst"). 소유자가 한 명이므로 팀 경계로 나눌 이유가 없다(Conway 의 법칙).
- model-runtime 은 GPU 자원과 부하를 따로 늘려야 하고, platform 은 인증이라는 다른 보안 경계이며, 화면 둘은 사용자와 보안 경계(기기 대 직원)가 다르다.
- 학습·평가·게시는 일회성 작업이라 상시 서비스가 아니라 실행 프로세스로 둔다(12-Factor App XII). 학습 파이프라인과 서빙은 모델 저장소를 사이에 두고 만난다(Google Cloud, "MLOps: Continuous delivery and automation pipelines in machine learning").
- 모델 패키지를 OCI 아티팩트로 레지스트리에 두는 것은 OCI Distribution·Image Spec 1.1 의 artifactType 으로 표준화된 방식이며, 이미 있는 레지스트리와 digest 고정을 그대로 쓴다.

## 검토한 대안과 버리는 이유
- **12개 유지:** 경계마다 붙는 비용(게이트웨이, 선언, 계약)이 근거 없이 늘고, 실제 담당이 시스템 밖인 일까지 서비스로 복제한다.
- **학습 파이프라인을 시스템 밖으로:** 소유자가 직접 모델을 학습하고 넣어 봐야 한다.
- **모델 패키지 게시용 HTTP API:** 레지스트리가 이미 있고 digest 고정·전송을 표준으로 제공한다.

## 결과
- **얻는 것:** 상시 서비스 3개, 영역 경계와 계약이 줄고, 학습에서 서빙까지 넘김이 레지스트리 하나로 정리된다.
- **감수하는 것:** survey-service 가 커진다(문진, 기록, 실패 사례, 문항 세트). 컴포넌트 경계로 나눈다(`docs/design.md`).

## 되돌리는 조건
학습 파이프라인이나 문항 올리기를 다른 사람이 이 시스템 안에서 독립 배포로 맡게 되거나, 기록 수집의 부하를 survey-service 와 따로 늘려야 할 때 해당 부분을 영역으로 나눈다.
