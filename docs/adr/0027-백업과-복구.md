# 0027. 백업과 복구: 영역 DB 마다 pg_dump, restic 으로 한 스냅샷, 서버 밖 사본, 일회용 DB 로 복구 시험

## 상태
승인(2026-11-11, 배포 담당). 계약 DeployBackupConfig(배치 설정의 `backup`)를 `./deploy` 가 쓰게 한다(ADR 0026 의 '검증만 하고 아직 쓰지 않는다'를 이행). 이전의 `backup`·`restore`(플랫폼 서버의 PostgreSQL 만, 폴더에 SQL 파일)를 대체한다. 같은 날 기기별 문진표 배치(`device_placements`)도 이 변경에서 쓴다(아래 '기기별 문진표 배치').

## 맥락
이전 `./deploy backup` 은 플랫폼 서버의 PostgreSQL(Keycloak)만 폴더에 저장했고 문진 결과가 있는 survey-service 의 DB(`survey-db`)를 다루지 않았다. 계약은 이미 다음을 정한다.
- 데이터베이스는 그 데이터 주인 영역의 컴포넌트다(D126). 백업은 데이터 주인 영역이, 저장 공간은 platform 이 맡는다. 백업 도구는 restic 이고 백업 저장소는 restic REST 서버(`--private-repos`, append-only 는 쓰지 않음), 백업 직후 `forget --prune` 으로 보존 상한을 지킨다(D130, D111). 정본: `contracts/inputs/DECISIONS.md` D126·D130·D111·D112.
- 백업 보관은 매일 14일(사용자 결정 2026-11-03, OPEN_GAPS U31. D88 U4 '백업 14일(일일)'). 보관 기간은 운영 데이터의 가장 짧은 보존 이하여야 한다(OPEN_GAPS U30).
- 서버 밖 대상은 필수 설정이고 없으면 백업 잡이 경고가 아니라 CRIT 이다(D88 U6). 일일 백업과 정기 복원 시험도 D88 U6 이다.
- 잡 이름 BACKUP·RESTORE·OFFSITE_SYNC·RESTORE_TEST, 잡 결과 JobRunResult(종료 코드 0·75·1, 마지막 줄 JSON), 스냅샷 ID `BackupSnapshotId`(restic 스냅샷 ID, 하나), `DeployBackupConfig` 여섯 칸(저장소 주소, 암호 파일, 저장소 자격 파일, 서버 밖 암호화 키 파일, 서버 밖 주소, 서버 밖 자격 파일).

## 결정
- **대상: compose 서비스 라벨 `io.openit.backup: postgres` 인 서비스 모두.** 그 서비스가 속한 서버(라벨 `io.openit.service` 의 영역이 있는 서버)에서 그 서버의 엔진으로 접속한다. 지금은 platform 의 `postgres`(Keycloak 의 사용자·realm 등)와 survey-service 의 `survey-db`(문진 결과)이고, 영역이 DB 를 더하면 라벨만 달면 된다(deploy 코드를 고치지 않는다). 서버가 다른 DB 도 서버 밖 호출 없이 그 서버의 `docker compose exec` 로 받는다.
- **형식: 데이터베이스마다 `pg_dump --format=custom`, 역할은 `pg_dumpall --globals-only`.** 복구는 `pg_restore --create` 로 하고 그 전에 `DROP DATABASE … WITH (FORCE)`(PostgreSQL 13+ 표준 옵션)로 지운다. 덤프를 뜰 때 `pg_restore --list` 의 테이블 항목 수를 센다(복구 시험의 기준).
- **한 번의 backup = 스냅샷 하나.** 모든 영역의 덤프와 `manifest.json`(영역, 서비스, 서버, 데이터베이스와 테이블 수, 비밀 없음)을 관리 노드의 0700 임시 폴더에 모아 restic 이 한 스냅샷(`/stage`)으로 저장하고 곧바로 지운다. 이유는 계약 `BackupSnapshotId` 와 JobRunResult 가 BACKUP 하나에 스냅샷 ID 하나를 말하기 때문이다. 스냅샷은 `--host <프로젝트 이름> --tag openit` 이라 (host, paths) 묶음이 안정되어 중복 제거와 보관 정리가 일관된다.
- **보관: `forget --keep-within 14d --prune`**(백업이 성공한 직후에만 부르므로 방금 만든 스냅샷은 항상 남는다. 백업이 14일 넘게 멈춰도 마지막 백업이 지워지지 않는다). 14일은 사용자 결정(U31)과 D88 U4 이고 가장 짧은 운영 보존(D88 U4 의 처리 끝난 원본 Trace 30일) 이하다(U30). 서버 밖 저장소에도 같은 정리를 한다. 계약에 보존 칸이 없어 값은 `deploy/backup.py` 의 상수 하나이고 운영자가 바꾸는 값이 아니다(바꾸려면 계약 변경 요청이 필요하다).
- **저장소: platform 서버의 `backup-store`(restic/rest-server, `--private-repos`)와 앞단 `backup`(Caddy, ACME 로 step-ca 에서 인증서).** 레지스트리와 같은 구성(ADR 0013·0014)이다. 계약 `repository_url`(`rest:https://<이름>[:<포트>]/<저장소>`)의 이름·포트가 앞단의 인증서 이름과 듣는 포트가 되고(`generated/backup.env`), 저장소 이름은 자격의 사용자와 같아야 한다(`--private-repos` 는 사용자 폴더만 연다). `repository_url` 의 이름은 사설 CA 가 발급하는 이름(`OPENIT_CA_ALLOWED_DNS`)이어야 해서 기본 목록에 `backup` 을 더했고 doctor 가 확인한다. 자격 파일은 한 줄 `사용자:비밀번호`(RFC 7617 user-pass)이고 서버의 인증 파일(bcrypt `.htpasswd`)은 deploy 가 그것에서 만든다(이미 있는 줄이 맞으면 그대로 둔다).
- **저장소는 하나, 영역별은 아니다.** D130 은 영역별 저장소·자격을 말하지만 계약 DeployBackupConfig 는 저장소 주소와 자격이 각각 하나다(deploy 가 도는 잡의 입력). 영역 구분은 스냅샷 안의 폴더(`/stage/<영역>/`)와 manifest 가 한다. 영역별 저장소로 나누려면 계약이 영역마다 주소·자격을 가져야 한다(변경 요청 필요, 하지 않았다).
- **restic 은 관리 노드의 빌드 엔진에서 일회용 컨테이너로 돈다**(이미지 `restic/restic`, digest 고정, compose.yaml 의 `backup-client`). 서버 한 대 배치는 compose 의 `edge` 네트워크로 앞단의 별칭에 닿고(호스트 포트를 게시하지 않는다), 여러 서버는 플랫폼 서버 주소의 게시 포트(`flows` 의 '관리 노드 → 플랫폼 서버')로 닿으며 `--add-host` 로 이름을 푼다(crane 과 같은 방식). 인증서는 신뢰 목록으로 검증한다(검증을 끄지 않는다). 저장소 주소(자격 포함)는 임시 파일(0700 폴더)로, 암호는 설정이 가리키는 파일로 마운트해 `RESTIC_REPOSITORY_FILE`·`RESTIC_PASSWORD_FILE`(복사는 `RESTIC_FROM_…`)로만 준다(D84: 비밀은 환경 변수·명령줄이 아니라 파일).
- **서버 밖: `restic copy` 로 로컬 저장소의 스냅샷을 서버 밖 REST 저장소(`rest:` + `offsite_url`)에 복사한다**(OFFSITE_SYNC). `encryption_key_file` 은 서버 밖 저장소의 restic 암호다(restic 은 저장소 암호로 모든 것을 암호화한다. 로컬 암호와 다르게 두어 로컬 암호가 새도 서버 밖 사본은 읽히지 않는다). `offsite_credentials_file` 은 한 줄 `사용자:비밀번호` 다. 서버 밖 저장소는 로컬의 쪼개기 값으로 만든다(`init --copy-chunker-params`, restic 문서). 복사된 스냅샷은 새 ID 를 갖는다(시험에서 확인). 서버 밖 사본에서 복구할 때는 그 저장소의 ID 를 쓴다(`restore --offsite`). 이미 복사한 것은 건너뛴다(멱등, 시험에서 확인).
- **서버 밖 설정이 틀리거나 파일이 없으면 backup 은 덤프를 뜨기 전에 멈춘다**(`CRIT:` 표준 오류, 종료 코드 1, D88 U6). `up` 도 배치 설정 파일이 있는데 `backup` 칸이 틀리면 서비스를 띄우지 않는다(백업 없이 운영이 시작되지 않게). 배치 설정 파일이 없는 서버 한 대 기본 설치는 백업 설정이 없어 backup 이 시작하지 않고 doctor 가 알린다.
- **복구(`restore`)**: 스냅샷의 manifest 를 읽고 영역마다 그 영역이 있는 서버의 DB 서비스에 복구한다. 그 DB 에(간접으로) `depends_on` 하는 서비스는 돌고 있든 아니든 멈추고, 복구가 끝나면 모두 다시 띄운다. 덮어쓰므로 `--yes` 가 필요하다(없으면 종료 코드 2). 복구한 데이터는 스트림으로 흘린다(`restic dump | pg_restore`, 디스크에 풀지 않고 양쪽 종료 코드를 모두 본다).
- **복구 시험(`restore-test`)**: 운영 DB 를 건드리지 않고 같은 이미지의 일회용 PostgreSQL(네트워크 없음, 메모리 파일시스템)에 영역마다 복구해, 모든 데이터베이스가 `pg_restore` 로 복구되고 복구된 테이블 수가 백업 때 목차의 테이블 수와 같은지 본다. 끝나면 컨테이너를 지운다. 행 내용의 같음은 운영 DB 가 계속 바뀌어 운영 시험에서 확인할 수 없고 샌드박스 시험(`tools/backup-sandbox`)이 한다.
- **잡 결과와 종료 코드**: 네 명령은 끝에 표준 출력으로 JobRunResult 한 줄을 낸다. 종료 코드 0 성공, 75 일시적 실패(DB 컨테이너가 떠 있지 않음, 저장소 잠금을 얻지 못함 = restic 종료 코드 11), 1 그 밖의 실패(sysexits.h EX_TEMPFAIL 75, D130). 사용법 오류(`--yes` 없음)는 2 이고 잡 결과를 내지 않는다.
- **백업 비밀 파일**: 배치 설정이 가리키는 관리 노드의 절대 경로이고 권한이 0600 이어야 한다(group·other 가 읽으면 doctor 와 backup 이 거절). `secrets init` 이 없는 것을 만든다(저장소 암호, 서버 밖 암호, 저장소 자격. 무작위 값, 값은 출력하지 않음). 서버 밖 자격은 서버 밖 대상이 주는 것이라 만들지 않는다.

## 기기별 문진표 배치(device_placements)
계약에 경로가 이미 있다: `DeploymentLayout.device_placements`(배치 설정) → 파일 `DevicePlacementTable`(소유 survey-service, 사용자 결정 U86) → `SurveyServiceEnv.SURVEY_DEVICE_PLACEMENTS_FILE`. deploy 가 배치 설정에서 표를 `deploy/generated/survey-service/device-placements.json` 으로 쓰고 compose 가 survey-service 의 `/etc/openit/device-placements.json` 에 읽기 전용으로 마운트한다(여러 서버면 다른 파일과 같이 서버의 스테이징 폴더로 올라간다). survey-service 는 시작할 때 읽고 세션을 시작할 때 mTLS 로 확인된 기기 ID(XFCC 의 CN)로 기본 문진표를 고른다(시작 코드의 문진표 > 요청의 문진표 > 기기 배치 > 활성이 하나일 때 그것). 그래서 배치된 기기의 키오스크는 먼저 `questionnaire_id` 없이 보내도 422 `QUESTIONNAIRE_REQUIRED` 를 받지 않고(계약 startSession), 배치가 없고 활성 문진표가 둘 이상일 때만 환자에게 묻는다(kiosk-frontend 는 그때만 선택 화면을 보인다). 계약을 바꾸지 않았다. 파일은 시작할 때만 읽으므로 배치가 바뀌면 `up` 이 survey-service 를 다시 만든다. 한 기기에 기본 문진표가 둘이면 어느 것이 기본인지 정할 수 없어 배치 설정을 거절한다(survey-service 는 기기 ID 로 하나를 고른다. 이 규칙은 계약 스키마가 말하지 않는 구조 규칙이다). 문진표가 실제로 활성인지는 deploy 가 모른다(survey-service 가 활성 문항 세트가 없으면 400 으로 답한다).

## 왜
- pg_dump/pg_restore 는 PostgreSQL 문서가 논리 백업으로 권하는 표준 도구이고 custom 형식은 압축되고 선택 복구가 된다. 정본(D85(6), D126)이 PostgreSQL 이다.
- restic·REST 서버·`--private-repos`·`forget --prune` 은 정본 결정이다(D111·D130). `restic copy` 는 restic 문서가 저장소 사이 복사로 안내하는 방법이고 서버 밖 사본이 따로 암호화된다(D88 U6 '암호화').
- 한 스냅샷은 계약이 정한 모양이다(JobRunResult 의 `snapshot_id` 하나).
- 앞단 Caddy 와 ACME 는 계약 C14(영역 사이 모든 HTTP 는 TLS)와 레지스트리의 선례(ADR 0013·0014)를 따른 것이다. rest-server 가 직접 TLS 를 끝내려면 인증서를 받고 갱신하는 일을 따로 해야 한다.
- 일회용 컨테이너 안의 restic 은 서버에 restic 을 설치하지 않게 하고(이미지 digest 고정) 관리 노드의 비밀 파일을 원격 엔진에 올릴 필요가 없다.

## 검토한 대안과 버리는 이유
- **데이터베이스마다 표준 입력 스냅샷(`restic backup --stdin`):** 디스크에 평문 덤프가 남지 않으나 스냅샷이 여러 개가 되어 BACKUP 하나의 `snapshot_id` 하나와 맞지 않고, 덤프가 도중에 실패해도 스냅샷이 생겨 지워야 한다. 임시 폴더는 0700 이고 올린 직후 지운다(감수: 관리 노드의 디스크 여유가 덤프 크기만큼 필요하다).
- **`pg_dumpall` 한 파일이나 폴더에 gzip SQL(이전 방식):** `--clean` 덤프가 쓰는 중인 DB 를 지우려다 실패하고(ADR 0008) 서버 밖 암호화·중복 제거·보관 정리가 따로 필요하다. 이전 형식의 백업 폴더(`deploy/backups/postgres-*`)는 새 `restore` 가 읽지 않는다.
- **WAL 보관·시점 복구(pg_basebackup):** 복구 시점 목표는 사용자가 정하지 않았다(OPEN_GAPS O16, 일일 백업이 정본 U31). 일일 논리 백업이면 복구 시점은 최대 하루 전이다.
- **age 등 파일 암호화:** D112 가 restic 의 대칭 암호를 사용자 확정으로 정했다(age 는 중복 제거·증분·검증을 포기).
- **append-only 저장소:** D112 의 선택이었으나 D130 이 이어서 append-only 를 쓰지 않는다고 정했다(`forget --prune` 이 지워야 한다). 서버가 침해되면 백업을 지울 수 있는 위험은 서버 밖 사본이 막는다.
- **restic 을 플랫폼 서버의 엔진에서 돌린다:** 암호·자격 파일을 서버에 올려야 하고(스테이징) 표준 입력과 비밀을 한 컨테이너에서 같이 다루기 어렵다.
- **영역마다 따로 backup·restore 잡(D130 의 그림):** 계약이 배치 설정의 backup 칸을 deploy 가 도는 잡의 입력으로 정했다(DeployBackupConfig 설명). 이 변경은 그 계약대로다.

## 결과
- **얻는 것:** 문진 결과(survey-db)와 Keycloak 이 같은 스냅샷에 들어가고, 영역 DB 를 더해도 라벨만 달면 된다. DB 가 플랫폼과 다른 서버에 있어도 된다. 서버 밖 사본이 있고 정기 복구 시험이 있다. `tools/backup-sandbox` 가 서버 한 대와 두 대에서 데이터 → backup → 삭제 → restore → 지문 비교를 한다.
- **감수하는 것:**
  - 백업하는 동안 관리 노드에 덤프 크기만큼의 임시 디스크가 필요하다. DB 크기와 백업 시간은 측정하지 않았다.
  - 백업 저장소는 플랫폼 서버에 하나고 `down --volumes` 가 그 볼륨을 지운다(서버 밖 사본은 남는다). 저장소 암호를 잃으면 읽을 수 없다. 관리 노드의 백업 비밀 파일을 별도로 보관한다.
  - 백업 대상은 PostgreSQL DB 뿐이다. 다음은 대상이 아니다: step-ca 의 저장소(`step-ca-data`: 발급된 인증서는 ACME 로 다시 받는다), 레지스트리(`registry-data`: 이미지는 `images.lock` 과 빌드로 다시 올린다), Prometheus·Alertmanager 데이터(지표와 침묵 규칙), model-runtime 의 `model-runtime-data`(활성화 기록과 받은 패키지: DB 가 아니라 파일이다. 이 영역에 백업 방법이 필요한지는 model-runtime 이 정할 일로 남긴다), 관리 노드의 `deploy/secrets/`·`deploy/pki/`·`deploy/.env`·`deploy/layout.json`(INSTALL.md 10절에서 따로 보관).
  - 운영 데이터의 보존 기간(D88 U4 30일)보다 백업(14일)이 짧으므로 U30 은 지켜지지만, 이 값이 병원 규정과 맞는지는 확인하지 않았다.
  - 실행 일정(매일)은 deploy 의 스케줄러가 정한다(D39). 이 리포의 deploy 에는 아직 스케줄러가 없어 이 ADR 은 일정을 만들지 않는다. 명령이 한 번 실행하는 잡이다(멱등: 같은 입력으로 다시 실행해도 안전하다. offsite-sync 는 시험에서 확인).
  - 실제 원격(SSH) 엔진, 공용 인터넷의 서버 밖 서비스(S3 호환 등), 대용량 DB 는 시험하지 못했다. 서버 밖 대상은 같은 이미지의 REST 서버를 TLS 로 띄워 시험했다.
  - 서버 밖 호출(`restic copy`)은 영역 게이트웨이의 CONNECT 터널을 지나지 않고 관리 노드의 일회용 컨테이너가 직접 나간다(CONVENTIONS 13절의 '유일한 예외' 목록을 이 작업 트리에서 읽지 못해 거기에 드는지 확인하지 못했다). 헤드가 확인할 일이다.
- 값: 보관 14일(위), 일회용 PostgreSQL 준비 상한 60초(측정하지 않았다, 되면 곧바로 넘어간다).

## 되돌리는 조건
계약이 영역마다 저장소 주소·자격을 가지게 되면 영역별 저장소로 나눈다. 복구 시점 목표가 정해져 하루보다 짧아야 하면 WAL 보관으로 바꾼다. 서버 밖 대상이 REST 가 아닌 것(S3 등)이어야 하면 계약 OffsiteBackupUrl 의 모양을 바꾸는 요청을 낸다. 영역이 DB 가 아닌 파일 상태의 백업을 요구하면 라벨 값(`postgres` 밖)을 더한다.
