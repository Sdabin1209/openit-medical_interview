# 0027. 백업과 복구: 영역 DB 마다 pg_dump, restic 으로 한 스냅샷, 서버 밖 사본, 일회용 DB 로 복구 시험

## 상태
승인(2026-11-11, 배포 담당). 계약 DeployBackupConfig(배치 설정의 `backup`)를 `./deploy` 가 쓰게 한다(ADR 0026 의 '검증만 하고 아직 쓰지 않는다'를 이행). 이전의 `backup`·`restore`(플랫폼 서버의 PostgreSQL 만, 폴더에 SQL 파일)를 대체한다. 같은 날 기기별 문진표 배치(`device_placements`)도 이 변경에서 쓴다(아래 '기기별 문진표 배치').

**갱신(2026-11-11, 배포 담당): 상태 파일을 대상에 넣었다.** 백업 표지(라벨 `io.openit.backup`)의 값을 `postgres` 하나에서 `postgres`·`files` 둘로 넓혔다(아래 '상태 파일'). 첫 대상은 model-runtime 의 활성화·롤백 기록이다. 이전 판이 '대상이 아니다'로 적은 model-runtime 상태를 이 갱신이 대상으로 바꿨다.

**갱신(2026-11-11, 배포 담당): 레지스트리의 모델 패키지를 대상에 넣었다.** model-runtime 의 활성화 기록(release-log)은 모델 패키지의 digest 를 가리키는데 그 패키지(어댑터, 목록표, 평가 보고서)는 레지스트리 볼륨(`registry-data`)에만 있었다. 서버를 잃고 백업에서 복구하면 기록은 돌아오고 그것이 가리키는 패키지는 없었다. 모델 패키지는 다시 게시하면 digest 가 달라지는 다시 만들 수 없는 산출물이라 받는다. 영역 이미지는 소스에서 다시 빌드하므로 뺀다(아래 '모델 패키지(레지스트리)'). 표지(라벨)로 고르는 대상이 아니라 deploy 가 레지스트리(플랫폼의 구성요소)에서 직접 받는다. manifest 형식은 3(`registries`)이고 1·2 도 읽는다.

## 맥락
이전 `./deploy backup` 은 플랫폼 서버의 PostgreSQL(Keycloak)만 폴더에 저장했고 문진 결과가 있는 survey-service 의 DB(`survey-db`)를 다루지 않았다. 계약은 이미 다음을 정한다.
- 데이터베이스는 그 데이터 주인 영역의 컴포넌트다(D126). 백업은 데이터 주인 영역이, 저장 공간은 platform 이 맡는다. 백업 도구는 restic 이고 백업 저장소는 restic REST 서버(`--private-repos`, append-only 는 쓰지 않음), 백업 직후 `forget --prune` 으로 보존 상한을 지킨다(D130, D111). 정본: `contracts/inputs/DECISIONS.md` D126·D130·D111·D112.
- 백업 보관은 매일 14일(사용자 결정 2026-11-03, OPEN_GAPS U31. D88 U4 '백업 14일(일일)'). 보관 기간은 운영 데이터의 가장 짧은 보존 이하여야 한다(OPEN_GAPS U30).
- 서버 밖 대상은 필수 설정이고 없으면 백업 잡이 경고가 아니라 CRIT 이다(D88 U6). 일일 백업과 정기 복원 시험도 D88 U6 이다.
- 잡 이름 BACKUP·RESTORE·OFFSITE_SYNC·RESTORE_TEST, 잡 결과 JobRunResult(종료 코드 0·75·1, 마지막 줄 JSON), 스냅샷 ID `BackupSnapshotId`(restic 스냅샷 ID, 하나), `DeployBackupConfig` 여섯 칸(저장소 주소, 암호 파일, 저장소 자격 파일, 서버 밖 암호화 키 파일, 서버 밖 주소, 서버 밖 자격 파일).

## 결정
- **대상: compose 서비스 라벨 `io.openit.backup: postgres` 인 서비스 모두.** 그 서비스가 속한 서버(라벨 `io.openit.service` 의 영역이 있는 서버)에서 그 서버의 엔진으로 접속한다. 지금은 platform 의 `postgres`(Keycloak 의 사용자·realm 등)와 survey-service 의 `survey-db`(문진 결과)이고, 영역이 DB 를 더하면 라벨만 달면 된다(deploy 코드를 고치지 않는다). 서버가 다른 DB 도 서버 밖 호출 없이 그 서버의 `docker compose exec` 로 받는다.
- **상태 파일(`files`): compose 서비스 라벨 `io.openit.backup: files` 인 서비스가 쓰는 볼륨의 지정한 경로.** 영역이 DB 없이 파일에 상태를 두는 경우의 표지다(D126: 상태의 주인은 그 영역, 백업은 영역의 몫). 같은 라벨 키가 저장소의 종류를 말하고, 종류에 따라 짝 라벨이 붙는다.
  - `io.openit.backup: postgres`: 그 서비스가 영역 PostgreSQL 이다(위).
  - `io.openit.backup: files` + `io.openit.backup.volume: <compose 볼륨 키>` + `io.openit.backup.paths: <볼륨 안의 상대 경로들, 공백으로 나눔>`: 그 볼륨의 그 경로(파일이나 폴더)만 tar 로 받는다. 경로는 글자 `A-Z a-z 0-9 . _ -` 와 `/` 뿐이고 점으로 시작하는 요소(`.`, `..`)나 절대 경로는 거절한다(복구가 그 경로를 지운다). 볼륨이 그 서비스가 쓰는 것이 아니면 거절한다.
  - 소유 영역은 같은 서비스의 라벨 `io.openit.service` 이고, 그 영역이 있는 서버의 엔진에서 받는다(DB 와 같다).
  - **서비스가 도는 중에 복사해도 깨지지 않는 파일만 이 값으로 표지한다**(덧붙이기만 하는 기록, 통째로 바꿔 쓰는 파일). 돌아가는 중에 복사하면 깨질 수 있는 저장소(SQLite 의 데이터베이스 파일 등)는 이 값으로 표지하지 않는다. 그런 저장소가 생기면 그 엔진의 일관된 백업 방법(SQLite 는 온라인 백업 API)을 쓰는 새 값을 더한다(아래 '되돌리는 조건'). 지금 `files` 를 쓰는 곳은 model-runtime 하나다.
  - 받는 방법: 서버의 엔진에서 일회용 컨테이너(네트워크 없음, 읽기 전용 루트, 볼륨은 `:ro`, 권한은 `DAC_READ_SEARCH` 만, 이미지는 모든 서버가 이미 가진 digest 고정 Caddy 이미지의 busybox `tar`)가 경로와 그 **부모 폴더 항목**(소유자·모드, 재귀 없이)을 tar 로 낸다. 부모 폴더를 담는 이유: 볼륨이 통째로 사라진 뒤 복구하면 부모 폴더(예: `cache`)가 root 소유로 만들어져 영역 사용자가 그 안에 새 폴더를 못 만든다. 볼륨이나 경로가 아직 없으면(서비스가 한 번도 쓰지 않았다) 빈 tar 이고 백업이 볼륨을 만들지 않는다.
  - model-runtime: 서비스 라벨이 `io.openit.backup.volume: model-runtime-data`, `io.openit.backup.paths: cache/model-runtime/release-log.jsonl`(활성화·롤백 기록, 승인자·시각·사유가 든 JSON Lines 한 파일)이다. **활성 패키지 포인터는 따로 저장하지 않고 이 기록에서 구하므로**(model-runtime ADR 0002) 이 한 파일이 활성 포인터와 기록 둘이다. 덧붙이기만 하는 파일이라 도는 중에 복사해도 앞부분이 깨지지 않고, 줄바꿈 없이 끝난 마지막 줄은 읽을 때 버린다(같은 ADR). **받은 패키지(`cache/model-runtime/packages/…`)와 기반 모델 가중치는 받지 않는다**: 레지스트리에서 digest 로 다시 받는다(패키지는 `link_registry` 가 활성화 요청 때 받고, 가중치는 엔진이 받는다). 이 가정은 레지스트리가 그 패키지를 가지고 있을 때 맞는데, 레지스트리의 모델 패키지도 이 백업이 함께 받으므로(아래 '모델 패키지(레지스트리)') 서버를 잃고 복구해도 같은 digest 로 다시 있다.
  - 경로 두 곳(compose 라벨과 model-runtime 소스의 상태 폴더·기록 파일 이름)이 어긋나면 백업이 빈 것을 받는다. `tools/checks` 시험이 영역 소스와 라벨이 같은지 본다.
- **모델 패키지(레지스트리): local 레지스트리의 모델 패키지 저장소(`OPENIT_MODEL_REGISTRY_REPOSITORY`, 기본 `openit/model-package`)에서 태그 `sha256-<digest 16진수>` 가 달린 패키지 모두.** model-runtime 의 게시 도구가 패키지마다 다는 태그다(model-runtime ADR 0008. 태그 목록이 OCI Distribution Spec 에서 저장소의 항목을 나열하는 표준 길이다). 태그 없이 digest 로만 올린 매니페스트는 나열되지 않아 받지 못한다(이 태그를 다는 게시 도구 이전의 패키지는 model-runtime 의 목록에도 나오지 않는다).
  - 받는 방법: 관리 노드의 일회용 컨테이너 crane(`registry-client`, 이미 digest 로 고정된 이미지, Apache-2.0)이 레지스트리 API 로 `ls` 한 뒤 패키지마다 `pull --format oci` 로 **OCI 이미지 레이아웃**(OCI Image Layout Spec: `oci-layout`, `index.json`, `blobs/sha256/`)을 `/stage/platform/registry/<저장소>/<digest 16진수>/` 에 낸다. 내려받은 직후 deploy 가 색인의 매니페스트 digest 가 태그가 말하는 digest 와 같은지, 매니페스트·config·layer 파일의 SHA-256 과 크기가 목록과 같은지 다시 계산해 본다(깨진 내보내기가 스냅샷에 들어가지 않게). 저장소가 아직 없으면(`NAME_UNKNOWN`) 빈 목록이고, 레지스트리에 닿지 못하면 종료 코드 75 다. manifest 에는 저장소 이름, 패키지마다 digest 와 크기 합이 든다.
  - 복구: 레지스트리가 떠 있지 않으면 띄우고(`registry-store`, `registry`) 스냅샷의 폴더를 `restic dump`(tar)로 관리 노드의 0700 임시 폴더에 풀어(PEP 706 `data` 필터) 위와 같은 확인을 한 뒤 패키지마다 `crane push` 로 태그 `sha256-<digest>` 에 올리고 `crane digest` 가 같은 digest 를 주는지 본다. 매니페스트 바이트를 그대로 올리므로 digest 가 같고, 그래서 복구한 활성화 기록의 digest 가 레지스트리의 패키지와 다시 이어진다. **상태 볼륨(model-runtime)보다 먼저 복구한다**: model-runtime 은 시작할 때 기록의 마지막 활성 패키지를 레지스트리에서 받는다. 레지스트리에 이미 있는 것은 지우거나 바꾸지 않는다(더하기만 한다. 영역 이미지는 `./deploy bootstrap` 이 올린다).
  - 복구 시험(`restore-test`): 같은 방식으로 풀어 digest·크기를 확인만 한다(운영 레지스트리에 올리지 않는다).
  - **외부 레지스트리(`OPENIT_REGISTRY_MODE=external`)는 받지 않는다.** 그 레지스트리는 설치처가 운영하는 서비스라 내구성과 백업은 운영처 몫이다(복제·스냅샷 등, 우리는 그 서비스의 자격·저장 방식을 알지 못한다). `backup` 이 그렇다고 한 줄 알리고 `doctor` 가 같은 말을 한다. 외부 레지스트리를 쓰는 설치에서 모델 패키지를 가진 스냅샷을 복구하면 패키지는 올리지 않고 경고만 한다(운영처가 그 레지스트리를 복구한다). 외부 레지스트리를 쓰면서 우리가 받으려면 레지스트리 클라이언트가 외부 주소와 자격을 알아야 하는데 지금 deploy 의 클라이언트(`crane()`)는 local 전용이다(external 의 push·존재 확인은 도커 엔진의 표준 경로다, ADR 0013). 필요해지면 새 결정이다.
  - **영역 이미지는 받지 않는다**: 이미지는 소스(git)와 `images.lock`·digest 로 고정한 기반 이미지에서 `./deploy build` 로 다시 만들고 `./deploy bootstrap` 이 다시 올린다(ADR 0013·0024). 모델 패키지와 달리 어느 기록도 이미지의 digest 를 가리키지 않는다(`images.lock` 은 build 가 다시 쓴다). 다시 만든 이미지의 digest 는 같다고 보장하지 않는다(빌드 증명 때문에 달라질 수 있다, ADR 0013). 한 가지 한계: 이미지 롤백(INSTALL.md 9절)은 레지스트리에 이전 digest 가 남아 있을 때 `pull` 로 되는데, 레지스트리를 잃었으면 그 커밋을 체크아웃해 다시 빌드해야 한다.
- **형식: 데이터베이스마다 `pg_dump --format=custom`, 역할은 `pg_dumpall --globals-only`.** 복구는 `pg_restore --create` 로 하고 그 전에 `DROP DATABASE … WITH (FORCE)`(PostgreSQL 13+ 표준 옵션)로 지운다. 덤프를 뜰 때 `pg_restore --list` 의 테이블 항목 수를 센다(복구 시험의 기준).
- **한 번의 backup = 스냅샷 하나.** 모든 영역의 덤프·상태 파일 tar·모델 패키지 레이아웃과 `manifest.json`(영역, 서비스, 서버, 데이터베이스와 테이블 수, 상태 파일의 경로·크기·SHA-256, 모델 패키지의 digest·크기, 비밀 없음. 형식 3, 형식 2(파일까지)와 1(DB 만)도 읽는다)을 관리 노드의 0700 임시 폴더에 모아 restic 이 한 스냅샷(`/stage`)으로 저장하고 곧바로 지운다. 이유는 계약 `BackupSnapshotId` 와 JobRunResult 가 BACKUP 하나에 스냅샷 ID 하나를 말하기 때문이다. 스냅샷은 `--host <프로젝트 이름> --tag openit` 이라 (host, paths) 묶음이 안정되어 중복 제거와 보관 정리가 일관된다.
- **보관: `forget --keep-within 14d --prune`**(백업이 성공한 직후에만 부르므로 방금 만든 스냅샷은 항상 남는다. 백업이 14일 넘게 멈춰도 마지막 백업이 지워지지 않는다). 14일은 사용자 결정(U31)과 D88 U4 이고 가장 짧은 운영 보존(D88 U4 의 처리 끝난 원본 Trace 30일) 이하다(U30). 서버 밖 저장소에도 같은 정리를 한다. 계약에 보존 칸이 없어 값은 `deploy/backup.py` 의 상수 하나이고 운영자가 바꾸는 값이 아니다(바꾸려면 계약 변경 요청이 필요하다).
- **저장소: platform 서버의 `backup-store`(restic/rest-server, `--private-repos`)와 앞단 `backup`(Caddy, ACME 로 step-ca 에서 인증서).** 레지스트리와 같은 구성(ADR 0013·0014)이다. 계약 `repository_url`(`rest:https://<이름>[:<포트>]/<저장소>`)의 이름·포트가 앞단의 인증서 이름과 듣는 포트가 되고(`generated/backup.env`), 저장소 이름은 자격의 사용자와 같아야 한다(`--private-repos` 는 사용자 폴더만 연다). `repository_url` 의 이름은 사설 CA 가 발급하는 이름(`OPENIT_CA_ALLOWED_DNS`)이어야 해서 기본 목록에 `backup` 을 더했고 doctor 가 확인한다. 자격 파일은 한 줄 `사용자:비밀번호`(RFC 7617 user-pass)이고 서버의 인증 파일(bcrypt `.htpasswd`)은 deploy 가 그것에서 만든다(이미 있는 줄이 맞으면 그대로 둔다).
- **저장소는 하나, 영역별은 아니다.** D130 은 영역별 저장소·자격을 말하지만 계약 DeployBackupConfig 는 저장소 주소와 자격이 각각 하나다(deploy 가 도는 잡의 입력). 영역 구분은 스냅샷 안의 폴더(`/stage/<영역>/`)와 manifest 가 한다. 영역별 저장소로 나누려면 계약이 영역마다 주소·자격을 가져야 한다(변경 요청 필요, 하지 않았다).
- **restic 은 관리 노드의 빌드 엔진에서 일회용 컨테이너로 돈다**(이미지 `restic/restic`, digest 고정, compose.yaml 의 `backup-client`). 서버 한 대 배치는 compose 의 `edge` 네트워크로 앞단의 별칭에 닿고(호스트 포트를 게시하지 않는다), 여러 서버는 플랫폼 서버 주소의 게시 포트(`flows` 의 '관리 노드 → 플랫폼 서버')로 닿으며 `--add-host` 로 이름을 푼다(crane 과 같은 방식). 인증서는 신뢰 목록으로 검증한다(검증을 끄지 않는다). 저장소 주소(자격 포함)는 임시 파일(0700 폴더)로, 암호는 설정이 가리키는 파일로 마운트해 `RESTIC_REPOSITORY_FILE`·`RESTIC_PASSWORD_FILE`(복사는 `RESTIC_FROM_…`)로만 준다(D84: 비밀은 환경 변수·명령줄이 아니라 파일).
- **서버 밖: `restic copy` 로 로컬 저장소의 스냅샷을 서버 밖 REST 저장소(`rest:` + `offsite_url`)에 복사한다**(OFFSITE_SYNC). `encryption_key_file` 은 서버 밖 저장소의 restic 암호다(restic 은 저장소 암호로 모든 것을 암호화한다. 로컬 암호와 다르게 두어 로컬 암호가 새도 서버 밖 사본은 읽히지 않는다). `offsite_credentials_file` 은 한 줄 `사용자:비밀번호` 다. 서버 밖 저장소는 로컬의 쪼개기 값으로 만든다(`init --copy-chunker-params`, restic 문서). 복사된 스냅샷은 새 ID 를 갖는다(시험에서 확인). 서버 밖 사본에서 복구할 때는 그 저장소의 ID 를 쓴다(`restore --offsite`). 이미 복사한 것은 건너뛴다(멱등, 시험에서 확인).
- **서버 밖 설정이 틀리거나 파일이 없으면 backup 은 덤프를 뜨기 전에 멈춘다**(`CRIT:` 표준 오류, 종료 코드 1, D88 U6). `up` 도 배치 설정 파일이 있는데 `backup` 칸이 틀리면 서비스를 띄우지 않는다(백업 없이 운영이 시작되지 않게). 배치 설정 파일이 없는 서버 한 대 기본 설치는 백업 설정이 없어 backup 이 시작하지 않고 doctor 가 알린다.
- **복구(`restore`)**: 스냅샷의 manifest 를 읽고 영역마다 그 영역이 있는 서버의 DB 서비스에 복구한다. DB 다음에 레지스트리의 모델 패키지를 올리고(위), 그 뒤 상태 파일을 되돌린다. 그 DB 에(간접으로) `depends_on` 하는 서비스는 돌고 있든 아니든 멈추고, 복구가 끝나면 모두 다시 띄운다. 상태 파일은 그 볼륨을 쓰는 서비스(와 그것에 의존하는 서비스)를 멈추고, 백업한 경로만 비운 뒤(백업 때 없던 파일이 남지 않게, 경로 밖의 받은 패키지는 건드리지 않는다) tar 를 풀고(`CHOWN`·`DAC_OVERRIDE`·`FOWNER` 만 가진 일회용 컨테이너, 소유자·모드 복원) 다시 띄운다. 파일을 시작할 때 읽는 서비스(model-runtime)가 복구한 기록을 다시 읽어야 하기 때문이다. 볼륨이 없으면 compose 가 만들게 한다(`compose create`). 덮어쓰므로 `--yes` 가 필요하다(없으면 종료 코드 2). 복구한 데이터는 스트림으로 흘린다(`restic dump | pg_restore`, 디스크에 풀지 않고 양쪽 종료 코드를 모두 본다).
- **복구 시험(`restore-test`)**: 운영 DB 를 건드리지 않고 같은 이미지의 일회용 PostgreSQL(네트워크 없음, 메모리 파일시스템)에 영역마다 복구해, 모든 데이터베이스가 `pg_restore` 로 복구되고 복구된 테이블 수가 백업 때 목차의 테이블 수와 같은지 본다. 끝나면 컨테이너를 지운다. 상태 파일은 스냅샷의 tar 를 읽어 파일마다 경로·크기·SHA-256 이 백업 때 manifest 와 같은지 본다(운영 볼륨은 건드리지 않는다). 행 내용의 같음은 운영 DB 가 계속 바뀌어 운영 시험에서 확인할 수 없고 샌드박스 시험(`tools/backup-sandbox`)이 한다.
- **잡 결과와 종료 코드**(`processed_count` 는 데이터베이스 수 + 상태 파일 볼륨 수 + 모델 패키지 수): 네 명령은 끝에 표준 출력으로 JobRunResult 한 줄을 낸다. 종료 코드 0 성공, 75 일시적 실패(DB 컨테이너가 떠 있지 않음, 저장소 잠금을 얻지 못함 = restic 종료 코드 11), 1 그 밖의 실패(sysexits.h EX_TEMPFAIL 75, D130). 사용법 오류(`--yes` 없음)는 2 이고 잡 결과를 내지 않는다.
- **백업 비밀 파일**: 배치 설정이 가리키는 관리 노드의 절대 경로이고 권한이 0600 이어야 한다(group·other 가 읽으면 doctor 와 backup 이 거절). `secrets init` 이 없는 것을 만든다(저장소 암호, 서버 밖 암호, 저장소 자격. 무작위 값, 값은 출력하지 않음). 서버 밖 자격은 서버 밖 대상이 주는 것이라 만들지 않는다.

## 기기별 문진표 배치(device_placements)
계약에 경로가 이미 있다: `DeploymentLayout.device_placements`(배치 설정) → 파일 `DevicePlacementTable`(소유 survey-service, 사용자 결정 U86) → `SurveyServiceEnv.SURVEY_DEVICE_PLACEMENTS_FILE`. deploy 가 배치 설정에서 표를 `deploy/generated/survey-service/device-placements.json` 으로 쓰고 compose 가 survey-service 의 `/etc/openit/device-placements.json` 에 읽기 전용으로 마운트한다(여러 서버면 다른 파일과 같이 서버의 스테이징 폴더로 올라간다). survey-service 는 시작할 때 읽고 세션을 시작할 때 mTLS 로 확인된 기기 ID(XFCC 의 CN)로 기본 문진표를 고른다(시작 코드의 문진표 > 요청의 문진표 > 기기 배치 > 활성이 하나일 때 그것). 그래서 배치된 기기의 키오스크는 먼저 `questionnaire_id` 없이 보내도 422 `QUESTIONNAIRE_REQUIRED` 를 받지 않고(계약 startSession), 배치가 없고 활성 문진표가 둘 이상일 때만 환자에게 묻는다(kiosk-frontend 는 그때만 선택 화면을 보인다). 계약을 바꾸지 않았다. 파일은 시작할 때만 읽으므로 배치가 바뀌면 `up` 이 survey-service 를 다시 만든다. 한 기기에 기본 문진표가 둘이면 어느 것이 기본인지 정할 수 없어 배치 설정을 거절한다(survey-service 는 기기 ID 로 하나를 고른다. 이 규칙은 계약 스키마가 말하지 않는 구조 규칙이다). 문진표가 실제로 활성인지는 deploy 가 모른다(survey-service 가 활성 문항 세트가 없으면 400 으로 답한다).

## 왜
- pg_dump/pg_restore 는 PostgreSQL 문서가 논리 백업으로 권하는 표준 도구이고 custom 형식은 압축되고 선택 복구가 된다. 정본(D85(6), D126)이 PostgreSQL 이다.
- restic·REST 서버·`--private-repos`·`forget --prune` 은 정본 결정이다(D111·D130). `restic copy` 는 restic 문서가 저장소 사이 복사로 안내하는 방법이고 서버 밖 사본이 따로 암호화된다(D88 U6 '암호화').
- 한 스냅샷은 계약이 정한 모양이다(JobRunResult 의 `snapshot_id` 하나).
- 앞단 Caddy 와 ACME 는 계약 C14(영역 사이 모든 HTTP 는 TLS)와 레지스트리의 선례(ADR 0013·0014)를 따른 것이다. rest-server 가 직접 TLS 를 끝내려면 인증서를 받고 갱신하는 일을 따로 해야 한다.
- 일회용 컨테이너 안의 restic 은 서버에 restic 을 설치하지 않게 하고(이미지 digest 고정) 관리 노드의 비밀 파일을 원격 엔진에 올릴 필요가 없다.

## 검토한 대안과 버리는 이유
- **데이터베이스마다 표준 입력 스냅샷(`restic backup --stdin`):** 디스크에 평문 덤프가 남지 않으나 스냅샷이 여러 개가 되어 BACKUP 하나의 `snapshot_id` 하나와 맞지 않고, 덤프가 도중에 실패해도 스냅샷이 생겨 지워야 한다. 임시 폴더는 0700 이고 올린 직후 지운다(감수: 관리 노드의 디스크 여유가 덤프 크기만큼 필요하다).
- **`pg_dumpall` 한 파일이나 폴더에 gzip SQL(이전 방식):** `--clean` 덤프가 쓰는 중인 DB 를 지우려다 실패하고(ADR 0008) 서버 밖 암호화·중복 제거·보관 정리가 따로 필요하다. 이전 형식의 백업 폴더(`deploy/backups/postgres-*`)는 새 `restore` 가 읽지 않는다.
- **WAL 보관·시점 복구(pg_basebackup):** 복구 시점 목표는 사용자가 정하지 않았다(OPEN_GAPS O16, 일일 백업이 정본 U31). 일일 논리 백업이면 복구 시점은 최대 하루 전이다.
- **age 등 파일 암호화:** D112 가 restic 의 대칭 암호를 사용자 확정으로 정했다(age 는 중복 제거·증분·검증을 포기).
- **model-runtime 의 상태를 별도 볼륨으로 나누고 볼륨 전체를 받는다:** 받은 패키지(어댑터)가 상태 폴더(`cache/model-runtime/packages`) 안에 있고 추론 엔진이 모델 서버의 쓰기 경로 하나를 같은 경로로 읽기 전용 마운트해 어댑터를 읽는다(model-runtime ADR 0006). 상태 폴더에 볼륨을 따로 마운트하면 엔진이 어댑터를 못 본다. 이미지·선언(`inputs.json`)·기존 설치의 볼륨도 바뀐다.
- **볼륨에 라벨을 단다(`io.openit.backup` 을 compose 최상위 `volumes` 항목에):** 이미 있는 볼륨에 라벨을 더하고 `docker compose up -d` 를 다시 하자 Compose(v2.40.3)가 120초가 넘도록 끝나지 않았다(이 환경에서 한 번 확인했다. 볼륨 설정이 달라 다시 만들지를 기다리는 것으로 보이나 기다리는 내용은 확인하지 못했다). 볼륨을 다시 만들면 데이터를 잃으므로 위험을 피했다. 서비스 라벨은 컨테이너만 다시 만든다.
- **볼륨 전체를 받는다:** 캐시(기반 모델 가중치, 받은 패키지)는 크고 다시 받을 수 있다. 경로를 고르면 상태만 받는다.
- **레지스트리 볼륨(`registry-data`)을 통째로 받는다(tar):** 일관성을 보장할 수 없다. Distribution 의 파일 저장소는 올리는 중인 blob 을 `_uploads` 에 쓰고 완성되면 내용 주소 경로로 옮기며 매니페스트는 태그·리비전 연결 파일로 가리킨다. 도는 중에 복사하면 연결은 있는데 blob 은 아직 없는 모양을 받을 수 있다(저장 구조에서 추론한 것이고 깨지는 것을 재현하지는 않았다. `files` 가 허용하는 '덧붙이기만 하는 파일'이 아니다. 멈추고 받으면 그 시간 동안 레지스트리가 선다). 영역 이미지까지 딸려 와 크기가 커지고(받지 않기로 한 것을 거르려면 저장소 내부 구조 경로를 알아야 한다) 복구가 Distribution 의 디스크 배치에 묶인다(버전·저장 드라이버가 바뀌면 깨진다). external 레지스트리에는 쓸 수 없다. 이미 있는 구현(일회용 컨테이너로 볼륨 읽기)을 재사용하는 이점은 있으나 위 이유로 버렸다.
- **`oras copy -r --to-oci-layout` 로 내보내고 `--from-oci-layout` 로 올린다:** 같은 방식(OCI Image Layout)이고 표준 CLI(Apache-2.0)다. 차이는 referrers(서명 등 `subject` 로 붙는 항목)까지 따라 복사한다는 것이다. 지금 모델 패키지 매니페스트에는 `subject` 가 없고 서명은 쓰지 않는다(model-runtime ADR 0003, 계약 ModelPackageOciManifest). 새 의존(이미지 하나, digest 고정, 허용형 라이선스 확인 필요)을 더할 이유가 없어 이미 쓰는 crane 을 택했다. 둘 다 `ls`·`pull`/`push` 가 레지스트리 API 로 도는 표준 방식이고 digest 를 바꾸지 않는다(시험에서 확인). 서명(referrers)을 쓰게 되면 oras 로 바꾼다(아래 '되돌리는 조건').
- **레지스트리를 둘째 레지스트리에 복제한다(`crane copy` 등):** 서버 밖 대상이 REST 저장소(restic)이고 계약 `DeployBackupConfig` 가 레지스트리를 말하지 않는다. 한 스냅샷(`BackupSnapshotId` 하나)에도 맞지 않는다.
- **append-only 저장소:** D112 의 선택이었으나 D130 이 이어서 append-only 를 쓰지 않는다고 정했다(`forget --prune` 이 지워야 한다). 서버가 침해되면 백업을 지울 수 있는 위험은 서버 밖 사본이 막는다.
- **restic 을 플랫폼 서버의 엔진에서 돌린다:** 암호·자격 파일을 서버에 올려야 하고(스테이징) 표준 입력과 비밀을 한 컨테이너에서 같이 다루기 어렵다.
- **영역마다 따로 backup·restore 잡(D130 의 그림):** 계약이 배치 설정의 backup 칸을 deploy 가 도는 잡의 입력으로 정했다(DeployBackupConfig 설명). 이 변경은 그 계약대로다.

## 결과
- **얻는 것:** 문진 결과(survey-db)와 Keycloak 이 같은 스냅샷에 들어가고, 영역 DB 를 더해도 라벨만 달면 된다. DB 가 플랫폼과 다른 서버에 있어도 된다. 서버 밖 사본이 있고 정기 복구 시험이 있다. `tools/backup-sandbox` 가 서버 한 대와 두 대에서 데이터 → backup → 삭제 → restore → 지문 비교를 한다.
- **감수하는 것:**
  - 백업하는 동안 관리 노드에 덤프 크기만큼의 임시 디스크가 필요하다. DB 크기와 백업 시간은 측정하지 않았다.
  - 백업 저장소는 플랫폼 서버에 하나고 `down --volumes` 가 그 볼륨을 지운다(서버 밖 사본은 남는다). 저장소 암호를 잃으면 읽을 수 없다. 관리 노드의 백업 비밀 파일을 별도로 보관한다.
  - 백업 대상은 PostgreSQL DB, model-runtime 의 활성화 기록, 레지스트리의 모델 패키지다. 다음은 대상이 아니다: step-ca 의 저장소(`step-ca-data`: 발급된 인증서는 ACME 로 다시 받는다), 레지스트리의 영역 이미지(`registry-data` 의 나머지: 소스에서 다시 빌드해 올린다, 위), 외부 레지스트리의 모든 것(운영처 몫), Prometheus·Alertmanager 데이터(지표와 침묵 규칙), model-runtime 의 받은 패키지와 기반 모델 가중치(`model-runtime-data` 의 나머지: 레지스트리에서 다시 받는다), 관리 노드의 `deploy/secrets/`·`deploy/pki/`·`deploy/.env`·`deploy/layout.json`(INSTALL.md 10절에서 따로 보관).
  - 모델 패키지는 매 백업이 전부 다시 내려받아 관리 노드의 임시 폴더에 두었다가 restic 이 올린다(restic 은 같은 내용을 중복 제거하므로 저장소는 패키지가 늘어도 새 것만큼 는다). 그래서 관리 노드의 임시 디스크는 패키지 크기의 합만큼 더 필요하고 백업 시간도 그만큼 는다. 패키지 수와 크기, 걸리는 시간은 측정하지 않았다(어댑터 둘과 프롬프트이고 수십 개를 가정한다). 패키지가 많아지면 이미 받은 패키지를 관리 노드에 두고 새 것만 받는 방식으로 바꾼다(아래 '되돌리는 조건').
  - 태그가 없는 매니페스트, 다른 저장소의 항목, referrers 는 받지 않는다(위).
  - 운영 데이터의 보존 기간(D88 U4 30일)보다 백업(14일)이 짧으므로 U30 은 지켜지지만, 이 값이 병원 규정과 맞는지는 확인하지 않았다.
  - 실행 일정은 deploy 의 스케줄러가 정한다(D39): [ADR 0028](0028-잡-스케줄러는-systemd-타이머.md). 이 ADR 의 명령은 잡 한 번이고 멱등이다(같은 입력으로 다시 실행해도 안전하다. offsite-sync 는 시험에서 확인).
  - 상태 파일 복구의 한계: model-runtime 의 기록은 백업 이후 덧붙은 줄을 잃는다(일일 백업의 복구 시점 한계, O16 과 같다). 복구 뒤 model-runtime 은 기록의 마지막 `LOADED` 패키지를 레지스트리에서 받아 다시 적재한다. 샌드박스 시험(`tools/backup-sandbox`)은 모델 패키지 둘을 제품의 게시 코드로 올리고 기록에 그 digest 로 활성화·롤백을 남긴 뒤, backup → 레지스트리 볼륨·model-runtime 의 기록과 받은 패키지를 지움 → restore 해 다음을 확인한다: 레지스트리의 패키지 목록이 같은 digest(매니페스트 SHA-256·config·layer digest 포함)로 돌아왔고, 복구한 기록의 같음(사건 목록·파일 SHA-256·소유자·모드)이 맞고, model-runtime 이 시작하며 기록의 마지막 활성 패키지를 레지스트리에서 받아 파일의 SHA-256 이 매니페스트와 같고 어댑터를 푼 뒤 **추론 엔진에 올리는 단계에서만 멈춘다**(model-runtime 은 어댑터를 하나씩 받아 풀고 곧바로 엔진에 올린다. 이 샌드박스에는 엔진이 없어 첫 어댑터 LORA_A 에서 멈추므로 받은 것은 config 와 LORA_A 의 가중치·프롬프트 세 파일이고, 기록에 `LOAD_FAILED` 와 사유 '추론 엔진에 닿지 못했다'가 남는다. 엔진이 있으면 다섯 파일을 모두 받아 `LOADED`). 엔진에 실제로 올라 `READY` 가 되는 것은 확인하지 못했다(GPU 엔진 필요).
  - 실제 원격(SSH) 엔진, 공용 인터넷의 서버 밖 서비스(S3 호환 등), 대용량 DB 는 시험하지 못했다. 서버 밖 대상은 같은 이미지의 REST 서버를 TLS 로 띄워 시험했다.
  - 서버 밖 호출(`restic copy`)은 영역 게이트웨이의 CONNECT 터널을 지나지 않고 관리 노드의 일회용 컨테이너가 직접 나간다(CONVENTIONS 13절의 '유일한 예외' 목록을 이 작업 트리에서 읽지 못해 거기에 드는지 확인하지 못했다). 헤드가 확인할 일이다.
- 값: 보관 14일(위), 일회용 PostgreSQL 준비 상한 60초(측정하지 않았다, 되면 곧바로 넘어간다).

## 되돌리는 조건
모델 패키지에 서명 등 referrers 를 쓰게 되면 내보내기·복구를 `oras copy -r` 로 바꾼다. 패키지가 많아져 매 백업의 내려받기가 부담이 되면(측정 뒤) 받은 패키지를 관리 노드에 두고 새 digest 만 받는다(패키지는 digest 로 불변이라 다시 받을 필요가 없다). 외부 레지스트리의 모델 패키지도 받아야 하면 deploy 의 레지스트리 클라이언트가 외부 주소와 자격을 알게 하는 결정을 먼저 한다.
계약이 영역마다 저장소 주소·자격을 가지게 되면 영역별 저장소로 나눈다. 복구 시점 목표가 정해져 하루보다 짧아야 하면 WAL 보관으로 바꾼다. 서버 밖 대상이 REST 가 아닌 것(S3 등)이어야 하면 계약 OffsiteBackupUrl 의 모양을 바꾸는 요청을 낸다. SQLite 처럼 돌아가는 중에 복사하면 깨지는 저장소를 영역이 쓰면 그 엔진의 일관된 백업 방법을 쓰는 새 라벨 값을 더한다(`files` 는 그런 파일에 쓰지 않는다). 영역이 어느 경로가 상태인지를 이미지 선언으로 알리게 계약이 바뀌면(`WritablePath` 에 백업 칸, 변경 요청 `deploy-001`) compose 라벨 대신 선언을 읽는다.
