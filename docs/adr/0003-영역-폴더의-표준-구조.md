# 0003. 영역 폴더의 표준 구조

## 상태
승인(2026-11-10, 헤드 판단). 원칙: 표준 구조, 빈틈 없음, 짧은 설명으로 전체를 이해할 수 있는 구조.

## 맥락
v1~v6은 영역마다 구조가 달라서(컴포넌트 위치, 시험 위치, 타입 위치, 스크립트 이름) 새로 보는 사람이 영역마다 다시 익혀야 했다.

## 결정
모든 서비스 영역은 같은 모양이다. Python 패키징은 PyPA 표준(`pyproject.toml`, src 레이아웃)을 따른다.

```
services/<영역>/
├── pyproject.toml          의존과 도구 설정(ruff, pyright, pytest, import-linter). 잠금 파일은 uv.lock
├── Dockerfile              이미지 하나(ADR 0004)
├── README.md               1. 하는 일 2. 받는 계약·내는 계약 3. 컴포넌트 표 4. 실행·시험 명령 5. 시험 상태 6. ADR 목록
├── docs/adr/               이 영역의 결정
├── src/<패키지>/
│   ├── contract/           contracts/에서 생성한 타입(models.py). 손대지 않는다(생성 명령 `openit-gen-contract` 로만 갱신, ADR 0020)
│   ├── types.py            영역 안 컴포넌트 사이 값. Pydantic 모델, 칸마다 description과 제약
│   ├── components/         컴포넌트. 파일 하나 = 컴포넌트 하나. types.py와 contract/만 import한다
│   ├── link/               영역 밖과 통신하는 컴포넌트(HTTP 서버 라우터, 이웃 클라이언트). 영역 밖 통신은 여기서만
│   ├── store/              이 영역 DB(SQLAlchemy 모델, Alembic 마이그레이션)
│   └── main.py             조립(의존 주입)과 진입점. /healthz, /readyz
└── tests/
    ├── unit/               컴포넌트마다
    ├── contract/           받는·내는 계약 검증, 경계 사례
    └── smoke/              이미지 스모크(ADR 0004)
```

- 화면 영역(`web/<영역>/`)도 같은 원칙을 TypeScript로 따른다(`src/contract/` 생성 타입, `src/components/`, `src/link/`, `tests/`).
- **경계 점검:**
  - Python은 import-linter(BSD-2-Clause)로 막는다. 컴포넌트끼리 import 금지, 다른 영역 import 금지, 영역 밖 통신은 `link/`에서만.
  - TypeScript는 eslint-plugin-boundaries(MIT)로 같은 규칙을 건다.
- **도구:** ruff(MIT), pyright strict(MIT), pytest(MIT). 패키지 관리는 uv(MIT/Apache-2.0)로 하고 잠금 파일을 커밋한다.

## 왜
- 구조가 하나라 한 영역을 익히면 모든 영역을 읽을 수 있다.
- D104 구조 규칙(컴포넌트는 자기 입출력과 할 일만 안다)을 폴더와 점검 도구로 강제한다.
- src 레이아웃과 `pyproject.toml`은 Python 패키징 표준(PyPA)이다.

## 검토한 대안과 버리는 이유
- 영역마다 자유 구조: v1~v6의 문제가 그대로 반복된다.
- requirements.txt만 쓰기: 도구 설정이 흩어진다. `pyproject.toml`이 표준이다.

## 결과
- **얻는 것:** 같은 명령(`uv run pytest`, `uv run lint-imports`)이 모든 영역에서 통한다.
- **감수하는 것:** 작은 영역도 같은 틀을 갖춰야 한다.

## 되돌리는 조건
표준(PyPA 패키징, src 레이아웃)이 바뀌면 이 ADR을 대체한다.
