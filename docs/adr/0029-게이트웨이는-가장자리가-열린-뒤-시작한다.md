# 0029. 여러 서버 배치에서 영역 게이트웨이는 가장자리의 80 번이 열린 뒤 Caddy 를 시작한다

## 상태
승인(2026-11-11, 간헐적 기동 실패 조사). ADR 0026(가장자리)과 platform ADR 0007(영역 게이트웨이)의 기동 순서를 정한다. 값(시간)은 바꾸지 않는다.

## 맥락
`tools/schedule-sandbox --two` 의 첫 실행이 bootstrap 에서 `survey-service-gateway is unhealthy` 로 실패하고 같은 명령을 다시 하면 통과했다. 진단 로그가 다음 실행에 지워져 원인을 남기지 못했다(진단 수단은 이 변경에서 고쳤다: `tools/layout-sandbox` 의 `begin_run`·`collect_diagnostics`).

재현하고 확정한 원인(이 환경 한 곳, 서버 두 대 배치의 서버 b 층을 인증서 볼륨을 비우고 다시 띄우기를 반복, CPU 14개를 태우는 부하 속, 수정 전 2번 중 1번 실패):
- 서버 b 의 층 하나에 `area-edge` 와 영역 게이트웨이들이 함께 있었고 compose 는 이들을 동시에 시작했다(`up -d --wait --no-deps`).
- 게이트웨이(Caddy)는 시작하자마자(약 1.6초) step-ca 에 ACME 주문을 내고, step-ca 는 곧바로 서비스 이름의 80 번(서버 b 의 가장자리 Envoy)으로 http-01 검증을 보낸다. 실패한 실행에서 step-ca 의 검증 요청은 02:58:25.98 였고 가장자리의 Envoy 가 듣기 시작한 것은 02:58:26.006(`cm init: all clusters initialized`)였다. 가장자리의 접근 기록에 그 영역의 검증 요청이 없다. 요청이 닫힌 포트에 닿았다.
- step-ca 는 한 번 실패한 주문을 다시 검증하지 않는다. 가장자리를 15초 늦게 올려 측정하니(서버 b, 위와 같은 구성) Caddy 의 ACME 클라이언트(acmez)가 302초 뒤 `authorization took too long` 으로 포기하고, certmagic 이 60초 뒤(`retrying_in: 60`) 새 주문을 내 성공했다. 시작부터 인증서까지 약 366초다.
- 영역 게이트웨이의 건강 확인(`test -s` 인증서·키)의 상한은 start_period 10초 + 5초 x 60회 = 약 310초라서 복구 전에 unhealthy 가 되고 `up --wait` 가 실패한다. 실패한 실행은 372초 걸렸다.
- 재실행이 통과한 것은 매번 새 주문을 내므로 경합이 다시 이기기 때문이다.

실제 설치에서도 같다. 서버를 재시작하거나 부하가 있으면 같은 경합이 난다. 서버 한 대 배치에는 가장자리가 없다(step-ca 가 게이트웨이의 별칭으로 바로 간다).

## 결정
1. 여러 서버 배치의 영역 게이트웨이(플랫폼 서버 포함, `deploy/layout.py` 의 서버 덮개)는 `command` 로 가장자리의 80 번에 연결되는 것(`nc -w 1 area-edge 80`, busybox)을 본 뒤에 `exec caddy run --config /etc/caddy/Caddyfile --adapter caddyfile`(이미지의 기본 명령과 같다)을 시작한다. 가장자리가 끝내 열리지 않으면 게이트웨이는 건강해지지 않고 compose 가 unhealthy 로 끝낸다(상한은 건강 확인이 이미 갖고 있다).
2. `area-edge` 는 같은 서버의 게이트웨이들에 `depends_on: service_started` 를 건다. 가장자리가 시작할 때 게이트웨이가 이미 네트워크에 있어 STRICT_DNS 가 첫 해석에서 게이트웨이 이름을 푼다. 순서가 반대면(가장자리가 먼저) 첫 해석이 NXDOMAIN 이고 Envoy 의 해석 갱신(기본 5초)을 기다리는 사이에 같은 실패가 난다.
3. `tiers()`(서버별 층 나누기)는 `service_started` 의존을 상대와 같은 층에 둔다(그 밖의 의존은 상대의 다음 층이다). `up --wait` 는 층 전체가 healthy 가 되기를 기다리는데 게이트웨이의 healthy 는 가장자리에 달려 있어, 가장자리를 다른 층에 두면 앞 층이면 가장자리가 먼저 시작해 이름을 못 풀고(2번) 뒤 층이면 서로를 기다린다. 플랫폼 서버에서는 게이트웨이가 step-ca 의 `service_healthy` 로 한 층 뒤에 있으므로 가장자리도 그 층으로 옮겨 간다. compose 는 한 번의 `up --no-deps` 안에서 선택한 서비스끼리의 `service_started` 순서를 지킨다(작은 compose 파일로 3번 확인했다).

건강 확인의 interval·retries·start_period 는 바꾸지 않는다.

## 왜
- Docker Compose `depends_on` 의 조건(`service_started`·`service_healthy`)과 서비스 안의 준비 확인은 시간에 기대지 않고 사건에 기댄 기동 순서의 표준 방법이다. 이 변경은 사건 둘(게이트웨이 시작 -> 가장자리 시작 -> 가장자리의 80 번 열림 -> Caddy 시작)을 순서로 고정한다.
- Caddy 는 시작과 함께 ACME 를 시작하고 늦출 설정이 없다. 공식 이미지의 `command` 만 바꾼다(영역 이미지의 command 금지는 이 이미지에 적용되지 않는다. 이 이미지는 digest 고정 공식 caddy 이고 `compose.yaml` 의 다른 기반 서비스도 `command` 를 쓴다).
- 폴링 간격 0.2초는 연결이 되는지 보는 주기이고 통과시키려고 기다리는 시간이 아니다. 측정하지 않았고 영향도 없다(조건이 되는 즉시 시작한다).

## 검토한 대안과 버리는 이유
- **건강 확인의 retries 를 늘린다(약 410초):** 실패를 366초 걸려 고치는 방법이다. 원인(검증이 닫힌 포트에 닿는 것)은 그대로이고 기동이 6분 지연된다. 실패한 주문을 다시 내는 추가 상한은 `retries` 만으로 정할 수 없다(두 번째 실패의 간격은 2분, 이후 길어진다).
- **게이트웨이가 가장자리의 `service_healthy` 에 의존:** 가장자리가 먼저 시작하면 게이트웨이 이름이 아직 없어 첫 해석이 NXDOMAIN 이다. 검증이 게이트웨이를 못 찾아 같은 실패가 난다(2번 설명). Envoy 의 해석 주기를 0.25초로 줄이는 것은 시간 경합을 줄일 뿐 닫지 않는다.
- **Envoy 의 재시도(retry_policy):** 이름을 못 푼 경우(no healthy upstream)는 라우터가 업스트림을 고르기 전의 실패라 재시도 대상이 아니라고 이해했다(시험하지 않았다). 닫힌 포트(가장자리 자체)에는 소용이 없다.
- **Envoy dynamic forward proxy:** 요청 때 이름을 풀지만 Host 를 바꾸지 않고는 게이트웨이 이름으로 풀 수 없고(Caddy 가 Host 로 검증 토큰을 찾는다고 이해했다, 시험하지 않았다), 서버 b 가장자리의 `extra_hosts` 가 영역 이름을 자기 주소로 푼다. 구조를 더 바꿔야 한다.
- **게이트웨이 앞에 별도 응답기를 두고 가장자리를 통해 확인:** 확인을 위한 구성 요소가 더 늘어난다.

## 결과
- 얻는 것: 검증이 닫힌 포트에 닿는 경합이 없어진다. 실패하면 5분이 아니라 사건(가장자리가 안 열림)으로 알린다.
- 감수하는 것: 게이트웨이의 기동이 가장자리를 기다린다(가장자리가 먼저 healthy 일 필요는 없다). 서버 덮개가 게이트웨이의 `command` 를 가진다. 이미지의 기본 명령이 바뀌면(caddy 이미지 갱신) 이 명령도 같이 본다(시험이 명령을 확인한다).
- 이 환경 한 곳에서만 확인했다. 수정 뒤 반복 결과는 변경 기록(커밋)에 있다.

## 되돌리는 조건
가장자리를 쓰지 않는 구성(서버마다 영역 게이트웨이가 하나이고 주소가 다른 경우)이 되거나, Caddy 가 ACME 시작을 늦추는 설정을 내면 `command` 를 걷는다.
