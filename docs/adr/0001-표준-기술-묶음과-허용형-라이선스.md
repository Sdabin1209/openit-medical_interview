# 0001. 표준 기술 묶음과 허용형 라이선스

## 상태
승인(2026-11-10, 사용자 결정). 원칙: 표준 기술을 쓰고, 라이선스는 허용형(MIT·Apache·BSD)으로 하며 GPL 계열은 쓰지 않는다.

## 맥락
v1~v6은 자체 형식(계약 YAML·생성기)과 직접 구현(표준 라이브러리 HTTP 서버)을 섞어 써서, 같은 값이 곳마다 다르게 정의되고 뜻이 비었다. v7은 처음부터 다시 만들며, 모든 선택을 업계 표준 오픈소스로 하고 라이선스를 허용형으로 묶는다.

## 결정

|---|---|---|
| 영역 사이 계약 형식 | OpenAPI 3.1, JSON Schema 2020-12 | 사양(OAI, JSON Schema 조직) |

## 왜
- 표준 도구는 검증·문서·생태계가 이미 있어 직접 구현한 것보다 빈틈이 적다. 예를 들어 FastAPI는 Pydantic 모델로 요청·응답을 검증한다.
- 계약은 OpenAPI가 사실상 표준이고, Spectral이 그 표준의 린터다. 값마다 뜻·범위·주인·근거를 강제하는 규칙을 표준 장치(규칙 파일)로 건다.
- 라이선스는 모두 허용형이다. 결과물의 배포·사용에 조건이 붙지 않는다.

## 검토한 대안과 버리는 이유
- **psycopg 3:** PostgreSQL 드라이버의 표준 중 하나지만 LGPL-3.0이라 GPL 계열을 피한다는 지시에 맞지 않는다. SQLAlchemy가 공식 지원하는 asyncpg(Apache-2.0)를 쓴다.
- **표준 라이브러리 HTTP 서버, WSGI 직접 구성:** 검증·문서·비동기를 직접 써야 해서 빈틈이 생긴다.
- **자체 계약 YAML과 생성기:** 표준이 아니다.

## 결과
- **얻는 것:** 모든 영역이 같은 도구를 쓴다. 계약에서 타입을 생성해 한 번만 정의한다.
- **감수하는 것:** 의존 수가 늘어난다. 잠금 파일로 버전을 고정하고, 라이선스를 바꾸는 의존이 생기면 이 ADR을 다시 본다.

## 되돌리는 조건
선택한 도구의 라이선스가 허용형이 아니게 바뀌거나 유지가 끊기면, 같은 표준을 따르는 다른 도구로 대체하고 이 ADR을 대체하는 새 ADR을 쓴다.
