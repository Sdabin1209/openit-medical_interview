# 0030. E2E product 판정은 프레임워크 기준: 모델 결과는 기록하고 시스템 규칙만 판정한다

## 상태
승인(2026-11-23, 사용자 결정). ADR 0025 의 product 판정(문진 완료·대본 기대 값 전부 저장·실패 신호 없음)을 대체한다. 실행 규약·샌드박스·여덟 단계는 ADR 0025 그대로다.

## 맥락
2026-11-23 프로젝트 기준 어댑터(LoRA-A `a_8b_1029`, LoRA-B `b_8b_1103`)로 처음 product 를 돌렸다. ①~④ 통과, ⑤의 턴 30번이 모두 200·계약 일치·실패 신호 0 이었는데 문진이 끝나지 않아 ⑤가 실패하고 ⑥~⑧(결과, FHIR, 직원 알림)은 시험되지 않았다. 턴 기록으로 본 원인은 모델이다: 심근경색 문항의 부정 답을 앞 문항(뇌졸중)과의 충돌로 해석해 확인을 되풀이했다(데모 재현 보고서의 '문제 2'와 같은 현상). 대본은 문항마다 발화가 하나라 확인이 오면 같은 발화를 다시 보내 상한까지 맴돌았다. 시스템은 계약대로 처리했다(확인 때 지금 문항을 되돌리고 저장 안 함 값은 저장하지 않음).

## 결정
- product 의 합격은 시스템 규칙으로만 정한다: 모든 호출의 계약 일치, 스트림 규칙, 실패 신호 때 상태·지금 문항 불변, 연속 실패 한도에서 건너뜀, 결과·확인 표시·병원 시스템 당겨 가기·FHIR·직원 호출 알림.
- 모델이 낸 결과(실패 신호, 확인·되묻기 반복, 문진 미완료, 대본 기대 값과 다른 저장)는 단계 기록에 '모델 관찰(판정 밖)'으로 적고 실패로 보지 않는다.
- 같은 문항에 보내는 턴이 세 번을 넘으면 세션을 끝내고 ⑥~⑧로 간다(`PRODUCT_REPEAT_LIMIT`, 근거는 코드 주석).

## 왜
- 이 E2E 는 시스템(프레임워크)이 모델의 어떤 출력에도 꺼지지 않고 계약대로 처리하는지를 보는 시험이다. 모델 품질은 학습 쪽의 평가(평가 보고서, 학습 서버의 시험)가 잰다. 두 가지를 한 판정에 섞으면 모델 결함이 시스템 시험을 막는다(이번처럼 ⑥~⑧이 한 번도 돌지 않는다).
- 모델 결과를 버리지 않고 기록하므로 모델이 바뀔 때의 차이는 기록에서 볼 수 있다.

## 검토한 대안과 버리는 이유
- **대본을 모델에 맞춰 고친다(발화를 더 명시적으로):** 특정 모델의 결함에 시험을 맞추는 것이고 모델이 바뀌면 다시 깨진다.
- **확인·되묻기에 답하는 대본을 더한다:** 반복은 줄지만 합격이 여전히 모델의 답에 달린다. 필요하면 이 결정 위에 더할 수 있다.

## 결과
- **얻는 것:** 모델이 무엇을 내든 여덟 단계가 끝까지 돈다. 반복을 일찍 끊어 실행 시간(GPU 임대 시간)이 준다.
- **감수하는 것:** product 통과가 '대본대로 문진이 완료된다'를 뜻하지 않는다. 그 확인은 모델 관찰 줄을 읽어야 한다.

## 되돌리는 조건
모델 품질의 합격선이 정해지고 그것을 시스템 E2E 에서 함께 보기로 하면, 모델 관찰 중 정한 항목을 판정으로 올린다.
