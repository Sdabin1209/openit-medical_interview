# 0026. 여러 서버 배치: 서버마다 compose 프로젝트, 가장자리 Envoy, 엔진 API 로 파일 올리기

## 상태
승인(2026-11-11, 배포 담당). 설계서 6절과 계약 DeploymentLayout(UD-15: 서버 수는 서비스 수 이하에서 자유, 서비스와 서버의 대응은 배치 설정)을 `./deploy` 가 읽게 한다. ADR 0023 의 '되돌리는 조건'(DeploymentLayout 을 deploy 가 읽게 되면 서버별 구성으로 바꾼다)을 이행하고, ADR 0013 의 '서버 여러 대에서 레지스트리를 공유하려면 따로 정한다'를 정한다. ADR 0021 의 '영역 안 구간이 서버 밖을 지나면 TLS'는 이 ADR 에서 해당하지 않는다(영역 안 구간은 서비스와 그 게이트웨이이고 같은 서버에 둔다).

## 맥락
deploy 는 배치 설정을 읽지 않고 compose 전체를 엔진 하나에 띄웠다. 서버를 나누려면 다섯 가지가 풀려야 했다.
1. 서버마다 어떤 서비스를 띄울지(서비스 선택)와 서버마다 어느 엔진을 쓸지.
2. 서비스가 서버를 넘어 부르는 길. 영역은 `https://<영역 이름>:8443`(계약 D129)으로 서로를 부르고 나가는 호출은 입구(Envoy)의 CONNECT 터널을 지난다(D128). compose 네트워크는 서버 안에서만 이어진다.
3. 한 서버에 영역 게이트웨이가 여럿일 때: 서버의 주소는 하나이고 TLS 포트(8443)와 ACME http-01 검증의 80 번(RFC 8555 8.3)은 영역마다 게시할 수 없다.
4. 원격 엔진은 관리 노드의 파일 경로를 모른다. compose 의 bind mount 와 file 비밀은 엔진 호스트의 경로다.
5. 레지스트리를 다른 서버가 받는 길.

## 결정
- **배치 설정 파일:** `OPENIT_LAYOUT_FILE`(기본 `deploy/layout.json`)을 계약 DeploymentLayout 으로 검증한다(계약 JSON Schema 에서 생성한 타입, ADR 0020). 기본 이름의 파일이 없으면 서버 한 대(관리 노드의 엔진에 전부, 지금 동작과 같다). 다른 이름을 줬는데 없으면 멈춘다. 계약이 말하지 않는 구조 규칙을 더 본다: 서비스 다섯이 정확히 한 서버에, 서버 이름·주소는 겹치지 않음, 서버마다 서비스 하나 이상. 예시는 `deploy/layout.example.json`.
- **서버마다 compose 프로젝트 하나, 서비스 선택은 라벨:** 엔진이 서버마다 다르므로 프로젝트도 서버마다다(여러 서버일 때 이름은 `<OPENIT_PROJECT_NAME>-<서버 이름>`, 한 서버면 그대로). compose.yaml 의 모든 서비스에 라벨 `io.openit.service`(계약 ServiceName 또는 배치가 만드는 `layout`)가 있고 deploy 는 이것으로 서버의 서비스를 고른다. `docker compose up -d --wait --no-deps <서비스들>` 을 depends_on 순서의 층마다 부른다.
- **서버의 docker context 이름은 서버 이름이다**(`ServerName` 은 소문자·숫자·`-` 라 context 이름 규칙과 맞다). ADR 0009 의 규칙 1(`DOCKER_CONTEXT` 가 `DOCKER_HOST` 보다 앞선다)로 서버마다 엔진을 고른다. 빌드와 이미지 올리기는 관리 노드의 기본 엔진(빌드 엔진)이다. context 는 사용자 `~/.docker` 가 아니라 프로젝트의 격리 설정 폴더(`.docker-config`)에 만든다.
- **서버를 넘는 길은 서버마다 가장자리(area-edge, Envoy)가 맡는다.** 같은 서버의 영역 게이트웨이들을 한 주소로 내보낸다: TLS 8443 은 SNI 로 가르는 TCP 통과(TLS 를 끝내지 않는다. mTLS 는 영역 게이트웨이가 끝낸다, ADR 0021), 80 번은 ACME 검증 경로만 Host 로 가려 넘김, 9100 은 감시용 상태·지표를 Host 로 가려 넘김. 플랫폼 서버가 아닌 서버에서는 영역 서비스의 나가는 터널(`OPENIT_EGRESS_PROXY`, 별칭 `gateway`)도 가장자리가 맡는다(입구와 같은 생성 코드, `gateway.egress_resources`). 설정은 `platform/src/openit_platform/edge.py` 가 만든다.
- **이름→주소는 compose `extra_hosts`:** 다른 서버에 있는 상대는 배치 설정의 서버 주소(ServerEntry)로 푼다. 서버 주소가 호스트 이름이면 관리 노드에서 IPv4 로 풀어 넣는다(`extra_hosts` 는 IP 만 받는다). 플랫폼 서버에서는 입구·사설 CA·감시가 다른 서버의 영역 이름을 찾고, 다른 서버에서는 영역 게이트웨이가 `step-ca` 를, 가장자리가 레지스트리·발급자·다른 영역 이름을 플랫폼 서버 주소로 찾는다. 계약 `HostsTable`(compose 밖 호출자용, 줄 수 최대 6)은 쓰지 않는다: 필요한 이름이 영역 이름 외에 사설 CA·레지스트리·입구 이름까지라 6줄에 맞지 않고, deploy 가 compose 에 주는 값이지 영역에 주는 값이 아니다(그래서 계약을 바꾸지 않았다).
- **게시 포트는 호출 관계에서 계산한다.** 서버를 넘는 호출(입구→영역, 영역 서비스의 나가는 터널→상대, 감시→9100, 사설 CA→ACME 검증 80, 영역 게이트웨이→사설 CA 9000, 서버 엔진→레지스트리 443, 관리 노드→레지스트리·입구)을 목록으로 만들고 그 도착 서버가 그 포트를 서버 주소에 게시한다(IP 면 그 주소, 호스트 이름이면 모든 인터페이스). `./deploy doctor` 가 이 목록을 '서버 사이에 열어야 하는 포트'로 보이고, 한 서버 안에서 게시 포트가 겹치면(입구의 `OPENIT_LISTEN_PORT` 와 영역의 `OPENIT_SERVICE_PORT` 가 같은 서버에서 같을 때 등) 막는다. 게시하는 컨테이너는 `internal` 네트워크가 아닌 `edge` 에 붙인다(internal 네트워크의 게시 포트는 열리지 않는다. 시험에서 확인). 영역 서비스 컨테이너는 안쪽 네트워크에만 둔다. 영역 게이트웨이는 다른 서버의 사설 CA 에서 ACME 로 인증서를 받아야 해서 플랫폼 서버가 아닌 서버에서는 `edge` 에도 붙는다.
- **원격 엔진에는 엔진 API 로 파일을 올린다.** 여러 서버일 때 compose 의 bind 원본과 file 비밀을 모아(compose 모델에서) 서버의 `OPENIT_STAGE_ROOT/<프로젝트>/files/<해시>/<이름>` 에 올리고(일회용 컨테이너가 그 폴더를 bind mount 하고 표준 입력의 tar 를 푼다) 서비스의 마운트를 그 경로로 바꾸는 덮개를 만든다. 바뀐 파일만 올리고 그 파일을 쓰는 돌고 있는 서비스를 다시 만든다. `down --volumes --yes` 가 스테이징 폴더도 지운다. ssh·rsync 가 필요 없다.
- **레지스트리는 플랫폼 서버에 두고 다른 서버가 받는다.** 레지스트리 443 을 플랫폼 서버 주소에 게시한다. 관리 노드의 빌드 엔진이 이미지를 올릴 때(crane 일회용 컨테이너)는 레지스트리 이름을 플랫폼 서버 주소로 풀어(`--add-host`) 같은 신뢰 목록으로 검증한다. 다른 서버의 엔진은 `docker pull registry:443/openit/<대상>@<lock 의 digest>` 로 받는다(`ensure_images`). 그 서버의 호스트가 `registry` 를 플랫폼 서버 주소로 풀고(`/etc/hosts`) 신뢰 목록의 루트를 `/etc/docker/certs.d/registry:443/ca.crt` 에 두어야 한다(ADR 0013 의 외부 레지스트리 경로와 같은 Docker 표준 위치). 사설 CA 의 발급 이름·허용 목록에 서버 주소를 더하지 않았다: 영역 게이트웨이의 인증서 이름은 서비스 이름이고 레지스트리는 이름(`registry`)으로 받으므로 주소 SAN 이 필요 없다(IP SAN 은 ACME IP 식별자가 필요해 사설 CA 지원을 확인하지 못했다).
- **순서:** `bootstrap` 은 신뢰의 뿌리(관리 노드) → 플랫폼 서버의 레지스트리(파일 올리기 포함) → 이미지 올리기와 서버별 받기 → 서버마다 서비스 기동(플랫폼 서버 먼저)이다. `status` 는 모든 서버를 보이고 서버에 닿지 못하거나 배정됐는데 컨테이너가 없으면 rc=1, `down` 은 서비스 서버를 먼저 내리고 플랫폼 서버를 마지막에 내린다.

## 왜
- compose 프로젝트는 엔진 하나에 묶인다(Docker 문서). 서버가 다르면 프로젝트도 달라야 한다. 서비스를 이름으로 고르는 `docker compose up <서비스>` 는 표준 기능이고 `--no-deps` 는 다른 서버에 배정된 의존을 이 서버에 띄우지 않게 한다.
- SNI 로 TLS 를 통과시키는 프록시는 한 주소·포트 뒤에 여러 TLS 서비스를 두는 표준 방식이다(Envoy `tls_inspector` 와 `server_names`). 이미 쓰는 제품(Envoy, 같은 이미지 digest)이라 새 의존이 없다. TLS 를 끝내지 않으므로 영역 사이 mTLS 의 신뢰 구성이 그대로다.
- 엔진 API 만으로 파일을 올리는 것은 SSH 접근을 따로 요구하지 않고(docker context(SSH) 하나로 끝난다) 관리 노드가 서버 엔진이 아닌 곳이어도 같다.
- 게시 포트를 호출 관계에서 계산하면 방화벽 목록과 실제 게시가 같은 계산에서 나온다(어긋나지 않는다).

## 검토한 대안과 버리는 이유
- **compose profiles 로 서버를 가른다:** 프로파일은 하나라도 켜지면 서비스가 켜지는 합집합이라 `registry`(플랫폼이면서 로컬 레지스트리일 때만)를 '둘 다'로 표현하지 못한다. 꺼진 프로파일의 서비스를 가리키는 depends_on 은 오류이고(서버를 넘는 의존이 정확히 그것이다) 기존 프로파일(`local-registry`, `inference-engine`)과 기존 소비자(E2E 샌드박스의 compose 인자)가 모두 바뀐다. 라벨은 compose 의 동작을 바꾸지 않는다.
- **서버마다 compose 파일을 따로 둔다:** ADR 0023 이 이미 버렸다(설치처 차이는 설정 값). 한 파일과 설정 하나가 정본이다.
- **Docker Swarm 오버레이 네트워크:** 서버를 넘는 컨테이너 네트워크는 되지만 ADR 0004 가 오케스트레이터를 나중으로 미뤘고 영역 사이 mTLS·게이트웨이 구조를 바꾼다.
- **영역마다 게시 포트를 따로(8443, 8444 ...):** 계약의 서비스 주소가 `https://<영역 이름>:8443` 하나이고 이름 표는 주소만 담는다(포트가 영역마다 다르면 입구·터널·감시·서비스 환경이 모두 바뀐다).
- **한 서버에는 서버 밖에 보이는 영역을 하나만 허용한다:** UD-15(서비스와 서버의 대응은 자유)에 어긋난다.
- **볼륨의 subpath 로 파일을 마운트한다:** 이미지에 이미 있는 파일(`/etc/caddy/Caddyfile`)에 파일 subpath 를 마운트하면 엔진(moby 28.5.1, 이 환경)이 `not a directory` 로 컨테이너를 만들지 못한다(시험에서 확인).
- **compose `configs`·`secrets` 의 `content`·`environment`:** 컨테이너에 복사하는 방식이라 읽기 전용 루트(ADR 0004)에서는 만들 수 없다(compose 가 거절한다. 시험에서 확인).
- **관리 노드에서 rsync 로 서버에 같은 경로로 보낸다:** 서버에 SSH 파일 접근과 rsync 가 따로 필요하고 샌드박스(같은 엔진에 context 둘)에서는 경로가 같아 이 경로를 시험하지 못한다.

## 결과
- **얻는 것:** 서버 한 대는 지금과 같고(배치 파일이 없을 때 명령과 compose 인자가 같다), 여러 대는 `layout.json` 한 파일로 나뉜다. 서버 사이 포트가 계산되어 doctor 가 알린다. 서버 둘 샌드박스(`tools/layout-sandbox`)가 서버 사이 호출 양방향(입구→영역, 서비스→이웃 영역, 영역→레지스트리·발급자), 감시, ACME 발급, 파일 올리기, status 의 고장 감지를 확인한다.
- **감수하는 것:**
  - 서버마다 컨테이너(가장자리)가 하나 더 돈다. 가장자리의 9100 번은 감시용 상태·지표를 평문으로 서버 주소에 게시한다(방화벽에서 플랫폼 서버에만 열어야 한다. doctor 가 방향을 적는다).
  - 플랫폼 서버가 아닌 서버의 영역 게이트웨이(Caddy)는 바깥으로 나가는 길(`edge`)을 갖는다(영역 서비스 컨테이너는 안쪽뿐이다).
  - 플랫폼은 한 서버에만 있다(분할하지 않는다). 서버에 올린 파일은 그 서버의 `OPENIT_STAGE_ROOT` 에 root 만 읽게 남는다(비밀 포함).
  - 샌드박스의 두 context 는 같은 엔진을 가리켜서 서버의 엔진이 레지스트리에서 이미지를 받는 길(`ensure_images`, 호스트 이름 풀이와 `certs.d` 신뢰)은 단위 시험까지만 했다. 실제 원격(SSH) 엔진과 GPU 서버(nvidia 런타임)는 확인하지 못했다.
  - 같은 서버의 영역 서비스 사이에는 TLS 가 계속 입구·터널을 지난다(서버 한 대 배치와 같다).
- `device_placements` 와 `backup`(배치 설정의 나머지 칸)은 이 ADR 에서는 검증만 했다. 두 칸은 [ADR 0027](0027-백업과-복구.md) 이 쓴다(2026-11-11).

## 되돌리는 조건
오케스트레이터(Swarm, Kubernetes 등)로 옮기면 서버 선택과 서버 사이 길을 그 도구의 표준으로 바꾼다. Docker 가 이미 있는 파일 위의 파일 subpath 마운트를 고치면 스테이징을 이름 있는 볼륨으로 바꿀 수 있다. ACME 가 IP 식별자를 지원하는 사설 CA 를 확인하면 서버 주소를 인증서 이름에 넣을 수 있다.
