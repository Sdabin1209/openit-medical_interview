# 0017. 라이선스 원칙: 의무가 생기는 사용 금지

## 상태
승인(2026-11-10, 사용자 결정). ADR 0001의 "라이선스는 모두 허용형" 문장과 "GPL 계열을 피한다" 문장, ADR 0007의 "도구에도 쓰지 않는다·허용 목록" 규칙, ADR 0004의 "hadolint는 GPL-3.0이라 쓰지 않는다"를 대체한다.

## 맥락
라이선스 원칙의 목적은 우리 결과물에 의무가 생기지 않게 하는 것이다. 이전 규칙은 모든 의존(도구 포함)을 허용형으로 묶어서, 이미지·배포물에 들어가지 않고 실행만 하는 도구(예: hadolint, GPL-3.0)까지 막았다. 도구를 실행하는 것은 그 도구의 라이선스 의무를 결과물에 옮기지 않는다.

## 결정
- **제품 의존**(서비스·화면의 운영 의존처럼 이미지·배포물에 들어가는 것)은 copyleft(GPL·AGPL·LGPL 계열)를 쓰지 않는다. 허용형(MIT·Apache·BSD·ISC 등)만 쓴다. 목록에 없거나 알 수 없는 라이선스도 실패한다(ADR 0007의 허용 목록과 예외 파일 방식 유지, 예외로도 copyleft는 허용하지 않는다).
- **개발·점검에서 실행만 하는 도구**(배포물에 들어가지 않는 것)는 라이선스와 무관하게 허용한다. `openit-check licenses`는 이런 도구의 비허용 라이선스를 실패시키지 않고 `[보고]` 줄로 알린다.
- **어느 쪽인지는 잠금 파일의 표준 구분으로 정한다:**
  - Python(`uv.lock`): `uv sync --frozen --no-dev`로 설치되는 패키지가 제품 의존이고, 나머지(dev 그룹)는 개발 의존이다.
  - npm(`package-lock.json`): 패키지의 `dev` 표시(`devOptional` 포함)가 개발 의존이다.
  - `tools/` 아래 프로젝트(`tools/checks`)와 PEP 723 스크립트(`deploy/deploy`)는 배포물이 아니므로 모두 도구다.
- 자체 시험이 두 경우를 확인한다: 제품 의존의 GPL은 실패, 개발 도구의 GPL은 통과(보고).
- 이 결정으로 hadolint(GPL-3.0)를 개발 도구로 쓸 수 있다(ADR 0016).

## 왜
- 사용자 결정(2026-11-10)이다. 이미지·배포물에 복사·링크되는 코드에만 라이선스 의무(소스 공개, 동일 조건 배포)가 생긴다. 실행만 하는 도구는 결과물에 포함되지 않는다.
- 구분은 잠금 파일이 이미 가진 표준 정보(uv의 dev 그룹, npm의 dev 표시)를 쓰므로 사람이 따로 목록을 관리하지 않는다.

## 검토한 대안과 버리는 이유
- **모든 의존을 계속 허용형으로 제한:** 목적(결과물에 의무가 생기지 않게)을 넘어 도구 선택을 좁힌다.
- **도구도 copyleft는 제한하되 보고만:** 실행만 하는 도구는 의무가 생기지 않으므로 보고로 충분하다.
- **의존을 사람이 제품·개발로 분류한 목록 파일:** 잠금 파일과 어긋난다.

## 결과
- **얻는 것:** 도구 선택이 라이선스에 막히지 않는다. 결과물에 들어가는 의존의 copyleft는 계속 막는다.
- **감수하는 것:** `dev` 표시가 정확해야 한다. `devOptional`을 개발로 보기 때문에, 제품에도 선택적으로 필요한 의존이 개발로 분류되어 점검을 빠져나갈 수 있다(npm의 표시 의미를 그대로 따른 것이다). 이미지 안에 들어가는 시스템 패키지(OS 패키지)의 라이선스는 이 점검이 보지 않는다.

## 되돌리는 조건
도구를 배포물에 포함하게 되면(예: 이미지 안에서 실행) 그 도구는 제품 의존으로 본다.
