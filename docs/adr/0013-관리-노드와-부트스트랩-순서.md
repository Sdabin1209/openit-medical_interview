# 0013. 관리 노드와 부트스트랩 순서

## 상태
승인(2026-11-10, 헤드 위임. ADR 0002의 배포 절차와 ADR 0004의 배포 명령을 구체화)

## 맥락
ADR 0002는 "서버에서 `git clone` 후 `./deploy up`"으로 설명하고 "레지스트리가 있으면 lock의 digest로 받는다"고만 적었다. 처음 설치할 때 무엇이 먼저 있어야 하는지(신뢰의 뿌리, 레지스트리, 이미지)는 정하지 않았다. 레지스트리는 TLS로 서비스해야 하고(검증을 끄거나 insecure 레지스트리로 통과시키지 않는다), TLS 인증서는 신뢰의 뿌리가 있어야 발급되므로 순서가 정해져야 한다.

## 결정
- **관리 노드:** `deploy` 명령이 도는 곳이다. 서버 한 대면 그 서버다. 서버가 여러 대면 관리 노드 한 곳에서 docker context(SSH)로 다른 서버의 엔진을 다룬다(엔진 선택은 ADR 0009의 우선순위). 루트 CA 개인 키, 비밀 파일(`deploy/secrets/`), `deploy/pki/`는 관리 노드에만 있다(모두 git 제외).
- **`./deploy bootstrap`** 은 아래 순서로 한다. 각 단계는 이미 된 것을 건너뛰며 두 번 실행해도 결과가 같다(멱등).
  1. **신뢰의 뿌리:** 비밀 파일 생성, 루트 CA 생성(`OPENIT_CA_MODE=self`) 또는 기관 CA가 서명한 중간 CA 설치(`institution`), step-ca 설정(`ca.json`)과 신뢰 목록 생성. 상세는 ADR 0014, 0015.
  2. **레지스트리:** step-ca와 레지스트리를 띄우고 TLS를 신뢰 목록으로 검증한다. 레지스트리 이미지는 Docker Distribution(`registry:3`, Apache-2.0)이고, TLS 종단은 앞단 Caddy(Apache-2.0)가 ACME로 step-ca에서 인증서를 받아 맡는다.
  3. **이미지 push와 digest 기록:** 서비스·화면 이미지를 레지스트리에 올리고, 레지스트리가 돌려준 매니페스트 digest를 `deploy/images.lock`에 쓴다. 로컬에 이미지가 없으면 먼저 `./deploy build`와 같은 빌드를 한다. lock의 digest가 이미 레지스트리에 있으면 건너뛴다.
  4. **서비스 기동:** `docker compose up -d --wait`.
  끝에 `./deploy ca status`로 인증서 상태를 보이고, 하나라도 기준 미만이면 rc=1이다.
- **외부 레지스트리:** `OPENIT_REGISTRY_MODE=external`이면 2단계를 건너뛰고(compose의 `local-registry` 프로파일을 켜지 않는다) `OPENIT_REGISTRY_ADDRESS`의 주소로 3단계를 한다. 이 경우 push·존재 확인은 도커 엔진의 표준 경로(`docker push`, `docker buildx imagetools inspect`)를 쓰며, 그 레지스트리의 인증서 신뢰는 운영처가 엔진에 설치한다(`/etc/docker/certs.d/<주소>/ca.crt`가 Docker의 표준 위치다).
- **레지스트리 클라이언트:** 로컬 레지스트리에 올리고 받는 일(`push`, `pull`, 존재 확인)은 compose 안쪽 네트워크의 일회용 컨테이너(crane, Apache-2.0)가 `registry:443`에 접속해서 한다. 인증서는 신뢰 목록의 루트만 믿고 검증한다. `./deploy pull`은 lock의 digest로 받는다.
- **TLS 예외는 localhost 하나뿐이다.** Docker 데몬은 `127.0.0.0/8`로 접속하는 레지스트리의 TLS 검증을 생략하는 것이 기본값이다. 같은 서버의 데몬이 compose 서비스 이미지를 받을 때를 위해 Caddy는 `127.0.0.1`·`localhost` 접속에 한해 Caddy 내부 CA의 인증서를 낸다(`default_sni`). 그 밖의 이름은 step-ca가 발급한 인증서만 받는다. 인증서 검증을 끄거나 insecure 레지스트리 설정(`insecure-registries`)을 쓰지 않는다.
- 컨테이너 이름·볼륨 이름은 `OPENIT_PROJECT_NAME`(기본 `openit`)이 접두어다. 한 서버에 설치를 둘 이상 두거나 시험용 설치를 따로 띄울 수 있다.

## 왜
- 순서는 의존 방향이다. 레지스트리의 TLS 인증서는 CA가 있어야 하고, 서비스 이미지는 레지스트리가 있어야 digest로 받을 수 있고, 서비스는 이미지가 있어야 뜬다. 거꾸로 하면 첫 설치가 닭과 달걀에서 멈춘다.
- 멱등은 워크스페이스 규칙(잡은 같은 입력에 같은 결과, 여러 번 실행해도 안전)이다. 이미 된 단계를 건너뛰므로 중간에 실패해도 같은 명령을 다시 실행하면 된다.
- 레지스트리를 일회용 안쪽 컨테이너로 다루는 이유: 호스트 도커 데몬이 게시된 포트에 닿는지는 설치 환경에 달렸다. 이 환경(Docker Desktop, WSL)에서는 데몬이 호스트에 게시된 `127.0.0.1` 포트로 접속하지 못했다(`docker run --network host`에서 같은 포트가 거부됨을 확인). 안쪽 네트워크의 이름으로 접속하면 어디서나 같고, 데몬에 루트 인증서를 설치하지 않아도 TLS를 끝까지 검증한다. docker context(SSH)로 원격 엔진을 다룰 때도 같다.
- Distribution registry는 OCI Distribution 사양의 참조 구현이다. 인증서를 시작할 때 한 번만 읽고 ACME를 모르므로, 갱신이 자동인 Caddy를 앞에 둔다(ADR 0014).
- Caddy의 `/data`는 이미지에서 root 소유라 비root가 쓸 수 없어 tmpfs로 두고 상태를 갖지 않는다(시작할 때마다 새로 발급). 레지스트리 저장소(`registry-data`)는 이미지의 `/var/lib/registry`가 root 소유라 이름 있는 볼륨도 root 소유이므로 root로 돌리되 모든 권한(capability)을 버린다(시험에서 확인).

## 검토한 대안과 버리는 이유
- **`insecure-registries` 설정이나 검증 생략 플래그:** 사설 CA가 있는데 검증을 끄는 것은 CA를 두는 목적을 없앤다.
- **호스트 도커 데몬으로 push:** 위 이유로 환경에 따라 닿지 않는다. 외부 레지스트리에는 이 경로를 쓴다.
- **레지스트리가 직접 TLS 종단:** 인증서를 갱신할 때마다 레지스트리를 다시 시작해야 한다. Caddy는 ACME 갱신을 스스로 하고 무중단이다.
- **Harbor, Zot:** 인증·취약점 스캔까지 있는 큰 구성이다. 지금 필요한 것은 digest로 받는 저장소 하나다.
- **레지스트리 없이 `docker save`/`load`로 서버마다 전달:** digest로 받는다는 ADR 0002의 결정과 서버가 여러 대일 때의 확장을 놓친다.

## 결과
- **얻는 것:** 새 서버에서 `./deploy bootstrap` 한 번으로 신뢰의 뿌리부터 서비스까지 올라오고, 다시 실행해도 안전하다.
- **감수하는 것:**
  - 로컬 레지스트리에는 인증(로그인)이 없다. 게시 주소의 기본값은 `127.0.0.1`(`OPENIT_BIND_ADDRESS`)이고 compose 안쪽에서는 같은 네트워크의 서비스만 닿는다. 서버 여러 대에서 레지스트리를 공유하려면 인증 구성을 따로 정한다(남은 것).
  - `images.lock`의 digest는 push한 매니페스트의 digest다. 같은 소스를 다시 빌드하면 빌드 증명(attestation) 때문에 digest가 달라질 수 있다. 의도한 변화는 lock의 diff로 보인다.
  - Caddy 설정 파일(`deploy/caddy/Caddyfile`)이 바뀌어도 compose는 다시 만들지 않는다. 바꾼 뒤에는 `docker compose up -d --force-recreate registry`가 필요하다.
  - 이 환경 한 곳(Docker Desktop, WSL)에서만 확인했다. 데몬이 localhost 레지스트리에 닿는 환경(리눅스 서버)에서 `127.0.0.1` 예외 경로는 확인하지 못했다.

## 되돌리는 조건
여러 서버로 확장하면서 오케스트레이터로 옮기면(ADR 0004) 레지스트리 절차를 그 도구의 표준에 맞춘다. 레지스트리에 인증이 필요해지면 이 ADR을 보완하는 새 ADR을 쓴다.
