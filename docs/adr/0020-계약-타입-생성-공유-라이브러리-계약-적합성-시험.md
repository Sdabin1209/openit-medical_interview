# 0020. 계약 타입 생성, 공유 라이브러리, 계약 적합성 시험, 잡 영역 틀

## 상태
승인(2026-11-10, 헤드 위임). ADR 0003(영역 구조)과 ADR 0006(빌드 컨텍스트)을 구체화한다. ADR 0006 의 "빌드 컨텍스트는 서비스 폴더다"는 그대로 두고, `libs/` 는 bake 의 이름 붙은 컨텍스트로 들인다(아래).

## 맥락
영역 작업을 시작하기 전에 세 가지가 비어 있었다. (1) 계약(`contracts/`)에서 코드 타입을 만드는 길이 없어 영역이 계약을 손으로 옮겨 쓰게 된다. 그러면 계약과 코드가 어긋난다. (2) `libs/model-io` 처럼 여러 영역이 쓰는 코드의 자리와 틀이 없다. (3) 서비스가 계약대로 응답하는지 보는 시험이 없다. 헤드가 잡 영역(`jobs/`, 설계 5절)의 틀도 함께 요청했다.

## 결정

### 1. 계약 타입 생성
- **파이썬:** datamodel-code-generator(MIT)로 `contracts/components.yaml` 과 영역의 `contracts/openapi/<이름>.yaml` 에서 Pydantic v2 모델을 `src/<패키지>/contract/models.py` 에 만든다. 명령은 `uv run --project tools/checks openit-gen-contract <영역 폴더>` 하나이고 서비스·잡·라이브러리가 같이 쓴다. 입력은 영역 `pyproject.toml` 의 `[tool.openit.contract]` 의 `openapi`(계약 파일 이름 목록)와 `schemas`(스키마 이름 목록)다. openapi 가 없는 영역(model-lab 같은 잡, 라이브러리)은 `schemas` 만 쓴다.
- 생성기는 영역에 두지 않고 `tools/checks` 한 곳에 둔다. 버전이 `tools/checks/uv.lock` 하나로 고정되어 모든 영역의 생성물이 같은 생성기에서 나온다.
- **계약의 부분집합만 만든다.** openapi 의 작업이 참조하는 스키마와 `schemas` 의 이름, 그리고 그것들이 참조하는 스키마를 닫힌 집합으로 계산해 그것만 생성한다(구조 규칙 4: 영역은 자기 입출력만 안다).
- 생성기에 넣기 전에 `x-` 확장(`x-owner`, `x-basis`, `x-enum-descriptions` 등)을 지운다. 계약 린트용 주석이고, 생성기는 `x-enum-descriptions` 를 다른 뜻(목록)으로 읽어 실패한다(실제로 확인).
- 같은 계약이면 같은 생성물이다. 시각을 넣지 않고(`--disable-timestamp`), 스키마를 이름순으로 정렬하고, 포맷터는 생성기 내장(`builtin`)이라 다른 도구 버전에 흔들리지 않는다(시험: 두 번 생성해 같음).
- **화면:** openapi-typescript(MIT)로 `src/contract/` 를 만든다. 설정은 화면 폴더의 `redocly.yaml`(이 도구가 읽는 표준 설정 파일)이고 `npm run generate:contract`, 점검은 도구 자체의 `--check`(`npm run check:contract`)다. 손으로 쓴 `health.d.ts` 와 그 fixtures 는 지우고 계약 `platform.yaml` 에서 만든 `platform.d.ts` 로 바꿨다.
- **생성물은 커밋하고** `openit-check contract-drift` 가 계약에서 다시 만든 결과와 다르면 실패시킨다(파이썬은 바이트 비교, 화면은 `openapi-typescript --check`). 템플릿도 같은 점검을 받는다.

### 2. 공유 라이브러리(`libs/`)
- 틀 `templates/lib` 와 `tools/new-area lib <이름>`. 구조는 ADR 0003 을 따른다: 공개 API 는 `src/<패키지>/__init__.py` 의 `__all__`(시험이 이름이 풀리고 설명이 있는지 본다), 구현은 `core/`, 생성 타입은 `contract/`. 시험·ruff·pyright strict·import-linter 는 영역과 같다. import-linter 는 라이브러리가 통신·저장소 패키지를 모르게 하고 `core` 가 `contract` 를 쓰는 방향만 허용한다.
- `libs/model-io` 를 이 틀로 만들었다. 지금은 빈 공개 API 와 생성 타입(`ActionExtraction`, `ActionExtractionInput`, `ActionExtractionRules`, `ExtractionAction`, `ModelInputSerialization`, `ResponseSentence`)뿐이다. 내용은 영역 에이전트가 채운다.
- **서비스와 잡은 `libs/<이름>` 을 경로 의존으로 쓴다(PEP 508 + `[tool.uv.sources]` 의 `path`).** `tools/new-area service|job <이름> --lib <라이브러리>` 가 `uv add ../../libs/<이름>` 를 부르고, uv 가 의존 한 줄(버전 없음)과 sources 표를 쓴다. 영역마다 `uv.lock` 이 따로 있다.
- 이미지 빌드: `docker-bake.hcl` 이 `contexts = { libs = "libs" }`(Buildx 의 이름 붙은 컨텍스트)를 주고, Dockerfile 이 `FROM scratch AS libs` 를 앞에 두어 `COPY --from=libs / /work/libs` 로 들인 뒤 `WORKDIR /work/services/<영역>` 에서 `uv sync --frozen` 을 한다. 개발 환경과 같은 상대 경로(`../../libs/<이름>`)로 풀린다. 빌드 컨텍스트는 영역 폴더 그대로다. `libs/.dockerignore` 는 이름 붙은 컨텍스트에서도 읽힌다(빌드 로그에서 확인).

### 3. 계약 적합성 시험
- Schemathesis(MIT)로 서비스의 FastAPI 앱을 영역의 openapi 로 시험한다. `tests/contract/test_contract_conformance.py` 가 ASGI 로 앱을 직접 부른다(네트워크 없음). 계약의 모든 작업에서 입력을 만들고 상태 코드·내용 형식·응답 헤더·본문 스키마를 계약과 견준다.
- 준비된 앱(200)과 준비되지 않은 앱(503) 둘을 시험한다(계약이 두 응답을 모두 정의). `not_a_server_error` 검사는 뺀다. 계약이 정의한 503 을 서버 오류로 보기 때문이다. 정의된 응답은 나머지 넷이 본다.
- 템플릿의 건강 응답(`/healthz`, `/readyz`, `/metrics`)을 계약 `platform.yaml` 에 맞췄다. 본문은 `HealthReport`, 준비 안 됨은 `ProblemDetails`(`application/problem+json`, `Retry-After`), 지표는 prometheus-client(Apache-2.0 AND BSD-2-Clause)의 표준 텍스트 형식이다.
- 계약에 없는 이름의 영역(시험 영역, 새 영역 이름)은 `HealthReport.service` 가 계약 `ServiceName` 값이어야 하므로 `platform` 의 이름을 빌린다(`tools/new-area` 가 정한다).

### 4. 잡 영역 틀(`templates/job`, `jobs/<영역>`)
- 서비스와 같은 구조(types, components, link, contract, tests)에서 HTTP 서버와 DB 를 뺐다. 진입점은 표준 CLI 라이브러리 Typer(MIT, deploy 명령과 같다)이고 `<이미지> <잡 이름>` 으로 한 번 실행한다. 이 호출 모양은 계약에 정해져 있지 않아 이 틀의 선택이다(deploy 와 맞춘다. 미확인).
- 결과는 표준 출력에 `JobRunResult` JSON 한 줄, 종료 코드 0(성공)·75(일시적 실패, sysexits EX_TEMPFAIL)·1(실패)(D130). 로그는 표준 오류로 낸다. 잡 이름은 계약 `JobName` 이다.
- 선언 `jobs.json`(`JobsDeclaration`)이 원본이고 이미지 라벨 `io.openit.jobs` 로 나간다. HCL 에는 파일을 읽는 함수가 없어(`file()` 이 없음을 확인) `deploy/deploy build` 가 모든 `jobs/*/jobs.json` 을 한 줄 JSON 으로 모아 bake 변수 `JOB_DECLARATIONS` 로 넣고, bake 가 영역 이름으로 골라 라벨 인자 `JOBS` 에 넣는다. 시험이 `jobs.json` 이 `JobsDeclaration` 이고 `JOBS` 표와 같은 이름 집합인지 본다.
- Dockerfile 은 비 root(10001), `ENTRYPOINT` 가 잡 명령, `HEALTHCHECK`·`EXPOSE` 없음(서버가 아니다). `docker-bake.hcl` 에 `JOB_AREAS` 목록과 `job` 대상, `deploy/deploy build` 의 대상 열거와 `tools/new-area` 의 갱신 대상에 `jobs/` 를 넣었다.

## 왜
- **표준 생성기가 계약을 코드로 옮기는 일을 사람 손에서 뺀다.** 손으로 옮기면 어긋남이 언제 생기는지 알 수 없다. 생성물을 커밋하고 점검이 다시 만든 결과와 비교하면 어긋남이 커밋 전에 잡힌다.
- **생성기를 한 곳에 두는 이유**: 영역마다 설치하면 버전이 영역마다 달라 같은 계약에서 다른 모양이 나온다.
- **부분집합 생성**: 계약 전체를 모든 영역에 넣으면 영역이 자기 입출력 밖을 알게 된다(구조 규칙 4).
- **경로 의존**: PEP 508 직접 참조와 uv 의 `path` 소스는 표준 방식이고, 영역마다 잠금 파일이라는 ADR 0006 의 전제를 지킨다.
- **이름 붙은 컨텍스트**: 빌드 컨텍스트를 리포 루트로 넓히면 이미지 빌드마다 `node_modules`, `.venv`, 다른 영역 전체가 컨텍스트 후보가 되고 영역마다 Dockerfile 전용 ignore 파일이 필요하다. 이름 붙은 컨텍스트는 Buildx 공식 기능이고 필요한 폴더만 들인다.
- **Schemathesis**: OpenAPI 에서 시험 입력을 만드는 표준 도구이고 ASGI 앱을 네트워크 없이 부를 수 있다(스모크는 별도).

## 라이선스(배포물 의존은 허용형만, 개발 도구는 무관, ADR 0017)
| 도구 | 라이선스 | 어디에 쓰나 |
|---|---|---|
| datamodel-code-generator | MIT | 개발 도구(`tools/checks`), 생성물에는 들어가지 않음 |
| openapi-typescript | MIT | 개발 도구 |
| Schemathesis | MIT | 개발 의존(시험) |
| hypothesis(Schemathesis 의 의존) | MPL-2.0 | 개발 의존만. 이미지에 들어가지 않는다(`openit-check licenses` 가 개발 전용으로 보고) |
| prometheus-client | Apache-2.0 AND BSD-2-Clause | 서비스 제품 의존(이미지에 들어가고 THIRD_PARTY_NOTICES 에 실린다) |
| Typer | MIT | 잡 제품 의존 |
| uv, hatchling | MIT·Apache-2.0, MIT | 도구 |

설치는 버전을 쓰지 않고(`uv add`, `npm install`) 잠금 파일이 고정한다.

## 검토한 대안과 버리는 이유
- **계약 타입을 손으로 쓰기**: 어긋남을 못 잡는다.
- **`components.yaml` 전체를 모든 영역에 생성**: 영역이 이웃의 값까지 알게 된다. 파일도 수천 줄이다.
- **openapi-python-client, openapi-generator(Apache-2.0, Java)**: 클라이언트·서버 틀까지 만들어 우리 구조(ADR 0003)와 겹친다. 우리는 값 타입만 필요하다.
- **orval**: 화면은 값 타입만 필요하고 호출은 `link/` 가 맡는다. 호출 코드까지 만드는 도구는 경계 규칙과 겹친다.
- **uv workspace**: 리포 루트에 잠금 파일이 하나뿐이라 영역별 `uv.lock`(ADR 0006, Dockerfile 의 `uv sync --frozen`)과 맞지 않고, 이미지 빌드에 리포 전체 컨텍스트가 필요하다.
- **라이브러리를 Git 태그나 패키지 저장소로 설치**: 같은 리포 안의 코드에 태그를 달고 올리는 단계가 더 생긴다. 모노레포에서는 경로가 같은 일을 한다.
- **빌드 컨텍스트를 리포 루트로**: 위 "왜" 참고. ADR 0006 이 되돌리는 조건으로 적어 둔 길이지만 이름 붙은 컨텍스트로 충분했다.
- **`not_a_server_error` 를 켜기**: 계약이 정의한 503 에 실패한다.

## 결과
- **얻는 것:** 계약에서 나온 타입을 쓰고 어긋남이 `openit-check` 에서 잡힌다. 서비스가 계약대로 응답하는지 영역마다 같은 시험으로 본다. 새 영역(서비스·잡·라이브러리·화면)이 한 명령으로 만들어진다.
- **감수하는 것:**
  - 생성물이 큰 파일로 커밋에 들어간다. 생성기를 올리면 생성물이 바뀌어 한 번에 다시 만들어야 한다(점검이 알려 준다).
  - 화면의 drift 점검은 `npm ci` 로 `openapi-typescript` 가 설치되어 있어야 돈다. 없으면 건너뛰지 않고 실패한다(어긋남을 놓치지 않으려고).
  - Dockerfile 을 bake 없이 `docker build` 로 직접 빌드하면 `libs` 컨텍스트가 비어 경로 의존이 있는 영역은 실패한다(`--build-context libs=libs` 를 줘야 한다).
  - 시험 값은 측정하지 않았다: 영역의 Schemathesis 시험 예시 수 25(생성된 입력 수의 임의 값. 건강 작업은 입력이 없어 영향 없음), 잡 시간 상한 600초와 `Retry-After` 5초(계약의 예시 값을 따른 것이고 측정이 아니다).
- **아직 안 한 것:** 화면의 `/metrics`(정적 nginx 라 Prometheus 지표를 내지 않는다), 계약이 영역에 요구하는 지표(`RequiredPrometheusMetric`), 인증이 있는 작업의 Schemathesis 설정(실제 영역이 계약을 받으며 채운다).

## 되돌리는 조건
datamodel-code-generator 가 계약의 JSON Schema 를 읽지 못하게 되거나 생성물이 흔들려 같은 입력에서 다른 출력을 내면 생성기를 바꾸는 새 ADR 을 쓴다. 영역마다 다른 라이브러리 버전이 필요해지면(경로 의존이 맞지 않으면) 라이브러리를 태그로 게시하는 방식으로 이 ADR 의 2절을 대체한다.
