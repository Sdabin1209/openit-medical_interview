# 0024. 빌드는 설치 설정을 읽지 않는다

## 상태
승인(2026-11-11, 통합 담당. 헤드의 새 clone 검증에서 나온 결함의 수정). ADR 0004·0016·0023 을 보완한다.

## 맥락
`./deploy build` 가 Trivy 를 `deploy/compose.yaml` 의 `trivy` 서비스로 돌렸다. compose 를 읽으려면 `./deploy` 가 platform 설정(입구·인증서·영역 노출 선언)을 먼저 생성해야 해서(`generated/platform.env` 등), 이미지 라벨의 노출 선언이 이미 한 번 동기화된 설치에서는 기기 CA 같은 설치 설정이 없으면 빌드가 '기기 경로를 열었는데 OPENIT_DEVICE_CA_CERTIFICATE_FILE 이 없다'로 멈췄다(새 clone 에서 doctor 를 먼저 돌린 뒤 build 한 경우).

## 결정
- 12-Factor App V(build, release, run 분리)를 따른다. 빌드 단계(`./deploy build`)는 설치 설정을 읽지 않는다. 설치 설정을 읽는 platform 설정 생성은 release·run 단계(`up`, `bootstrap`, `doctor`)에서만 일어난다.
- 빌드 단계의 도구(Trivy)는 설치와 무관한 `deploy/compose.tools.yaml` 로 옮긴다(공식 이미지, digest 고정, `network_mode: bridge` 로 프로젝트 네트워크를 만들지 않는다). `trivy()` 는 이 파일만 읽는다.
- `doctor` 는 platform 설정 생성이 틀리면(예: 기기 CA 없음) 다른 점검처럼 `[FAIL]` 한 줄로 알리고 멈춘다.

## 왜
- 같은 소스에서 같은 이미지가 나와야 한다(ADR 0004). 이미지가 설치처의 기기 CA 같은 값에 따라 빌드가 되거나 안 되면 build 와 run 이 섞인 것이다.
- CI 가 서버 안의 로컬 레지스트리로 이미지를 올리는 것(D24)은 설치 설정이 없는 곳에서 돌 수 있다.

## 검토한 대안과 버리는 이유
- **빌드에서 platform 생성 오류를 삼킨다:** 오류를 숨겨 release 단계에서야 드러난다.
- **compose.yaml 에서 Trivy 를 프로파일로 두고 생성 파일을 빈 자리로 채운다:** 빈 자리 값이 늘고 compose 가 생성 파일에 계속 기댄다.

## 결과
- **얻는 것:** 새 clone 에서 `secrets init` 뒤 설치 설정 없이 `build` 가 된다.
- **감수하는 것:** compose 파일이 둘이다. Trivy 이미지의 digest 는 `compose.tools.yaml` 에 있고 image-pins 점검이 이 파일도 본다.

## 되돌리는 조건
빌드가 설치 설정 없이 쓸 다른 도구가 늘면 그 도구도 이 파일로 옮긴다.
