# 0004. LoRA-A state 고르기와 묶음 순서

## 상태
승인(2026-11-10, 계약 8.0.0: 모델 입력의 글과 state 에 넣을 문항의 선택은 model-runtime 이 한다. ADR 0019).

## 맥락
LoRA-A 입력의 `state` 는 저장된 칸 중 세 문항의 값만 넣는다(IO_SPEC.md 2.1, SQL.md 7.1): 지금 문항, 직전에 물은 문항, 참조 원천 문항(`taxonomy.py` 의 `REF_SOURCE`, 예: Q10 → Q9_1). 학습 데이터의 칸 묶음 순서는 정본 `prev_state.py` 가 정한다. 그 순서는 시나리오가 원래 가진 state 가 먼저이고 그 뒤에 직전·참조 문항이 오는 구조라, 서비스는 시나리오 정보를 몰라 완전히 재현할 수 없다(OPEN_GAPS G13).

## 결정
- `REF_SOURCE` 는 정본 `taxonomy.py` 의 표를 글자 그대로 `core/taxonomy_port.py` 에 옮기고(ADR 0003 과 같은 방식) 시험이 정본 소스와 대조한다.
- 직전 문항은 요청의 `previous_question_id`(서비스가 세션 진행으로 안다)를 쓴다.
- 칸의 순서: 지금 문항의 확정 값 → 직전 문항의 확정 값 → 참조 원천 문항의 확정 값 → 다시 묻는 칸(MISSING·UNCLEAR). 같은 칸이 다시 나오면 값은 나중 것, 자리는 처음 자리다(정본 `a_state` 가 dict 에 쓰는 규칙). 이 순서는 `prev_state.py` 의 `a_state(answered, pending)` 이 확정 값 뒤에 다시 묻는 칸을 붙이고, 흐름이 직전 문항 뒤에 참조 원천을 붙이는 구조를 서비스가 아는 것만으로 옮긴 것이다.

## 왜 이 순서인가(측정)
학습 파일 A 입력 46655행에서, 저장된 칸 목록을 state 항목에서 대화 순서로 되만들고 직전 문항을 '지금·참조 원천이 아닌 문항 중 순서표에서 가장 뒤'로 정해(시험용 되만들기, 직전 문항은 학습 파일에 없다) 재현했다.
| 후보 순서 | final 44563행 칸 순서까지 같음 |
|---|---|
| 지금(확정) → 직전 → 참조 → 다시 묻는 칸(채택) | 43886행(98.48%) |
| 대화 순서(순서표 순서), 다시 묻는 칸 마지막 | 35887행(80.5%) |
| 대화 순서, 다시 묻는 칸도 제자리 | 35887행(80.5%) |
- 고르는 문항 집합은 세 후보 모두 100% 같다(44563행, finaltest 2092행).
- 평가 파일 finaltest 는 칸 순서가 1843/2092행(88.1%)이다. 나머지 차이는 시나리오가 정한 순서로 보이며 서비스가 재현할 수 없다(데이터셋 변경 요청 DC-09 와 같은 평가 집합 문제).
- 바이트까지 같은 전체 A 입력: 43978행(final 43886 + 빈 state 92). 틀리는 677행(1.52%)은 '참조 원천이 먼저, 그 뒤 직전' 같은 시나리오가 정한 순서다.

## 검토한 대안과 버리는 이유
- **대화 순서 그대로:** 80.5% 로 더 낮다.
- **서비스가 순서까지 정해 보내기:** 서비스가 데이터셋 규칙을 알게 된다(헤드 결정: 규칙은 model-runtime 한 곳).
- **모든 저장 값을 state 에 넣기:** 학습 분포와 다르다(IO_SPEC.md 2.1).

## 결과
- **얻는 것:** 서빙이 학습과 같은 규칙으로 state 를 만든다. 선택은 100%, 순서는 98.48% 재현한다.
- **감수하는 것:** 1.52% 는 학습 데이터와 칸 순서가 다르다. 순서 차이가 모델 출력에 주는 영향은 GPU 에서만 확인할 수 있다(미확인).

## 되돌리는 조건
데이터셋이 시나리오와 무관한 묶음 순서 규칙을 정본으로 정하면 그 규칙으로 바꾸고 이 ADR 을 대체한다.
