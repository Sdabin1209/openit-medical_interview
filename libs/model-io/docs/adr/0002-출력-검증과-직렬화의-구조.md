# 0002. 출력 검증과 직렬화의 구조

## 상태
승인(2026-11-10, model-runtime 영역 작업자). 계약 변경이 필요한 부분은 변경 요청 model-runtime-001, 002 로 헤드에게 넘겼다.

## 맥락
모델 입력 글자는 학습 데이터의 user 메시지와 바이트까지 같아야 하고(D77), 모델 출력은 계약의 합격 조건 위반 코드 10개로 한 번만 검사해야 한다(R7). 생성 모델(datamodel-code-generator)은 JSON Schema 의 `if/then` 조건과 수의 정수/실수 구분을 담지 못한다. 이 라이브러리는 model-runtime 이미지에도, model-lab 의 평가에도 들어간다.

## 결정
1. **입력은 JSON 으로 푼 dict 다.** 영역이 가진 생성 클래스와 이 라이브러리의 생성 클래스는 다른 클래스라 클래스를 넘기지 못한다. 계약 값은 낸 쪽(FastAPI 가 요청을 검증)이 이미 검증했으므로 색인을 만들 때 다시 검증하지 않는다(R7).
2. **OUTPUT_SCHEMA = 생성 모델 strict 검증 + 코드로 쓴 `if/then` 조건.** 조건(NEXT·CORRECT 에는 reason/targets/note 없음, REASK 등은 reason·targets 필수, REDIRECT 는 reason 필수·targets 없음, note 는 OUT_OF_SCHEMA 일 때만, 값이 null 이면 precision 이 unspecified)은 계약에서 옮긴 것이다. 어긋남은 `tests/contract/test_output_schema_matches_contract.py` 가 계약 파일을 직접 읽어 jsonschema(2020-12)로 같은 판정인지 335건으로 확인한다.
3. **next_item 규칙은 데이터셋 정본(labels.py `a_target`, `next_after`)을 따른다.** 계약 `NextItemRuleKind.SEQUENCE_AFTER_SAVED` 설명("저장한 칸 중 가장 뒤 문항의 다음")대로 하면 정답 46655건 중 168건이 어긋난다(측정). 정본대로는 0건이다. 계약 문구 수정은 변경 요청 model-runtime-001 이다.
4. **고쳐 쓰기(D115)는 세 가지만 한다.** 다음 문항 채우기(U74), 칸 규격 최댓값 초과(`REASK/OUT_OF_RANGE`, 값 null, UNCLEAR, save 거짓, U32), 횟수가 기간 날수보다 큼(R2, `REASK/COUNT_EXCEEDS_DAYS`). 자료형·최솟값·선택지 위반은 데이터셋에 정답 모양이 없어 고쳐 쓰지 않고 출력 불가다(D115). R1·R3 은 규칙 데이터(술 환산표 등)가 계약에도 `contracts/inputs` 에도 없어 만들지 않았다(변경 요청 model-runtime-002).
5. **고친 출력은 다시 검사한다.** 고친 뒤에도 위반이 있으면 출력 불가다. 위반 수는 고치기 전 출력으로 센다.
6. **직렬화.** A: `json.dumps(obj, ensure_ascii=False)`, 최상위 키 정렬, state 는 `state_key_order`, state 항목 안은 `value` → `status`. B: `sort_keys=True`. 정수로 읽힌 실수(15.0)는 정수 글자로 쓴다.

## 왜
- 정본이 데이터셋이다(D74). 서빙이 학습에 맞춘다(D77).
- 학습 파일 측정: A 입력 46655행 중 학습·검증·시험(final) 44563행이 바이트까지 같다. 평가 파일(finaltest) 2000행은 state 항목 안 키 순서가 `status, value` 다(학습 파일은 `value, status`, 계약은 항목 안 순서를 정하지 않는다: 변경 요청 model-runtime-001). B 입력 46774행 중 10행은 학습 파일 자체가 정렬되어 있지 않다.
- 정수/실수: 학습 파일의 state·출력 값에 `x.0` 글자가 없다(실측). 계약 값이 수를 실수로 읽어 15 를 15.0 으로 만들므로 정수로 읽히는 값은 정수로 쓴다.
- 날수 상한(주 7, 달 31, 해 366)은 달력이 정하는 가장 긴 값이다. 가능한 답을 되묻지 않으려는 선택이고 측정하지 않았다(정답에서 받아들인 최대 횟수는 주 7, 월 30, 년 15 로 위반 0).

## 검토한 대안과 버리는 이유
- **계약 YAML 을 이미지에 넣어 jsonschema 로 검사:** 계약 사본을 이미지에 두게 되고(영역은 자기 입출력만 안다, 구조 규칙 4), 이미지 빌드 컨텍스트에 `contracts/` 가 없다. 대신 드리프트 시험이 계약을 직접 읽는다.
- **생성 모델만으로 검증:** `if/then` 조건이 빠진다.
- **고쳐 쓰기를 모두 출력 불가로:** U74 가 서버가 next_item 을 채우라고 정했다.
- **계약 문구대로 '가장 뒤 저장 문항':** 위 측정으로 기각.

## 결과
- **얻는 것:** 운영과 평가가 같은 검사기. 학습 정답 46655행이 위반 0, 고쳐 쓰기 0.
- **감수하는 것:** 계약 `if/then` 을 코드로 한 번 더 쓴다(드리프트 시험이 지킨다). 계약 문구와 정본의 차이를 코드가 정본 쪽으로 해소한다.

## 되돌리는 조건
계약이 `SEQUENCE_AFTER_SAVED` 를 정본에 맞게 고치거나 규칙 데이터(R1·R3)를 싣거나 항목 안 키 순서를 정하면 이 ADR 을 대체한다.
