# 0008. 시험은 외부 제품의 갱신 시간을 재지 않는다

## 상태
승인(2026-11-11, platform 작업). 리포 ADR 0014 의 "시험 방법(수명 5분 설치에서 갱신을 기다린다)"과 platform ADR 0006 결과 절의 "1단계 직후 2단계 rc=1, 갱신 뒤 rc=0 확인"을 대체한다(인증서 수명과 갱신 설계는 그대로).

## 맥락
샌드박스 시험이 수명 5분 인증서가 실제로 갱신되기를 기다렸다(입구 인증서 일련번호가 바뀔 때까지 최대 420초, 루트 교체 뒤 이전 루트를 뺄 수 있을 때까지 최대 600초). 이 시간은 step-ca·Caddy·Envoy 의 타이머이고 우리 코드가 아니다. 시스템 부하가 높으면 갱신이 늦어져 시험이 흔들리고, 갱신 동작 자체는 그 제품들의 시험이 보증한다.

## 결정
- 갱신 동작을 실제 시간으로 기다리는 시험을 두지 않는다. 우리가 그 제품들에 건네는 **설정**이 갱신을 가능하게 하는지를 생성물로 시험한다(`platform/tests/unit/test_certificate_renewal.py`).
- 샌드박스는 리프 수명 기본값을 쓴다(5분 덮어쓰기를 없앤다). 샌드박스의 기다림은 기동·반영이 끝나는 **상태**를 보는 것이고, 시간은 멈춘 기동을 끝내는 상한이다(`Sandbox.wait(…, limit_seconds)`). 간격은 통과 조건이 아니다.
- step-ca 가 거부하는 5분 미만 리프 수명은 기동 뒤가 아니라 설정 단계에서 막는다(`pki.MIN_LEAF_MINUTES`, `ca_settings`).

## 지운 시험과 보증이 옮겨 간 곳
| 지운 것 | 보던 것 | 지금 보증하는 곳 |
|---|---|---|
| `test_ingress_certificate_is_renewed_and_envoy_reloads_it_without_restart` | Caddy 가 5분 리프를 갱신한다 | 갱신 점검 주기(`renew_interval 1m`)가 가장 짧은 허용 리프(5분)의 갱신 구간(수명의 1/3 = 100초) 안에 든다: `test_renewal_check_runs_inside_the_renewal_window_of_the_shortest_allowed_leaf`(입구 에이전트와 영역 게이트웨이 둘 다). CA 가 건네받는 수명·하한: `test_leaf_lifetime_is_never_shorter_than_the_ca_minimum_and_the_ca_is_told_so`, 기존 `test_ca_json_carries_acme_provisioner_policy_and_leaf_lifetime` |
| 같은 시험의 "Envoy 가 다시 시작하지 않고 새 인증서를 읽는다" | Envoy 가 갱신된 파일을 다시 읽는다 | 두 인증서(입구, 영역 사이 클라이언트) 모두 파일 SDS 이고 인증서·키가 있는 폴더를 `watched_directory` 로 감시하며 인라인 인증서가 없다: `test_both_envoy_certificates_are_sds_files_that_watch_their_own_folder`, 기존 `test_certificates_are_read_through_file_sds_that_watches_the_folder`. Envoy 가 그 설정대로 다시 읽는 것은 Envoy 의 동작이다(과거 시험에서 인라인 인증서는 읽지 않았고 파일 SDS 는 읽는 것을 확인했다는 기록이 `gateway.py` 에 있다) |
| `test_root_rotation_keeps_both_roots_until_leaves_are_renewed` 의 뒷부분(리프가 새 루트로 갱신되길 기다려 2단계 `--finish --distributed` 완료, 이전 루트 제거 뒤 교체 확인) | 교체 중 두 루트를 함께 믿고, 이전 루트를 빼면 하나만 남는다 | 신뢰 목록 생성: `test_root_rotation_bundle_keeps_both_roots_until_the_old_one_is_removed`(1단계가 두는 `old-root-*.crt` 이름으로 두 루트, 파일을 빼면 하나), 기존 `test_bundle_allows_several_roots_without_duplicates`. 같은 목록 파일을 Caddy 와 Envoy 가 읽는다: `test_trust_list_is_the_one_file_renewal_and_upstream_checks_read_roots_from` |
| `test_area_metrics_are_scraped_and_watchdog_fires` 의 Watchdog 대기 | Watchdog 가 Alertmanager 에 닿는다 | 규칙의 발화는 `monitoring/rules.test.yml`(promtool, 가짜 시간), Prometheus→Alertmanager 대상과 Watchdog 전용 경로는 `test_prometheus_sends_alerts_to_alertmanager_and_watchdog_has_its_own_route` |

남긴 샌드박스 시험 `test_root_rotation_keeps_both_roots_and_traffic_flows` 는 1단계 직후만 본다(두 루트, 영역 게이트웨이를 새 목록으로 다시 만든 뒤 입구가 영역 서비스에 닿음, 배포 확인 없는 2단계는 rc=2).

## 왜
- 우리 코드만 시험한다. 라이브러리·외부 제품의 타이머를 실제 시간으로 재는 시험은 부하에 흔들리고 그 제품의 책임을 대신 시험한다.
- 갱신이 일어나려면 우리가 정하는 값이 맞아야 한다: 수명(step-ca 하한 이상), 점검 주기(갱신 구간 안), 갱신된 파일을 읽는 설정, 두 루트를 함께 담은 신뢰 목록. 이것들은 생성물로 결정적으로 시험된다.
- 1/3 은 Caddy(certmagic)의 기본 갱신 구간이다(리포 ADR 0014 가 채택). 5분은 step-ca 의 `minTLSCertDuration` 기본 하한이다(제품의 제약이며 측정값이 아니다).

## 검토한 대안과 버리는 이유
- **가짜 시계로 Caddy·step-ca 를 앞당기기:** 컨테이너 안 제품의 시계를 우리가 바꿀 수 없다(표준 수단이 없다).
- **갱신 대기 상한을 늘리거나 재시도를 붙이기:** 시험을 느슨하게 할 뿐 시간 의존을 없애지 못한다.
- **시험을 남기고 샌드박스에서만 실행:** 시간 의존이 그대로이고 한 번 도는 데 10분이 더 든다.

## 결과
- **얻는 것:** 갱신 관련 보증이 부하와 무관하게 결정적으로 돈다. 샌드박스는 5분 수명 때문에 중간에 인증서가 만료될 위험이 없다.
- **감수하는 것:** 갱신이 실제로 일어나는 것(Caddy 의 갱신, Envoy 의 재적재), 루트 교체 2단계의 종단 완료(이전 루트 서명 리프가 없어져 `--distributed` 가 성공하는 것)는 이 영역의 어떤 시험도 실행으로 보지 않는다. 배포 쪽 종단은 deploy 의 E2E 가 다룬다(그 결과는 `deploy/docs/E2E_RESULTS.md`). 샌드박스 대기의 상한(240초, 60초, 수집 주기의 4배)은 측정하지 않았다.

## 되돌리는 조건
설치처에서 갱신 실패가 설정이 아닌 원인으로 반복되면, 짧은 수명의 갱신 확인을 시험이 아닌 운영 점검(`./deploy ca status`, 만료 경보)으로 둔다.
