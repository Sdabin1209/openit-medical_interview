# 0009. 응답 문장 스트림의 시간 상한과 중간 장치

## 상태
승인(2026-11-11, platform 작업). 계약 9.2.0 을 받는다. ADR 0003 의 라우트 생성에서 스트림 경로에 전체 시간 제한 0초와 유휴 한도를 거는 규칙(`gateway.py`)을 끝이 없는 스트림에만 한정한다(0003 의 나머지는 그대로).

## 맥락
계약 9.2.0 은 끝이 있는 응답 문장 스트림 작업 셋을 더했다: `startSessionStream`·`submitTurnStream`(survey-service, 환자 경로), `generateResponseStream`(model-runtime, 영역 사이). 본문 스키마는 `ResponseEventStream` 이다. 끝이 없는 직원 알림 스트림은 `ServerSentEventStream` 이다. 계약은 `GatewayPatientRouteLimitSeconds`(55초)를 JSON 작업에서는 머리글까지, 스트림 작업에서는 **응답 끝까지**에 건다고 정한다(계약 README "응답 문장 스트림" 8항). 그런데 입구 생성기는 응답에 `text/event-stream` 이 있는 작업을 모두 같은 종류로 보고 route timeout `0s` 와 유휴 45초를 걸었다. 응답 문장 스트림이 55초 상한 없이 열려 있을 수 있었다.

## 결정
1. 스트림의 종류는 작업의 `text/event-stream` 응답 스키마 참조로 가른다(`gateway.STREAM_SCHEMAS`). `ResponseEventStream` 은 끝이 있는 것, `ServerSentEventStream` 은 끝이 없는 것이다. 경로 이름을 보지 않는다. 둘 밖의 스키마나 한 작업의 두 종류는 시작하지 않는다(`ConfigError`).
2. 끝이 있는 스트림의 Envoy 라우트는 JSON 작업과 같은 `timeout: 55s`(`GatewayPatientRouteLimitSeconds`)이고 `idle_timeout` 을 두지 않는다. 끝이 없는 알림 스트림은 지금처럼 `timeout: 0s` 와 `idle_timeout: 45s` 다.
3. 입구(Envoy)의 HTTP 필터에 버퍼링·압축 필터를 두지 않는다. Lua 필터는 요청 쪽(`envoy_on_request`)만 정의하고 본문을 읽지 않는다. ext_authz·jwt_authn·rbac 는 요청 머리글로 판정한다.
4. 영역 게이트웨이(Caddy)는 `encode` 지시어를 쓰지 않고 `reverse_proxy` 에 `flush_interval -1` 을 유지한다. 주석을 응답 문장 스트림까지 넓혔다.
5. CONNECT 터널(나가는 호출)은 바이트를 그대로 넘기므로 바꾸지 않는다.

## 왜
- Envoy `RouteAction.timeout` 은 "요청 전체(end-of-stream)가 처리된 때부터 업스트림 응답이 완전히 처리될 때까지"다. 즉 응답 끝까지이고 이것이 계약 8항의 "응답 끝까지에 건다"와 같다. 새 값도 장치도 필요 없다. 문서: https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/route/v3/route_components.proto (RouteAction.timeout, idle_timeout).
- `idle_timeout` 은 조각 사이 상한이다. 계약 8항은 "조각 사이의 상한은 따로 두지 않는다(전체 상한이 스트림을 묶는다)"고 하므로 끝이 있는 스트림에는 걸지 않는다. 끝이 없는 알림 스트림은 전체 상한이 없으므로 heartbeat 15초의 3배 유휴 상한이 필요하다(`gateway.STREAM_IDLE_SECONDS` 주석, 측정하지 않았다).
- Caddy `reverse_proxy` 문서: `Content-Type: text/event-stream` 응답은 `flush_interval` 과 무관하게 바로 flush 한다. 문서에 기대지 않고 `-1` 을 명시해 두는 것은 알림 스트림 때부터의 설정이고 비용이 없다. https://caddyserver.com/docs/caddyfile/directives/reverse_proxy
- Caddy `encode` 문서: 기본 match 가 `text/*` 를 포함하지만 `Cache-Control: no-transform` 응답은 압축하지 않고 text/event-stream 응답은 머리글을 바로 보내고 본문을 쓰는 대로 흘린다. 서비스가 `no-store, no-transform` 을 주므로(계약 1항) 켜도 압축되지 않지만, 영역 안은 평문 HTTP·영역 사이는 TLS 라 압축으로 얻을 것이 없어 쓰지 않는다. 쓰게 되면 `match` 에서 `text/event-stream` 을 뺀다. https://caddyserver.com/docs/caddyfile/directives/encode
- 계약 9항: 입구와 게이트웨이는 모으거나 압축하지 않고 받는 대로 넘긴다. `no-transform` 은 버퍼링을 막지 못하므로 설정이 맡는다.

## 검토한 대안과 버리는 이유
- **작업 경로가 `/stream` 으로 끝나면 스트림으로 본다:** 계약이 이름 짓기를 바꾸면 틀린다. 종류는 스키마가 정한다.
- **끝이 있는 스트림에도 `idle_timeout` 을 건다:** 계약 8항이 두지 않는다고 했고, 값(예: 15초)은 모델 첫 토큰 지연의 측정 없이는 근거가 없다. 늘리거나 재시도를 더하는 것은 하지 않는다.
- **끝이 있는 스트림에 `timeout: 0s` 를 유지:** 환자 경로에 응답 끝 상한이 없어 계약 위반이다.
- **Caddy 에 `encode` 를 두고 match 로 text/event-stream 을 뺀다:** 얻는 것이 없는 지시어를 더하면 나중에 match 가 바뀔 때 스트림이 깨질 수 있다.

## 결과
- 얻는 것: 환자 경로의 스트림이 55초 안에 끝나지 않으면 입구가 끊는다(JSON 작업과 같은 상한). 알림 스트림은 변함이 없다.
- 감수하는 것: 계약이 `text/event-stream` 에 새 스키마를 쓰면 입구가 시작하지 않고 이 표를 고쳐야 한다(조용히 틀리는 것보다 낫다).
- 시험: `tests/unit/test_gateway.py`(종류별 라우트, 스키마로 가름, 모르는 스키마 거절, 버퍼링·압축 필터 없음), `tests/unit/test_area_gateway.py`(`encode` 없음, `flush_interval -1`). 실제 스트림을 흘려 조각이 바로 오는지는 확인하지 않았다(영역 서비스가 없는 이 영역의 시험에서는 E2E 의 몫).

## 되돌리는 조건
계약이 스트림 상한의 끝을 바꾸거나 조각 사이 상한을 정하면 새 ADR 로 대체한다. Envoy 의 route timeout 의미가 바뀌면 다시 본다.
