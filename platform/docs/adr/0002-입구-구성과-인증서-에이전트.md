# 0002. 입구 구성과 인증서 에이전트

## 상태
승인(2026-11-10, platform 작업). 리포 ADR 0008의 "Envoy 기반 설정은 /healthz 만 응답"과 ADR 0015의 "공개 입구의 TLS 구성은 남은 것"을 이행한다. ADR 0014의 "ACME 클라이언트는 Caddy" 결정을 입구에도 쓴다.

## 맥락
입구(Envoy)는 공개 TLS 를 끝내고(인증서 방식 세 가지), 기기 인증서(mTLS)를 검증하고, 영역 서비스에는 사설 CA 의 클라이언트 인증서로 접속한다(계약 `area_mtls`). Envoy(v1.35)에는 ACME 클라이언트가 없고, 인증서 수명은 짧아(기본 7일) 갱신을 사람 손에 맡길 수 없다.

## 결정
- **인증서 에이전트 `ingress-acme`(Caddy, ACME RFC 8555):** 입구 이름의 인증서(`private` 은 사설 CA 에서, `acme-public` 은 공인 CA 에서)와 영역 서비스에 보일 클라이언트 인증서(이름 `gateway`, 늘 사설 CA 에서)를 받고 갱신한다. `organization` 은 조직이 준 인증서 파일을 쓰므로 입구 이름은 받지 않고 `gateway` 클라이언트 인증서만 받는다. http-01 만 쓴다(tls-alpn-01 은 끈다).
- **네트워크 이름공간 공유:** `envoy` 는 `network_mode: service:ingress-acme` 로 에이전트의 네트워크를 쓴다. CA 의 http-01 검증이 입구 이름의 80 번(에이전트)에 닿고 입구는 같은 이름의 8443 번(Envoy)으로 받는다. 입구 이름의 DNS 별칭은 에이전트 하나에만 붙는다(`deploy/generated/compose.platform.yaml`).
- **공유 폴더:** 인증서는 tmpfs 형식의 이름 있는 볼륨 `ingress-certs`(uid 10001)에 둔다. 에이전트가 쓰고 Envoy 가 읽기 전용으로 읽으며 둘 다 uid 10001 이다(키 파일은 0600). 서버가 다시 켜지면 새로 받는다.
- **갱신 반영:** 입구의 인증서(서버, 영역 사이 클라이언트)는 파일 기반 SDS(`deploy/generated/gateway/sds/*.yaml`)로 가리키고 Secret 안의 `watched_directory` 가 인증서 폴더를 지켜본다. Caddy(certmagic)가 인증서를 임시 파일을 쓴 뒤 이름을 바꾸는 방식으로 두므로 Envoy 가 인증서와 키를 한 쌍으로 다시 읽는다. 다시 시작하지 않는다. 인라인 `tls_certificates` 에 `watched_directory` 를 두는 방식은 갱신된 파일을 다시 읽지 않았다(수명 5분 설치에서 인증서가 만료될 때까지 그대로였다. 그래서 SDS 파일로 바꿨다). SDS 는 노드 식별자(`node.id`, `node.cluster`)를 요구한다.
- **상태 확인:** 에이전트의 healthcheck 는 인증서 파일이 있는지만 본다. 입구 설정이 읽는 경로는 `ingress.acme_issuer_key` 가 디렉터리 URL 에서 만든다(certmagic 의 저장 규칙).
- **포트:** 입구는 컨테이너 안 8443(`OPENIT_LISTEN_PORT`, 비 root 라 1024 이상)을 호스트의 `${OPENIT_BIND_ADDRESS}::8443`(Docker 배정)으로 게시한다. 80 번은 게시하지 않는다.
- **`acme-public`:** 공인 CA 는 공개 주소의 80 번으로 되돌아 접속하므로 설치처가 80 번을 에이전트로 이어 줘야 한다. 이 환경에서는 공개 도메인이 없어 시험하지 못했다.
- 설정 검증: `./deploy doctor` 가 생성한 Envoy 설정을 `envoy --mode validate`, Caddyfile 을 `caddy validate` 로 본다(자리에 시험용 인증서를 두고 일회용 컨테이너에서).

## 왜
- ACME 클라이언트는 ADR 0014 가 Caddy 로 정했다. 갱신 상태를 따로 관리하는 스크립트가 필요 없다.
- 네트워크 이름공간 공유가 없으면 http-01 검증 대상 이름이 에이전트와 Envoy 둘로 나뉘어 DNS 가 번갈아 답한다(검증이 확률적으로 실패한다).
- `watched_directory` 는 Envoy 의 TlsCertificate 기능이다. 갱신 때 연결을 끊지 않는다.

## 검토한 대안과 버리는 이유
- **Caddy 가 공개 TLS 를 끝내고 Envoy 로 넘기기:** 기기 인증서 정보는 Envoy 의 `X-Forwarded-Client-Cert` 가 계약이다(`securitySchemes.device_mtls`). Caddy 가 같은 형식을 만들게 하면 계약의 근거(Envoy 표준 헤더)가 사라진다.
- **step CLI 의 `ca renew --daemon`:** ADR 0014 가 ACME 로 정했고, 갱신 방식이 둘이 된다.
- **certbot, lego:** ADR 0014 가 버린 이유와 같다(재적재를 따로 이어야 한다).
- **Envoy SDS 서버(xDS):** 인증서 한 쌍에 서버 하나는 과하다. 파일 감시로 충분했다.
- **Envoy 가 root 로 돌며 에이전트의 파일을 읽기:** 비 root 와 cap_drop 규칙(ADR 0004)을 어긴다.

## 결과
- **얻는 것:** 입구 인증서와 영역 사이 클라이언트 인증서가 사람 손 없이 갱신되고 Envoy 는 다시 시작하지 않는다. 이 환경에서 5분 수명으로 갱신을 확인했다(`tests/scenario`).
- **감수하는 것:** 에이전트 하나가 더 돈다. 인증서 폴더가 메모리에 있어 서버를 다시 켜면 발급이 다시 일어난다(공인 CA 의 발급 횟수 제한에 닿을 만큼 자주 다시 켜지는 설치처는 `acme-public` 대신 `organization` 을 쓴다). 에이전트가 만든 `/data`·`/config` 도 tmpfs 다. 신뢰 목록(`OPENIT_TRUST_LIST_FILE`)이 바뀌면 에이전트와 Envoy 가 다시 만들어져야 읽는다(`./deploy ca rotate-root` 가 한다).
- 확인하지 못한 것: `acme-public` 방식, `organization` 방식의 종단 간 시험(단위 시험과 설정 검증만 했다), 갱신 직후 신뢰 목록이 달라지는 경우 외의 장시간 운영.

## 되돌리는 조건
Envoy 가 ACME 를 내장하면(릴리스 노트로 확인) 에이전트를 없앤다. 서버를 여러 대로 나누어 입구가 여러 대가 되면 인증서 공유 방식을 새 ADR 로 정한다.
