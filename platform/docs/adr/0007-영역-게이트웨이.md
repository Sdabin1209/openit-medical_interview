# 0007. 영역 게이트웨이(Caddy)

## 상태
승인(2026-11-11, platform 작업). 계약 9.0.0 의 결정 (a)(survey-service-006, model-runtime-003 의 7번)을 이행한다. 입구와 서비스 사이의 TLS 를 서비스가 끝낸다는 이전 가정(ADR 0002 의 '영역 사이 mTLS' 와 시험용 에코 상류)을 영역 게이트웨이가 끝내는 것으로 바꾼다. ADR 0002(입구 에이전트)는 유효하다.

## 맥락
계약은 영역 사이를 사설 CA 가 발급한 인증서의 mTLS(`area_mtls`)로 정했고, 서비스가 `X-Forwarded-Client-Cert`(XFCC)를 믿는 근거를 '게이트웨이와의 mTLS 연결'로 정했다. 서비스 컨테이너마다 ACME 클라이언트와 TLS 서버와 클라이언트 인증서 검증을 넣으면 서비스가 넷이고 구현이 넷이다. 9.0.0 은 서비스를 평문 HTTP 로 두고 TLS 를 영역마다 하나인 게이트웨이(Caddy)가 끝낸다고 정했다. 서비스가 XFCC 의 출처를 확인하는 방법은 영역 네트워크 구성(게이트웨이만 서비스에 닿는다)이다.

## 결정
영역(서비스 영역)마다 Caddy 컨테이너 하나가 `platform/caddy/area-gateway.Caddyfile` 한 파일(환경 변수 `OPENIT_AREA_NAME`, `OPENIT_AREA_UPSTREAM`, `OPENIT_SERVICE_PORT`, `OPENIT_INTERNAL_ACME_DIRECTORY_URL` 로 파라미터화)로 아래를 한다. 설명과 컨테이너 요건은 `platform/caddy/area-gateway.md`.

1. **인증서:** 서비스 이름으로 사설 CA(step-ca)에서 ACME(RFC 8555) http-01 로 받고 갱신한다(입구 에이전트, ADR 0002 와 같은 방식). 상태 폴더는 영역 안 공유 tmpfs 볼륨 `/area-certs` 이고 서비스가 읽기 전용으로 마운트해 이웃을 부를 때 보일 클라이언트 인증서와 키(`OPENIT_TLS_*_FILE`)로 쓴다. 경로는 입구와 같은 certmagic 규칙(`ingress.acme_issuer_key`)이고 `area_gateway.certificate_paths` 가 만든다.
2. **영역 사이 mTLS:** `client_auth { mode require_and_verify }` 와 신뢰 목록(`/etc/openit/trust-list.pem`). 신뢰 목록의 루트가 서명한 클라이언트 인증서가 없으면 핸드셰이크에서 끊는다. `strict_sni_host on`: Caddy 는 SNI 별 TLS 연결 정책에 클라이언트 인증을 건다. SNI 와 Host 가 다른 요청을 받으면 인증이 걸리지 않은 정책(SNI 가 맞는 사이트가 없는 연결)으로 서비스 이름의 Host 를 보낼 수 있어 둘이 같아야 받게 했다.
3. **XFCC:** 클라이언트 인증서의 SAN 이 `gateway`(입구)인 요청에서만 서비스에 넘기고 그 밖의 요청에서는 지운다(`@not_ingress not expression {http.request.tls.client.san.dns_names.0} == "gateway"` 에 `request_header -X-Forwarded-Client-Cert`). 이웃 영역(같은 CA 의 인증서)이나 입구를 거치지 않은 호출이 위조한 기기 신원이 서비스에 닿지 않는다. 입구 쪽 SANITIZE_SET(ADR 0003)과 겹치는 두 겹이다.
4. **영역 안 감시:** `/healthz`·`/readyz`·`/metrics` 셋만 TLS 와 별개의 평문 포트 9100(`area_gateway.MONITOR_PORT`)으로 서비스에 이어 주고 나머지는 404 이다. backend 내부 네트워크에서만 닿고 입구는 이 포트로 라우트를 만들지 않는다(입구는 이 세 경로를 404 로 막는다, D129). `monitoring.py` 의 영역 대상이 `<서비스>:9100` 이고 `prometheus.yml` 의 `openit-areas` 는 `scheme: http` 이다.
5. **건강 확인:** 인증서와 키 파일이 비어 있지 않은지 본다(`area_gateway.healthcheck_command`, compose `CMD-SHELL`).
6. **스트림:** `reverse_proxy` 에 `flush_interval -1`(알림 스트림 `text/event-stream` 을 버퍼 없이 흘린다). 응답 시간 제한을 Caddy 가 걸지 않는다.

시험: 단위 시험(`tests/unit/test_area_gateway.py`: 템플릿의 환경 변수·경로·포트가 코드의 값과 같다), 샌드박스(`tests/scenario`: 앞에 가짜 평문 상류를 두고 실제 영역 게이트웨이 넷을 띄워 입구→게이트웨이→상류, XFCC 위조 거절, 클라이언트 인증서 없는 호출 거절, SNI·Host 불일치 거절, 평문 감시 포트).

## 왜
- **영역마다 하나(서비스에 안 넣기):** 서비스가 TLS 를 끝내면 서비스마다 ACME·mTLS 구현이 생긴다. 게이트웨이는 이미지 하나(digest 고정 caddy)와 설정 파일 하나로 같다. 서비스는 평문 HTTP 로 단순해지고 계약 9.0.0 이 정한 방침이다.
- **Caddy:** 입구 에이전트와 레지스트리가 쓰는 같은 이미지·같은 ACME 설정이라 갱신 방식이 하나다(ADR 0014). 클라이언트 인증서 검증(`client_auth`)과 XFCC 규칙을 한 파일에 쓸 수 있다.
- **파일로 건강 확인:** 클라이언트 인증서 없는 TLS 접속은 거절되고, 인증서 검증을 끄고 두드리는 것은 규칙에 어긋난다. 관리 API(`admin off`)는 끈다. 파일이 있으면 사설 CA 에서 받았다는 뜻이다(입구 에이전트와 같은 판정).
- **평문 감시 포트와 고정 9100:** TLS 포트는 클라이언트 인증서를 요구해 Prometheus 가 인증서 없이 긁을 수 없다. 긁는 쪽에 영역마다 클라이언트 인증서를 주는 것은 감시가 영역의 비밀을 갖게 한다. backend 는 내부 네트워크라 밖에서 닿지 않는다(`internal: true`). 값 9100 은 Prometheus 계열 exporter 가 쓰는 포트 대역이고 TLS 포트(기본 8443)와 80 번과 겹치지 않는다. 계약에 없는 platform 내부 값이라(영역 사이 값이 아니다) 환경 입력으로 받지 않는다. 측정한 값이 아니다.
- **TLS 포트 기본 8443(`OPENIT_SERVICE_PORT`, 계약의 선택 입력):** 비 root 로 1024 이상이어야 하고 HTTPS 대체 포트로 널리 쓴다. 측정한 값이 아니다.
- **http-01:** tls-alpn-01 은 443 번(RFC 8737 3)이어야 하고 게이트웨이는 443 을 열지 않는다. http-01 은 80 번이라 `NET_BIND_SERVICE` 하나가 필요하다(입구 에이전트와 같은 이유).

## 검토한 대안과 버리는 이유
- **서비스가 직접 TLS 를 끝내기(8.0.0 의 가정):** 서비스마다 ACME·mTLS 구현이 생긴다. 서비스 틀은 이미 평문 HTTP 다(survey-service-006).
- **영역마다 Envoy:** Envoy 에는 ACME 클라이언트가 없어 에이전트가 따로 필요하다(ADR 0002). Caddy 는 둘을 한 프로세스가 한다.
- **게이트웨이 하나로 모든 영역(입구 Envoy 가 평문으로 서비스에 접속):** 영역 사이 호출(`area_mtls`)과 영역 안 평문의 경계가 없어진다. 계약이 영역마다 게이트웨이를 정했다(D127).
- **감시를 TLS 포트로, 클라이언트 인증서를 감시에 발급:** 위 '왜'.
- **XFCC 를 서비스가 검증:** 서비스가 출처를 확인할 수단이 영역 네트워크 구성 밖에 없다(계약 9.0.0).

## 결과
- **얻는 것:** 서비스는 평문 HTTP 만 안다. TLS·인증서 갱신·클라이언트 인증서 검증·XFCC 정리가 한 설정에 있다. 입구가 서비스에 보인 인증서 이름(SAN `gateway`)으로만 기기 신원이 넘어간다.
- **감수하는 것:**
  - 서비스와 게이트웨이 사이는 평문이다. 영역 전용 내부 네트워크에 게이트웨이와 서비스만 있어야 한다는 배치에 기댄다(deploy 의 compose 책임).
  - 게이트웨이 컨테이너가 서비스 수만큼 늘고 80 번을 위한 `NET_BIND_SERVICE` 를 가진다.
  - 키 파일은 게이트웨이 uid 가 0600 으로 쓴다. 서비스가 읽으려면 같은 uid 이거나 볼륨 소유를 맞춘다(deploy 가 정한다).
  - 감시 포트는 평문이라 backend 의 다른 컨테이너도 `/healthz`·`/readyz`·`/metrics` 를 읽는다(영역 안에서만 닿는 경로로 계약이 정했다).
  - 샌드박스의 상류는 가짜 평문 에코다. 실제 서비스 이미지와의 종단 시험은 E2E 의 몫이다(이 작업에서 하지 않았다).
  - 이 환경에서 `caddy adapt` 와 샌드박스에서 게이트웨이가 동작함을 확인했다. `/area-certs` 를 서비스 컨테이너가 같은 uid 로 읽는 구성은 deploy 가 만든 뒤에야 확인된다.

## 되돌리는 조건
서비스가 TLS 를 직접 끝내기로 계약이 바뀌거나(9.0.0 의 결정 (a) 변경), 영역 전용 내부 네트워크가 평문을 지킬 수 없는 배치가 되면 게이트웨이를 없애거나 서비스 안으로 옮긴다.
