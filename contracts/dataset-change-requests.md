# 데이터셋에 필요한 변경

LoRA-A·LoRA-B 의 입출력은 데이터셋 정의(D74)가 정본이고 계약은 그 사본이다. 계약의 해당 부분은 학습 서버의 `~/dataset/docs/labels.py`(2026-11-10 서버 판이 로컬 사본과 같음)와 학습 파일 `lora_a_train.jsonl`, `lora_b_train.jsonl`에서 키 이름과 값을 글자까지 맞췄다. 아래는 v7 의 사용자 결정 때문에 계약에 넣었지만 데이터셋에는 아직 없는 것이다. 데이터셋 담당이 반영하기 전에는 모델이 이 값을 학습하지 못한 상태다.

| 번호 | 무엇을 | 왜 | 근거 |
|---|---|---|---|
| DC-01 | LoRA-A 입력(`ActionExtractionInput`)에 선택 칸 `confirming`을 더한다. 형식은 `state` 와 같은 표(칸 키에서 `{value, status}`)이며 환자에게 맞는지 확인 중인 칸과 그 값을 담는다. 확인 중이 아닌 턴에는 없다 | 직전에 CONFIRM 으로 확인을 물었다면 환자의 "네"·"아니요"가 어느 값에 대한 답인지 모델이 알아야 한다. 지금 입력에는 확인 중인 칸을 가리키는 칸이 없다(`current_question` 글에만 있다) | 사용자 결정 2026-11-10(확인 중 상태, 곧 무엇과 무엇을 확인하는지를 LoRA-A 입력에 담는다) |
| DC-02 | `reason` 에 `MEANING_ASKED`(환자가 질문의 뜻이나 대상을 물음)를 더한다. 이 사유의 action 과 학습 행(A 와 B 모두)을 정의한다. 현재 `ASK_PURPOSE`(왜 묻는지)는 REDIRECT 이고 질문의 뜻·대상을 묻는 말은 별도 분류가 없다 | 뜻을 묻는 되물음은 되묻기 한도에 세지 않는다. 서비스가 이것을 세지 않으려면 모델이 이 분류를 내야 한다. 같은 문항에서 3번 이어지면 직원 도움을 안내한다 | 사용자 결정 2026-11-10(질문의 뜻·대상을 물음은 한도에 세지 않고 설명 요청 3번 이어지면 직원 도움 안내) |
| DC-03 | `reason` 에 `REASK_LIMIT`(되묻기 한도에 닿아 건너뜀)를 더한다. 서비스가 SKIP 을 합성할 때 LoRA-B 입력(`reason`, `hold`, `next`)과 정답 문장 학습 행을 정의한다. 지금은 SKIP 의 사유가 `REQUEST_SKIP` 과 `REFUSED` 뿐이다 | 한도로 건너뛰는 것은 환자가 넘어가자고 한 것(`REQUEST_SKIP`)이나 거절한 것(`REFUSED`)과 다르다. 결과에도 이 원인이 남는다(`BlankReason.REASK_LIMIT`). 한도는 처음 질문 1회에 되묻기 2회로 정해졌다 | 사용자 결정 2026-11-10(한도로 인한 건너뛰기 사유, 되묻기 한도), U100 |
| DC-04 | 한 문항에서 설명 요청만 3번 이어졌을 때 환자에게 직원 도움을 안내하는 문장을 누가 만드는지 정한다. LoRA-B 가 만든다면 그 입력 표현(예: `action`, `reason`)과 학습 행을 정의한다. 서비스의 고정 문장으로 한다면 데이터셋은 변경이 없다 | 계약은 `TurnResponse.staff_help_notice` 로 안내 여부만 알리고 문장 출처를 정하지 않았다. 데이터셋에는 직원 도움을 안내하는 응답이 없다 | 사용자 결정 2026-11-10(설명 요청 3번 이어지면 직원 도움 안내) |
