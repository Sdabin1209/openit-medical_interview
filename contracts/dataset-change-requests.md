# 데이터셋에 필요한 변경

LoRA-A·LoRA-B 의 입출력은 데이터셋 정의(D74)가 정본이고 계약의 모델 입출력 v2(`model-io-v2`)는 그 사본이다. 사본은 학습 서버의 `~/dataset/docs/labels.py` 와 학습 파일(`final/`, `finaltest/`)에서 키 이름과 값을 글자까지 맞췄다. 아래는 데이터셋에 있어야 할 변경과 확인이다. 상태가 "v3"인 것은 `model-io-v3-proposal.md` 에 속하며 지금의 모델 입출력 v2 에는 넣지 않는다.

| 번호 | 상태 | 무엇을 | 왜 | 근거 |
|---|---|---|---|---|
| DC-01 | v3 | LoRA-A 입력에 선택 칸 `confirming`을 더한다. 형식은 `state` 와 같은 표(칸 키에서 `{value, status}`)이며 환자에게 맞는지 확인 중인 칸과 그 값을 담는다 | 직전에 CONFIRM 으로 확인을 물었다면 환자의 "네"·"아니요"가 어느 값에 대한 답인지 모델이 알아야 한다. 지금 입력에는 확인 중인 칸을 가리키는 칸이 없다 | 사용자 결정 2026-11-10(확인 중 상태를 LoRA-A 입력에 담는다) |
| DC-02 | v3 | `reason` 에 `MEANING_ASKED`(환자가 질문의 뜻이나 대상을 물음)를 더하고, 이 사유의 action 과 학습 행(A 와 B)을 정의한다. `ASK_PURPOSE`(왜 묻는지, REDIRECT)와는 다른 분류다 | 뜻을 묻는 되물음을 되묻기 한도에 세지 않으려면 모델이 이 분류를 내야 한다. 모델 입출력 v2 에서는 이 기능이 꺼져 있다 | 사용자 결정 2026-11-10(질문의 뜻·대상을 물음은 한도에 세지 않고 설명 요청 3번 이어지면 직원 도움 안내) |
| DC-03 | 닫음 | 변경 없음. 되묻기 한도로 건너뛸 때 서비스가 고정 안내 문장을 쓰고 LoRA-B 를 부르지 않는다. 결과의 빈칸 원인(`BlankReason.REASK_LIMIT`)은 서비스 값이다 | 모델이 내지 않는 사유를 모델 입력에 보내지 않는다 | 사용자 결정 U36 2026-11-10, 구조 규칙 11 |
| DC-04 | 닫음 | 변경 없음. 직원 도움 안내 문장은 서비스의 고정 문장이다 | 안전과 닿는 안내는 서비스가 쓴다 | 구조 규칙 11 |
| DC-05 | 확인 | 학습 데이터의 LoRA-A 입력 `state` 항목 안의 키 순서를 하나로 맞춘다. 실측은 `value` 다음 `status` 가 90,416개, `status` 다음 `value` 가 4,215개다 | 입력 글자가 학습 글자와 같아야 하는데(D77) 학습 데이터 안에서 글자가 갈린다 | D77, 실측 학습 파일 |
| DC-06 | 확인 | 학습 데이터의 LoRA-B 입력에서 정렬되지 않은 행을 맞춘다. 실측은 최상위 키 순서가 `action, topic, user_utterance, known, next` 인 행 10개와 `next` 의 키 순서가 `type, question_id, text` 인 행 10개다 | LoRA-B 입력은 모든 수준을 정렬해 직렬화한다는 규칙(D77)과 다르다 | D77, 실측 학습 파일 |
| DC-07 | 확인 | (1) 발화 한 턴의 상한은 300자인데 학습 발화 최대가 140자라 141~300자는 학습 분포 밖이다. 긴 발화의 학습 행이 필요한지 정한다. (2) 문진 끝 재질문 단계의 합성 REASK(빈칸 문항의 마지막 질문과 환자 답)가 실제 LoRA-B 에서 자연스러운 문장을 내는지 GPU 로 확인한다 | 상한이 학습 분포보다 넓다. 합성 REASK 는 GPU 확인이 남은 항목이다 | 사용자 결정 2026-11-10(발화 상한 300자), U100 |
| DC-08 | 확인 | 학습 서버의 `final/`(6개)과 `finaltest/`(2개)는 모두 split 값이 `test` 인 평가 파일이 둘이다. 계약은 `DatasetFileSet`(final, finaltest)으로 구분하는데 두 묶음의 이름과 쓰임이 맞는지 확인한다 | 같은 역할의 test 파일이 둘이라 한 데이터셋 버전으로 게시하려면 구분이 필요하다 | 실측 학습 서버 파일, F18 |
| DC-09 | 확인 | (DC-05 를 파일별로 좁힌 것) 평가 파일 `finaltest` 의 LoRA-A 입력 `state` 항목 안의 키 순서를 학습 파일 `final` 과 같은 `value`, `status` 순서로 맞춘다. 실측은 `final` 의 항목 90,416개가 모두 `value`, `status` 순서이고 `finaltest` 2092행 중 state 가 있는 2000행의 항목 4,215개가 `status`, `value` 순서다(DC-05 의 `status` 다음 `value` 4,215개가 `finaltest` 의 것이다) | 서빙은 `labels.py a_state` 와 `final` 의 순서(`value`, `status`)로 입력을 만든다(계약 `StateEntryKeyOrder`). 평가 입력 글자가 서빙 글자와 다르면 평가가 서빙을 대표하지 못한다(D77) | model-runtime 변경 요청 001 2절(측정), D77 |
| DC-10 | 확인 | (DC-06 의 `action, topic, ...` 순서 행 10개를 행 단위로 특정한 것) 학습 파일 LoRA-B 입력 중 정렬되지 않은 10행을 정렬한다. 학습 4행·3행과 시험 3행이고, 모두 action 이 NEXT 이며 `known` 이 "1년 기준", "일주일 기준", "한 달 기준" 인 Q7 기준 기간 행이다. 최상위 키 순서가 `action, topic, user_utterance, known, next` 로 들어 있다 | 계약은 B 입력을 모든 수준 문자 순으로 정렬해 직렬화하고 서빙도 그렇게 한다. 학습 글자와 서빙 글자가 이 10행에서 다르다(D77). 요청이 아니라 알림에 가깝다: 이 10행 때문에 서빙을 바꾸지 않는다 | model-runtime 변경 요청 001 3절(측정), D77 |
