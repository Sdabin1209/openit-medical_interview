# 0007. 프로파일 표와 기반 모델

## 상태
승인(2026-11-11, model-runtime 영역 작업자). 변경 요청 model-runtime-003 의 6번에 대한 헤드 결정(계약 9.0.0: 프로파일 표는 영역 안의 값이고 영역이 소유한다)을 영역에 맞춘다. 8.0.0 의 임시 선택('받아서 읽기만 한다. 엔진 기반 모델은 엔진 컨테이너 설정이 정한다')을 대체한다.

## 맥락
`OPENIT_MODEL_PROFILE`(GPU 크기별 이름)이 가리키는 표(기반 모델, 서빙 크기)의 정본이 없었다. vLLM 은 시작할 때 `--model` 로 정한 기반 모델 하나를 서빙하고 런타임에 바꿀 수 없다(어댑터만 런타임에 올린다). 그래서 이 서비스가 엔진에 기반 모델을 '알리는' 길은 없다.

## 결정
- **표의 위치와 모양:** 영역 안 파일 `src/model_runtime/profiles.json`(패키지와 함께 배포). 모양은 `{"profiles": {"<이름>": {"base_model": "<모델 허브 식별자>"}}}` 이고 `store/profiles.py` 의 pydantic 모델이 읽는다(알 수 없는 칸은 거부, `base_model` 은 계약 `BaseModelName`).
- **값:** `gpu-12g` → `Qwen/Qwen3-1.7B`, `rtx4090-24g` → `Qwen/Qwen3-8B`. 출처는 `contracts/inputs/DECISIONS.md` 의 D81(프로파일별 기반 모델)이다.
- **쓰임 둘:** (1) 활성화·적재할 패키지의 `base_model` 이 프로파일의 기반 모델과 다르면 적재하지 않는다(422 `PACKAGE_INVALID`). D74(3)·D81 이 '어댑터와 프로파일의 기반 모델이 다르면 적재를 거부한다'고 정했다. (2) `/readyz` 의 `engine` 점검이 엔진의 `GET /v1/models`(OpenAI 호환 표준)에 프로파일의 기반 모델이 있는지 본다. 없으면 엔진이 다른 모델로 떠 있는 것이라 준비되지 않았다.
- 알 수 없는 프로파일 이름은 시작할 때 오류로 멈춘다(설정 오류).
- **서빙 크기는 표에 넣지 않았다.** 최대 길이·동시 시퀀스 같은 값은 엔진 시작 인자이고 GPU 에서 잰 값이 없다. 값을 지어내지 않고, 잰 값이 생기면 `ModelProfile` 에 칸을 더한다(미측정).

## 왜
- 영역이 자기 값을 소유한다(구조 규칙 4·5). deploy 가 이 표를 읽으면 영역 내부 구조를 아는 것이라 하지 않는다.
- 엔진에 알릴 수 없으니 '확인'이 표준적이고 단순한 쪽이다. `GET /v1/models` 는 OpenAI 호환 API 의 표준 엔드포인트다.
- 어댑터는 학습한 기반 모델에만 맞는다. 다른 기반 모델에 올리면 엔진이 거절하거나(차원 불일치) 조용히 이상한 출력을 낸다. 적재 전에 막는 것이 안전하다.

## 검토한 대안과 버리는 이유
- **설정 파일을 환경 변수 경로로 받기:** 계약 Env 에 입력이 없다. 새 입력은 계약 변경이다. 버린다.
- **표를 계약에 싣기:** 계약이 영역 소유로 정했다. 버린다.
- **엔진에 기반 모델을 알리기:** vLLM 이 런타임에 기반 모델을 바꾸지 못한다. 버린다.

## 결과
- 얻는 것: 잘못된 기반 모델의 패키지·엔진을 적재 전·준비 확인에서 드러낸다. 값의 출처가 문서에 있다.
- 감수하는 것: **엔진 컨테이너를 `--model <프로파일의 기반 모델>` 로 띄우고 `--served-model-name` 으로 바꾸지 않아야** 준비 확인이 통과한다(deploy 가 맞춘다). 프로파일이 늘면 표 파일을 고친다. 이 확인을 실제 vLLM 으로는 하지 못했다(가짜 엔진으로 확인).

## 되돌리는 조건
계약이 프로파일 표를 영역 밖 입력(파일)으로 받게 하거나, 엔진이 런타임에 기반 모델을 바꿀 수 있게 되면 대체한다.
