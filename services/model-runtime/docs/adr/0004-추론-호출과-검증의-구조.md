# 0004. 추론 호출과 검증의 구조

## 상태
승인(2026-11-10, model-runtime 영역 작업자).

## 결정
- **컴포넌트는 포트(Protocol)만 안다.** 레지스트리, 추론 엔진, 활성화 기록 저장소는 `types.py` 의 포트이고 구현은 `link/`, `store/` 다. 컴포넌트가 통신 라이브러리를 import 하지 못하게 import-linter 가 막는다(ADR 0003).
- **적재와 호출 순서는 `link/runtime.py` 가 정한다.** 판단은 컴포넌트가 한다.
- **재호출 없음.** 추출 출력이 합격 조건을 끝내 지키지 못하면 같은 요청을 다시 보내지 않고 503 `OUTPUT_INVALID` 를 낸다. 시간 상한이 20초이고 서빙 설정의 기본 온도가 0 이라 다시 불러도 같은 출력이 나올 가능성이 크다(측정하지 않았다). 재시도는 호출자(Retry-After)가 정한다.
- **시간 상한은 계약 값이다:** 추출 20초, 응답 25초(D125). 넘기면 503 `DEADLINE_EXCEEDED`. 엔진 실패는 원인(주소 등)을 싣지 않고 503.
- **적재는 요청 밖의 작업이다.** 활성화는 매니페스트·목록표 검증(404, 422)만 요청 안에서 하고 202 로 돌려준다. 적재 중에도 이전 패키지가 계속 쓰인다. 실패하면 이전 패키지를 유지하고 상태만 `FAILED` 로 둔다(D46). 한 번에 하나의 적재만 한다(다른 패키지 적재 중이면 409).
- **엔진에 남기는 어댑터는 두 패키지(활성과 직전)** 까지다. 롤백이 빠르고 어댑터가 쌓이지 않는다. 값은 측정하지 않았다.
- **추출 응답의 값은 모델이 낸 JSON 값 그대로** 낸다(3 이 3.0 으로 바뀌지 않게). 응답 본문은 계약 모델로 검증한 값이 아니라 `output_guard` 가 검증을 마친 값이다.
- **`/readyz`** 는 저장 폴더가 쓸 수 있는지와 엔진이 살아 있는지를 본다. 모델 적재 여부는 보지 않는다(처음 설치에는 활성 패키지가 없고 활성화 호출을 받으려면 서버가 준비되어야 한다). 적재 여부는 `getModelStatus` 와 요청별 503 `MODEL_NOT_LOADED` 가 말한다.
- **지표:** 계약 필수 `model_call_duration_seconds{op}`(히스토그램, 구간은 목표 p95 2초와 상한 20·25초 사이를 두루 보는 값이고 측정하지 않았다)와 위반 코드별·고쳐 쓰기별·출력 불가 수.

## 왜
D104(컴포넌트는 자기 입출력만 안다), R7(낸 쪽이 한 번만 검증), D75(실패는 값을 지어내지 않는다), D46(적재를 거부하면 이전 패키지 유지), D125(시간 상한).

## 되돌리는 조건
GPU 에서 측정해 재호출이 위반을 줄이는 것이 확인되면 새 ADR 로 한 번 재호출을 둔다(시간 상한 안에서).
