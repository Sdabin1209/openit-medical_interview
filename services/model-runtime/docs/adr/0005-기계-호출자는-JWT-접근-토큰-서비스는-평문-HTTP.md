# 0005. 기계 호출자는 JWT 접근 토큰, 서비스는 평문 HTTP

## 상태
승인(2026-11-11, model-runtime 영역 작업자). 계약 9.0.0(변경 요청 platform-002, model-runtime-003 7번, survey-service-006)이 정한 것을 영역에 맞춘다. [ADR 0003](0003-레지스트리-패키지-형식-HTTP-클라이언트-TLS.md) 의 7항(영역 사이 TLS)과 8항의 기계 토큰 부분을 **대체한다**(Supersedes). 0003 의 나머지(ORAS, 기본 인증, 패키지 파일 형식, httpx2, openai SDK)는 그대로다.

## 맥락
- 8.0.0 에서는 서비스가 `OPENIT_LISTEN_PORT` 에서 TLS 를 끝내고 클라이언트 인증서를 요구했고, survey-service 는 파일에 든 고정 문자열 토큰으로 인증했다. 컨테이너 건강 확인은 루프백 18081 의 별도 서버가 맡았다.
- 9.0.0 은 TLS 를 영역 게이트웨이(Caddy)가 끝내고 서비스는 영역 전용 내부 네트워크에서 평문 HTTP 를 듣는다고 정했다. 기계 호출자는 Keycloak client credentials(RFC 6749 4.4)로 받은 JWT 접근 토큰(RFC 9068)을 쓴다. 호출자 표(`MachineTokenTable`)에는 비밀이 없다(`client_secret_file` 은 호출자가 읽는 경로).

## 결정
1. **TLS 를 끝내지 않는다.** `serve.py` 는 uvicorn 하나로 `0.0.0.0:OPENIT_LISTEN_PORT` 를 평문으로 듣는다. 루프백 18081 서버와 TLS 인자를 없앴다. `HEALTHCHECK` 는 그 포트의 `/healthz` 를 본다(포트는 환경 입력이라 `os.environ` 에서 읽고 `EXPOSE` 는 두지 않는다).
2. **사람과 기계가 같은 검증기를 지난다.** `OidcVerifier.verify` 가 서명(JWKS)·`iss`·`aud`·`exp`·필수 클레임·`typ`·알고리즘을 확인한다(RFC 9068 4). 그 뒤 `client_id` 가 `machine-` 로 시작하면 기계 호출자로 본다(계약 `MachineOidcClientId`).
3. **기계 토큰은 계약 `MachineIdentityClaims` 가 클레임을 그대로 검증한다.** platform 이 Keycloak 기계 클라이언트의 범위를 제한해 토큰의 `realm_access.roles` 에 계약 `MachineRole` 만 실린다(변경 요청 model-runtime-006 에 대한 헤드 결정). 계약 밖 역할이 실리거나 모양이 틀리면 모델이 거절하고 401 이다(역할을 걸러 내는 코드는 없다).
4. **호출자 표는 허용 목록으로 쓴다.** `client_id`(`machine-<이름>`)로 호출자를 찾고, **토큰의 역할과 표의 허용이 모두 있는 역할**만 인정한다. 표에 없거나 역할이 모자라면 403(인증은 됐으나 권한이 없다). 표의 `client_secret_file` 은 읽지 않는다(토큰을 받을 쪽의 비밀이다).
5. 기계 토큰을 사람 전용 작업(활성화 등)에 쓰면 403 이다. 8.0.0 의 고정 문자열 토큰은 받지 않는다(JWT 가 아니면 401).
6. 영역 안에서 이웃을 부르는 클라이언트 인증서(`OPENIT_TLS_CERTIFICATE_FILE`·`KEY`)는 레지스트리 클라이언트(`link_registry`)가 받아 쓴다([ADR 0006](0006-계약-9.0.0-입력-엔진-주소-이름-표-자격-어댑터-배치.md)).

## 왜
- **표준:** RFC 6749 4.4(client credentials), RFC 9068(접근 토큰 JWT 프로파일), RFC 7517(JWKS), RFC 6750(bearer). 헤드가 정한 방침(platform-002)이다.
- 두 번 검증 코드를 두지 않는다(D117: 같은 뜻은 한 번만 정의). 사람과 기계는 `client_id` 접두어만 다르다.
- 호출자 표를 허용 목록으로 쓰는 것은 계약 설명('client_id 로 호출자를 찾고 역할 허용을 확인')과 맞다. IdP 설정이 어긋나 표 밖의 호출자가 역할을 받아도 이 서비스는 들이지 않는다(최소 권한을 두 곳에서 확인).
- 평문 HTTP: 서버 쪽 TLS 와 클라이언트 인증서 검증은 영역 게이트웨이가 한다(계약 `area_mtls` 설명). 서비스가 다시 끝내면 인증서 갱신 때 재시작이 필요하고 게이트웨이와 책임이 겹친다.

## 검토한 대안과 버리는 이유
- **토큰의 역할만 믿기(표를 안 읽기):** 표의 허용 목록 역할이 사라지고 IdP 설정 오류가 곧 권한 오류가 된다. 버린다.
- **표의 역할만 믿기(토큰 역할 무시):** 토큰이 가진 권한의 정본은 IdP 이고 platform 이 표로 그 역할을 만든다. 둘이 어긋나면 안전한 쪽(교집합)이 낫다.
- **서비스가 계속 TLS 를 끝내기:** 계약 9.0.0 이 게이트웨이로 정했다. 버린다.
- **계약 밖 역할을 걸러 낸 뒤 검증:** Keycloak 기본 역할이 실려도 통과시키지만, 토큰 범위를 제한하는 쪽(platform)이 정해졌으므로 코드에 두 번째 방어를 두지 않는다(모델 하나로 검증, D117). [변경 요청 model-runtime-006](../../../../docs/change-requests/model-runtime-006.md) 처리됨.

## 결과
- 얻는 것: 고정 비밀이 사라진다(발급·회전은 Keycloak). 사람과 기계의 검증이 하나다. 건강 확인에 인증서가 필요 없다.
- 감수하는 것: 서비스는 게이트웨이를 믿는다(네트워크 구성으로 게이트웨이만 닿는다). 호출 때마다 JWKS 서명 검증을 한다(공개 키는 캐시하고 알 수 없는 `kid` 일 때만 30초 간격으로 갱신, 측정하지 않은 값). **실제 Keycloak 으로는 확인하지 못했다**(시험용 신원 공급자로 확인했다). platform 의 범위 제한이 실제로 적용되어 기본 역할이 빠지는지는 platform 쪽 확인이 필요하다. 빠지지 않으면 기계 호출이 모두 401 이 된다.

## 되돌리는 조건
계약이 서비스의 직접 TLS 종단을 다시 요구하거나, 게이트웨이를 거치지 않는 호출 경로가 생기면 이 ADR 을 대체한다.
