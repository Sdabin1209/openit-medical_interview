# 0008. 게시된 모델 패키지 목록(listModelPackages)

## 상태
승인(2026-11-11, model-runtime 영역 작업자). 변경 요청 admin-console-002 에 대한 헤드 결정(계약 9.0.0 `GET /v1/model-packages`)을 구현한다.
(2026-11-11 보강: 기본 설치 이름에서 목록이 비는 결함은 [ADR 0011](0011-저장소-경로는-레지스트리-이름과-따로-ORAS-Container-로-만든다.md)이 고쳤다.)

## 맥락
승인자는 활성화 전에 레지스트리에 게시된 패키지를 골라야 한다. 계약은 `ModelPackageList`(최근 것이 먼저, `Limit`·`Cursor`, 항목마다 digest·게시한 때(알 수 있을 때)·활성 여부)를 정했다. OCI Distribution Spec 에서 저장소의 항목을 나열하는 표준 길은 태그 목록(`GET /v2/<이름>/tags/list`)이고, 태그 없이 digest 로만 올린 매니페스트는 나열되지 않는다.

## 결정
- **게시 도구가 패키지마다 태그를 단다.** `package-publish` 가 매니페스트를 digest 로 올린 뒤 같은 바이트를 태그 `sha256-<16진수 64자>`(digest 의 콜론을 줄표로 바꾼 이름)로도 올린다. 태그는 digest 에서 정해지므로 다른 매니페스트를 가리킬 수 없다.
- **`link_registry.list_manifests`** 는 `tags/list` 를 `n=100` 으로 받고 `Link: rel="next"` 를 따라가 모든 태그를 모은 뒤 위 형식의 태그만 골라 매니페스트를 받는다(다른 태그는 건너뜀). 매니페스트 digest 는 받은 바이트의 sha256 이다. 저장소가 없으면(404) 빈 목록, 닿지 못하거나 인증이 거절되면 `RegistryUnavailableError` → 503(계약의 기존 응답, 새 사유 없음).
- **`package_catalog` 컴포넌트**가 목록을 만든다. 정렬 기준은 목록표(config)의 `created_at`(큰 것이 먼저, 같으면 digest 큰 것이 먼저)이다. 계약 매니페스트에는 주석(annotations)이 없어 게시 시각이 없으므로 `published_at` 은 싣지 않는다(계약: 주석이 있으면 그 값, 없으면 없다). 계약과 다른 항목은 건너뛴다.
- **쪽 나누기:** `Limit`(기본 30, 최대 100)과 `Cursor` 는 계약 모델(`PageLimit`, `PageCursor`)로 확인한다. 커서는 마지막으로 준 패키지의 digest(32바이트, base64url 43자)이고 불투명 값이다. 목록을 요청마다 새로 정렬해 그 digest 다음부터 준다. 커서가 가리키는 패키지가 없으면 400.
- **활성 여부**는 `release` 의 상태(`ModelStatus.package_digest`, 활성화 기록에서 구한다)와 대조한다.
- 권한은 계약대로 사람 토큰의 `operator` 또는 `release-approver` 다.

## 왜
- OCI Distribution Spec 의 `tags/list`(쪽 나누기는 `n`·`last` 와 `Link` 머리글)가 나열의 표준이다. 레지스트리가 별도 카탈로그 API(`/v2/_catalog`)를 주는 것은 저장소 목록이지 저장소 안 항목이 아니다.
- digest 를 커서로 쓰면 목록 사이에 게시가 있어도 위치가 어긋나지 않고 서버가 상태를 쥐지 않는다.
- `created_at` 을 읽으려면 패키지마다 config 파일 하나를 받아야 한다. 패키지는 digest 로 불변이라 읽은 값을 기억한다(프로세스 안 메모리).

## 검토한 대안과 버리는 이유
- **레지스트리 referrers/카탈로그 API:** 레지스트리 구현마다 지원이 다르고 계약이 정한 태그 목록·매니페스트 조회가 아니다. 버린다.
- **활성화 기록(release log)만으로 목록 만들기:** 아직 활성화하지 않은 후보가 빠진다. 목록의 목적(승인 대기를 찾기)에 어긋난다.
- **정렬 없이 태그 사전순:** '최근 것이 먼저'라는 계약 설명을 못 지킨다.
- **config 를 받지 않고 태그 사전순 + 게시 시각 생략:** 위와 같은 이유로 버린다.

## 결과
- 얻는 것: 승인자가 digest 를 직접 입력하지 않는다. 표준 API 만 쓴다.
- 감수하는 것: 목록을 처음 만들 때 패키지 수만큼 요청이 나간다(패키지가 수십 개라는 가정이고 측정하지 않았다). `n=100` 도 측정한 값이 아니다. **이 변경 전에 게시한 패키지는 태그가 없어 목록에 나오지 않는다**(같은 바이트를 태그로 다시 올리면 된다. deploy 의 기존 패키지가 있으면 헤드가 판단한다). 실제 레지스트리(Distribution + Caddy)로는 확인하지 못했다(시험용 레지스트리가 태그 목록과 쪽 나누기를 흉내 낸다).

## 되돌리는 조건
계약이 매니페스트에 게시 시각 주석을 허용하면 `published_at` 을 싣고 정렬 기준도 그 값으로 바꾼다(config 를 받지 않아도 된다). 패키지가 수백 개가 되면 캐시를 영속화하거나 색인을 둔다.
