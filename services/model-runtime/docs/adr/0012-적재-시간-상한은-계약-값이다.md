# 0012. 모델 적재의 시간 상한은 계약 값이다

## 상태
승인(2026-11-11, model-runtime 작업자). 계약 9.1.0(`TimeBudgetTable.model_load`, 변경 요청 model-runtime-007)을 구현한다.

## 맥락
활성화 요청을 받은 뒤 패키지를 받고 어댑터를 엔진에 올리는 적재에는 상한이 없었다. 레지스트리나 엔진이 멈추면 상태가 LOADING 으로 남고 승인자는 끝이 없는 기다림을 본다. 계약이 사람 화면 쪽 기다림(190초, D125)과 맞는 상한을 정했다.

## 결정
- `link/runtime.py` 의 `LOAD_LIMIT_SECONDS = 180` 은 계약 `ModelLoadLimitSeconds` 의 값이다(추출 20초·응답 25초 상수와 같은 방식으로 계약 값을 상수로 둔다).
- 받기·검증·어댑터 올리기(`inspect_package`, `load_package`)를 `asyncio.timeout` 으로 감싼다. 넘기면 적재는 FAILED 로 끝나고 이전 패키지를 유지한다(D46). 실패 기록(`LOAD_FAILED`)의 사유는 `적재가 180초 안에 끝나지 않았다` 다. `load_package` 는 취소되면 이미 올린 어댑터를 내린다.
- 기록 쓰기(`release.loaded`)는 감싸지 않는다. 중간에 끊기면 활성화 기록과 메모리 상태가 어긋난다.
- 롤백과 시작 때의 복원 적재도 같은 상한이다(`_load` 한 곳).

## 왜
- 계약이 상한을 정하면 서버가 그 안에 끝나지 않을 때 실패를 선언해야 호출자의 기다림에 끝이 생긴다(D125: 안쪽 상한이 바깥보다 짧다).
- 값은 계약이 정한 것이다. 계약 값은 측정하지 않았다(계약 `x-basis`).

## 검토한 대안과 버리는 이유
- **상한 없이 호출자가 기다림을 끊는다:** 서버에 적재가 계속 남아 나중에 READY 가 되면 호출자가 실패로 본 패키지가 활성이 된다.
- **기록 쓰기까지 감싼다:** 위와 같은 이유로 버린다.

## 결과
- 얻는 것: 멈춘 적재가 FAILED 로 끝나고 이전 패키지가 계속 추론한다.
- 감수하는 것: 매우 큰 패키지나 느린 망에서 180초를 넘으면 실패한다(측정하지 않았다). 시험은 시간을 재지 않고 상한을 0 으로 바꿔 상한에 닿는 경로를 확인한다(실제 180초 경과는 시험하지 않는다).

## 되돌리는 조건
실제 서버에서 적재 시간을 재어 계약 값을 바꾸면(변경 요청) 이 상수를 따라 바꾼다.
