# 0002. 활성화·롤백 기록은 덧붙이는 파일 하나

## 상태
승인(2026-11-10, model-runtime 영역 작업자). 브리프가 저장 방식을 ADR 로 정하라고 했다.

## 맥락
활성 패키지 포인터와 활성화·롤백 기록(승인자, 시각, 사유)을 어디에 둘지 정해야 한다. 계약 `ModelRuntimeEnv` 에는 데이터베이스 연결 입력이 없고, 유지되는 폴더(`OPENIT_MODEL_CACHE_DIR`)만 있다. 설계 문서의 영역 목록에도 model-runtime 의 DB 가 없다.

## 결정
- 유지되는 폴더 안 `model-runtime/release-log.jsonl` 한 파일에 JSON Lines 로 덧붙인다(기록 하나 = 한 줄: 종류, 패키지 digest, 시각, 요청한 사람, 사유). 종류는 `ACTIVATE_REQUESTED`, `ROLLBACK_REQUESTED`, `LOADED`, `LOAD_FAILED`.
- **활성 패키지는 따로 저장하지 않고 기록에서 구한다**(마지막으로 `LOADED` 가 된 패키지). 포인터와 기록이 어긋날 수 없다.
- 덧붙일 때 `O_APPEND` 로 쓰고 `fsync` 한 뒤에 돌아온다. 파일 권한은 0600. 줄바꿈 없이 끝난 마지막 줄(덧붙이다 멈춘 흔적)만 버리고, 줄바꿈으로 끝난 줄이 깨졌으면 숨기지 않고 시작을 멈춘다.
- 시작할 때 기록을 읽어 마지막 `LOADED` 패키지를 스스로 적재한다(C05). 적재 결과 없이 끝난 요청은 활성으로 보지 않는다.
- 활성화 요청은 받은 즉시 기록하고, 적재가 끝나면 `LOADED` 나 `LOAD_FAILED` 를 덧붙인다. 롤백 대상은 `LOADED` 가 있었던 패키지 중 지금 활성이 아닌 것이다. 적재에 실패한 패키지는 롤백 대상이 아니다.

## 왜
- 이 영역의 상태는 작고(활성화 수십 건) 한 프로세스가 쓴다. 파일 하나면 의존이 늘지 않는다. DB 컨테이너와 마이그레이션은 계약에 입력이 없다.
- 덧붙이기만 하는 기록은 승인 이력(D53, D85(3))의 감사 성질에 맞고, 활성 상태를 기록의 함수로 두면 두 곳을 맞출 일이 없다.
- `O_APPEND` + `fsync` 는 POSIX 의 표준 덧붙이기·내구성 수단이다.

## 검토한 대안과 버리는 이유
- **PostgreSQL(ADR 0001 의 기본 DB):** 계약에 연결 입력이 없고, 상태가 작아 컨테이너 하나를 더 둘 이유가 없다. 영역 DB 가 필요해지면 새 ADR 로 바꾼다.
- **SQLite:** 표준 라이브러리이지만 파일 하나를 덧붙이는 것보다 얻는 것이 없고 동시 쓰기 잠금이 따라온다.
- **활성 포인터 파일 + 기록 파일:** 둘을 원자적으로 맞춰야 한다(`rename` 과 덧붙이기는 한 번에 안 된다).

## 결과
- **얻는 것:** 의존 없음, 재시작 복원, 승인 이력이 사람이 읽는 파일로 남는다.
- **감수하는 것:** 서버가 둘 이상이면 기록이 갈라진다(모델 서버 하나를 전제한다). 오래 쌓이면 읽는 시간이 늘지만 활성화 빈도가 낮아 측정하지 않았다. 백업은 deploy 의 유지 폴더 백업이 맡는다(C15).

## 되돌리는 조건
서빙 서버가 둘 이상이 되거나 기록을 조회하는 작업이 계약에 생기면 영역 DB 로 바꾼다.
