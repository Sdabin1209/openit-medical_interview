# 0013. 모델 입력의 글은 model-runtime 이 만들고 서비스는 구조화된 값만 보낸다

## 상태
승인(2026-11-10, 계약 8.0.0 반영). [0003](0003-모델-입력의-글-조각은-문항-세트에서만-만든다.md)을 대체한다.

## 맥락
계약 8.0.0 은 변경 요청 survey-service-002 를 받아, 모델 입력의 글(topic, known, ask, previous, current, hold)과 모델 입력 state 에 넣을 문항의 선택을 model-runtime 이 데이터셋 정본(labels.py, IO_SPEC.md)으로 만들게 했다. 서비스가 보내는 요청은 구조화된 값만 싣는다.

## 결정
- 추출 요청(`ExtractionRequest`): 지금 문항(question_id), 직전에 물은 문항(previous_question_id, 첫 문항이면 없음), 화면에 보인 직전 질문 문장(current_question), 환자 발화, 이번 턴을 반영하기 전에 저장된 모든 칸 값(slots, 넣은 순서 그대로, 다시 묻는 칸은 값 null 과 상태), 순서표, 칸 규격, 문항 은행 버전.
- 응답 요청(`ResponseGenerationRequest`): A 출력의 행동·사유·값(values)·칸(targets)·노트, 지금 문항과 직전 문항, 발화, 저장된 칸 값(slots), 다음 자리(next: 종류, 문항, 질문 문장). 질문 문장은 문항 세트의 문장이다. 문진 시작(START)은 행동과 next 만 보낸다.
- 되묻기 한도로 서비스가 건너뛸 때는 모델 응답을 부르지 않고 고정 문장과 다음 질문을 환자에게 보인다(변함없음).
- 표에서 찾는 글(질환명 등)은 서비스가 만들지 않는다.

## 왜
- 데이터셋 입출력 규칙(labels.py)이 닿는 곳은 model-runtime 하나다(design.md 2절). 서비스가 같은 규칙을 복사하면 정본이 둘이 된다(D74, D117).
- 서비스는 세션의 진행(직전 문항, 화면에 보인 글, 저장된 값)만 안다. 계약 설명이 이 값들을 서비스가 보내라고 정했다.
- slots 의 순서와 길이(최대 136)는 계약 StoredSlots 가 정한다. 넘기면 가장 최근에 넣은 칸부터 남긴다(문항 세트 검증이 칸 수를 묶어 실제로는 넘기 어렵다).

## 검토한 대안과 버리는 이유
- 0003 의 임시 생성 유지: 모델이 학습한 분포와 달라 품질을 보증할 수 없고 계약이 더는 그 칸을 받지 않는다.

## 결과
- 얻는 것: 정본이 한 곳이다. turn 컴포넌트가 단순해졌다(글 조각 만들기, 값을 사람 말로 바꾸기 코드 삭제).
- 감수하는 것: 응답 품질은 model-runtime 의 글 만들기에 달렸고 이 영역은 확인하지 못한다(가짜 model-runtime 으로 요청의 모양만 시험한다).

## 되돌리는 조건
계약이 요청의 모양을 다시 바꾸면 따른다.
