# 0018. 응답 문장 스트림: SSE 서버·클라이언트의 선택과 끊김 처리(처리와 연결을 분리한다)

## 상태
승인(2026-11-11, 영역 작업자 판단. 계약 9.2.0 `startSessionStream`·`submitTurnStream`의 구현)

## 맥락
계약 9.2.0 은 LoRA-B 응답 문장을 토큰 단위로 키오스크까지 흘리는 별도 작업 둘(`startSessionStream`, `submitTurnStream`)을 더했다. 규칙은 계약 README '응답 문장 스트림' 1~9항이 정본이다. 이 영역이 정해야 하는 것은 다섯이다. (1) SSE 응답을 어떻게 내보내나. (2) model-runtime 의 `generateResponseStream` 을 어떻게 읽나. (3) 키오스크가 끊어도 받아들인 요청을 끝까지 처리하는 구조. (4) 같은 기기·같은 코드의 시작이 처리 중인지 어떻게 아나(계약 `SESSION_START_IN_PROGRESS`). (5) JSON 작업은 어느 클라이언트를 쓰나.

## 결정
1. **서버.** FastAPI(Starlette)의 `StreamingResponse` 로 `text/event-stream` 을 낸다. 머리글은 `Cache-Control: no-store, no-transform` 하나만 더한다(계약 1·9항). 이벤트는 `event: <이름>\ndata: <JSON 한 줄>\n\n` 이고 data 의 `event` 칸은 event 줄과 같다. 받아들이는 조건은 JSON 작업과 같은 함수(`prepare_start`, `prepare_turn`)가 판정하고, 거절은 스트림을 열기 전에 같은 `ApiError` 로 나간다. 받아들인 뒤의 실패(`ApiError`)는 `error` 이벤트(`problem`, Retry-After 를 주었을 실패면 `retry_after_seconds`)로 바꾼다.
2. **클라이언트.** `httpx` 의 `stream()` 으로 열고 `httpx-sse`(MIT)의 `EventSource.aiter_sse()` 가 WHATWG HTML 9.2.6 의 줄·이벤트 규칙(CR/LF/CRLF, 주석 줄, 여러 data 줄, 모르는 이벤트 이름 무시)으로 읽는다. 상태 코드는 우리가 먼저 판정한다(그래서 `aconnect_sse` 가 아니라 `EventSource` 를 직접 쓴다). `delta` 는 받는 대로 콜백으로 넘기고 모으지 않는다. `result` 를 받으면 끝낸다. `error` 이벤트, `result` 없이 끝난 스트림, 200 이 아닌 응답, 스트림이 아닌 응답은 모두 `UNAVAILABLE`, 시간 초과는 `DEADLINE` 이다(JSON 클라이언트와 같은 구분). 모델 출력은 다시 검증하지 않고 계약 타입으로 읽을 뿐이다(R7).
3. **시간.** `RespondClientLimitSeconds`(21초)를 `asyncio.timeout` 으로 요청을 열 때부터 마지막 이벤트까지에 건다. httpx 의 `timeout` 은 읽기 한 번마다 걸려 조각이 계속 오면 끝나지 않기 때문이다(계약 8항은 마지막 이벤트까지). `SurveyTurnLimitSeconds`(50초)는 JSON 작업과 같이 서비스의 `asyncio.timeout` 이 건다. 값은 바꾸지 않았고 조각 사이의 상한도 두지 않았다(계약 8항).
4. **처리와 연결을 분리한다.** 받아들인 요청의 처리(모델 호출, 기록, `result`)는 요청이 아니라 앱이 쥔 `Background` 의 작업으로 돌린다. 응답 본문은 그 작업이 채우는 `asyncio.Queue` 를 읽어 내보내기만 한다. 키오스크가 끊으면 Starlette 가 본문 생성기를 취소하지만 작업은 취소되지 않아 기록(턴, 세션)까지 간다(계약 3항). `Background` 는 작업을 집합으로 쥐어(asyncio 문서: 이벤트 루프는 작업을 약한 참조로만 쥔다) 치워지지 않게 하고, 종료 때 `drain()` 으로 진행 중인 처리를 마친 뒤 DB·이웃 연결을 닫는다. 예기치 못한 예외는 기록하고 `error`(503) 로 닫는다(헤더를 이미 보내 상태 코드를 바꿀 수 없고, 닫지 않으면 키오스크가 끝없이 기다린다).
5. **세션 시작이 처리 중인지는 DB 표시로 안다.** 새 표 `start_attempt`(기기, 코드, 시작한 때; 마이그레이션 0002)에 모델을 부르기 전에 따로 커밋한다. 이미 있으면 `409 SESSION_START_IN_PROGRESS` 와 `Retry-After` 를 스트림을 열기 전에 준다(`startSession` 과 `startSessionStream` 둘 다). 세션 저장과 같은 트랜잭션에서 지우고, 실패하면 따로 지운다. 프로세스가 죽어 남은 표시는 `SurveyTurnLimitSeconds`(50초)가 지나면 넘겨받는다(턴의 PROCESSING 과 같은 규칙, ADR 0008). `PURGE_EXPIRED` 는 하루 지난 표시를 지운다.
6. **재시도.** JSON 작업의 "출력 불가는 같은 요청 1회 재시도"(D75)는 스트림에서 **조각을 아직 흘리지 않았을 때만** 한다. 조각을 흘린 뒤에 다시 하면 키오스크가 이어 그린 앞 시도의 조각 뒤에 새 문장의 조각이 붙어 글이 섞인다(계약 7항은 `result` 가 오면 바꾸지만 그 사이 화면이 틀리다). 흘린 뒤의 실패는 재시도 없이 턴은 `failure_signal` 의 `result`(기록하지 않음, D86), 시작은 `error`(아무것도 남기지 않음)로 끝난다. 시간 초과는 어느 쪽이든 다시 보내지 않는다. 재시도를 더한 것이 아니라 JSON 작업의 규칙이 보이는 곳까지만 같게 둔 것이다.
7. **JSON 작업은 JSON 클라이언트(`generateResponse`)를 그대로 쓴다.** 둘은 같은 `prepare_*`/`run_*` 를 쓰고 모델에서 문장을 받는 함수 하나(`respond`)만 다르다.
8. 서비스가 직원 도움 안내 같은 고정 문장을 붙이면 `result.response_text` 가 조각을 이은 것과 달라질 수 있다(계약 7항이 허용). 지금 모델 문장에 서비스가 붙이는 문장은 없다. 되묻기 한도로 건너뛰는 턴은 LoRA-B 를 부르지 않으므로 `delta` 없이 `result` 하나다.

## 왜
- WHATWG HTML 9.2(Server-Sent Events)와 계약 9.2.0 이 정본이다. FastAPI 는 이미 알림 스트림(ADR 0004)에서 `StreamingResponse` 로 SSE 를 낸다. 새 서버 의존이 없다.
- 클라이언트의 줄 규칙(CRLF, 주석, 필드 이어 붙이기)을 손으로 쓰면 틀리기 쉽다. 표준 파서를 쓰면 규칙을 다시 쓰지 않는다. `httpx-sse` 는 MIT 이고 이미 쓰는 `httpx` 위에서 돌며 파서 하나가 전부다. 버전은 `uv.lock` 에만 있다.
- 끊김과 처리의 분리는 계약 3항의 요구다. 요청 처리 중 취소를 막는 `asyncio.shield` 는 바깥 대기만 보호하고 안쪽 작업의 소유가 모호하다. 처리를 별도 작업으로 두고 앱이 그 수명을 쥐는 쪽이 종료 때 `drain` 으로 끝을 보장한다.
- 처리 중 표시를 DB 에 두는 것은 턴(ADR 0008)과 같은 이유다. 영역이 여러 복제본으로 돌 수 있고 프로세스 안 잠금은 복제본을 넘지 못한다.

## 검토한 대안과 버리는 이유
- **손으로 쓴 SSE 파서**: 표준 파서가 있고 MIT 이다. 규칙을 다시 쓸 이유가 없다.
- **`sse-starlette` 로 서버 쪽 SSE**: 머리글·하트비트·끊김 감지를 해 주지만 이 스트림은 유한하고 하트비트가 필요 없으며 새 의존이 늘어난다. `StreamingResponse` 로 충분하다.
- **`asyncio.shield` 만으로 끊김을 막기**: 생성기가 취소될 때 안쪽 작업을 누가 기다리는지가 모호하다. 종료 때 끝을 보장할 수 없다.
- **프로세스 안 집합으로 처리 중 시작을 가르기**: 복제본이 둘이면 다른 복제본으로 간 재전송을 못 막는다.
- **JSON 작업도 스트림 클라이언트로 모아 쓰기**: JSON 응답은 상태 코드 하나로 끝나는 더 단순한 경로이고, 스트림 클라이언트를 거치면 조각이 오다 끊긴 경우의 오류 구분이 JSON 작업에 새로 생긴다. JSON 작업의 동작을 바꾸지 않는 쪽을 골랐다.
- **조각을 흘린 뒤에도 재시도**: 위 6번의 이유로 글이 섞인다.

## 결과
얻는 것: 첫 글자를 모델이 낸 즉시 보인다. 끊겨도 기록이 서고 재전송은 409 뒤 재생으로 이어진다. 같은 기기·코드의 중복 시작이 첫 문장을 두 번 만들지 않는다. 감수하는 것: 표 하나와 마이그레이션이 늘었다. 조각을 흘린 뒤의 일시적 출력 불가는 JSON 작업과 달리 재시도 없이 실패 신호가 된다. 복제본이 죽을 때 남은 시작 표시는 최대 50초 동안 같은 코드의 재시도를 409 로 기다리게 한다. 이 영역은 게이트웨이·입구의 버퍼링을 바꿀 수 없다(계약 9항, 배치 쪽 일). 측정하지 않은 것: 조각 전달 지연과 동시 스트림 수의 영향.

## 되돌리는 조건
측정에서 스트림이 응답 시간을 줄이지 못하거나(게이트웨이가 모은다) 동시 스트림이 작업자를 고갈시키면 JSON 작업만 남기는 쪽을 검토한다. `start_attempt` 가 복제본 하나로만 돌게 확정되면 프로세스 안 표시로 바꿀 수 있다.
