# 0020. 모델 입출력 v3 의 화면 절차·설명 요청 원본·설명 요청 연속 수는 세션 행에 두고, v3 기능은 추출 응답의 버전으로 켠다

## 상태
승인(2026-11-23, 영역 작업자 판단). 계약 9.4.0(모델 입출력 v3, 어댑터 1118)을 구현한다. [0013](0013-모델-입력-글은-model-runtime-이-만든다.md)(서비스는 구조화된 값만 보낸다)과 [0019](0019-연속-턴-실패-수의-저장과-원자적-더함.md)(연속 실패 한도)는 그대로다.

## 맥락
v3 는 직전 화면에 따라 모델 입력이 달라진다. 확인(CONFIRM) 다음 턴의 state 는 확인하는 문항의 값만 담고(`previous_screen_action`), 설명 요청(REDIRECT 의 ASK_MEANING·ASK_HOW)은 직전 되묻기·확인 턴의 B 요청을 반영 전 값으로 이어 받는다(`AskBackSource`, fix3.md 1장). 설명 요청이 한 문항에서 3번 이어지면 서비스가 직원 도움을 안내하고(`ExplainStreakLimit`, `StaffHelpNotice`), 되묻기 한도로 넘길 때 v3 는 LoRA-B 가 문장을 만든다(`ModelIoFeature` LIMIT_REACHED_SENTENCE). 독립 검토(2026-11-23)는 확인이 앞 문항을 가리킬 때 B 의 SAME 이 묻던 문항을 가리키는 버그(v2 부터)도 찾았다. 이 값들은 재시작·재전송 뒤에도 같은 턴을 가리켜야 한다.

## 결정
1. `survey_session` 에 칸 셋을 더한다(마이그레이션 0004): `screen_action`(지금 화면을 만든 절차, 문자열), `explain_streak`(정수, 기존 행 0), `ask_back_source`(계약 `AskBackSource` 의 JSON). 기존 세션의 `screen_action`·`ask_back_source` 는 비워 둔다(알 수 없다). 비어 있으면 `previous_screen_action` 을 싣지 않아 model-runtime 이 v2 규칙으로 고른다.
2. `screen_action` 은 화면을 만든 LoRA-B 요청의 action 이다. 시작은 START, A 출력으로 만든 화면은 그 action, 되묻기 한도·연속 실패 한도로 서비스가 건너뛴 화면은 문장이 고정 문장이든 LIMIT_REACHED 든 SKIP 이다. 정지가 풀려도 바꾸지 않는다(화면 문장 `last_assistant_text` 도 그대로라 A 가 받는 `current_question` 과 맞는다). 추출 요청과 응답 생성 요청(START 밖) 모두에 싣는다.
3. 설명 요청의 원본: 턴이 기록될 때 화면을 만든 요청이 REASK·CONFIRM 이면 그 요청의 `AskBackSource` 칸(반영 전 slots, values, targets, reason, question_id, previous_question_id, user_utterance, next)을 저장하고, 설명 요청이면 그 요청이 이어 받은 원본을 그대로 남기고(처음 원본), 그 밖의 화면과 고정 문장이면 지운다. 설명 요청 턴은 저장한 원본이 있을 때만 `ask_back_source` 로 싣는다.
4. 설명 요청 연속 수는 같은 문항에서 ASK_MEANING·ASK_HOW 가 이어질 때 1 씩 더하고, 다른 절차나 문항이 바뀌면 0 이다. 연속 수가 한도(3) **이상**인 설명 요청 턴마다 LoRA-B 문장 뒤에 서비스의 고정 문장(`StaffHelpText.EXPLAIN_STAFF_HELP`, 키오스크의 '직원 부르기' 버튼을 안내)을 붙이고 응답에 `staff_help_notice: true` 를 준다. 붙인 글이 화면 문장 상한(`ResponseSentence` 344자)을 넘으면 고정 안내와 지금 문항의 질문으로 바꾼다. 세션을 멈추거나 직원 알림을 내지는 않는다. 설명 요청은 지금처럼 되묻기 수에 세지 않고 UNCLEAR_TARGET(REASK)은 센다.
5. 되묻기 한도로 넘길 때 v3 이고 다음 자리가 END 가 아니면 SKIP/LIMIT_REACHED 요청(values 빈 배열, targets 없음, 묻던 문항, 이번 발화, next NEXT 와 그 질문)으로 문장을 받는다. v2 이거나 END 면 지금처럼 고정 문장이다. 빈칸 원인은 REASK_LIMIT 그대로다. 그 문장을 받지 못하면 다른 LoRA-B 실패처럼 실패 신호이고(턴을 기록하지 않아 세션은 그대로) 연속 실패 수에 센다. 연속 실패 한도의 고정 문장 경로는 바꾸지 않는다.
6. v3 의존 기능(`ModelIoFeature`)은 그 턴의 추출 응답 `model_io_version`(없으면 v2)으로 켠다(`types.model_io_features`). 세션 시작 때 기록한 `model_io_version` 은 쓰지 않는다.
7. B 요청의 SAME 자리(REASK·CONFIRM·REDIRECT)의 문항과 질문 문장은 A 출력의 `next_item` 에서 만든다(정본 `labels.py` b_input).

## 왜
- 세션 행에 둔다: 세 값 모두 세션 하나의 '지금 화면' 상태이고 턴을 반영하는 트랜잭션(세션 행 잠금, 0008·0019)에서 함께 바뀐다. 실패한 턴은 세션을 바꾸지 않으므로(0017) 실패 뒤 재전송도 같은 원본과 수를 본다. 기록한 턴의 재전송은 저장한 응답을 재생한다(0008).
- 원본을 요청 그대로(반영 전) 저장한다: 지금의 answers 로 다시 만들면 확인 중인 값이 반영된 뒤라 저장 시점이 달라진다(검토 3번). 계약 `AskBackSource` 가 글이 아니라 원재료를 싣게 정해 model-runtime 이 같은 규칙으로 다시 만든다.
- 한도 이상마다 안내한다: 계약은 '닿으면 안내'만 정했다. 셋째 뒤에도 설명 요청이 이어지면 환자는 여전히 도움이 필요하므로 안내를 거두지 않는 쪽을 골랐다(측정하지 않은 선택).
- 고정 문장을 B 문장 뒤에 붙인다: 계약 README '응답 문장 스트림' 7항이 "서비스가 직원 도움 안내 같은 고정 문장을 붙이면" 이라고 적었고, 설명 자체는 LoRA-B 가 학습한 일이다. 버튼 이름을 가리키는 것은 안내가 직원 호출 사건이 아니라 환자가 고르는 일이기 때문이다(`StaffHelpNotice`).
- 추출 응답의 버전: 계약 `ExtractionResult.model_io_version` 이 "서비스가 v3 의존 기능을 켤지 이 값으로 정한다" 고 정했다. 세션 도중 패키지가 바뀌어도 그 출력을 만든 패키지의 버전을 따른다.

## 검토한 대안과 버리는 이유
- 원본을 턴 기록(turn_record)에서 찾기: 직전 기록 턴을 찾는 조회가 늘고, 설명 요청이 이어질 때 '처음 원본' 을 고르려면 여러 턴을 거슬러 가야 한다. 세션 칸 하나가 단순하다.
- 화면 절차를 턴 기록의 A 출력에서 다시 계산: 한도 건너뛰기(SKIP)와 시작(START)은 A 출력에 없다.
- 셋째에만 안내하고 수를 0 으로: 넷째 설명 요청에 안내가 사라진다.
- 셋째에 LoRA-B 를 부르지 않고 고정 문장만: 설명을 바란 환자에게 설명 없이 안내만 준다.
- 세션 시작 때의 `model_io_version`: 계약이 추출 응답의 값을 기준으로 정했다.

## 결과
얻는 것: 확인이 앞 문항을 가리켜도 B 가 그 문항을 묻는다. 확인 다음 턴의 state 를 model-runtime 이 학습 모양대로 고른다. 설명 요청이 직전 되묻기 내용을 잃지 않는다(재시작·재전송 뒤에도). 시험: `tests/unit/test_v3_components.py`, `tests/api/test_v3_turns.py`(SQLite·PostgreSQL), `tests/unit/test_migrations.py` 의 0004. 감수하는 것: 세션 행의 칸 셋과 마이그레이션 0004. v3 의 한도 턴은 LoRA-B 호출이 하나 늘어 실패할 수 있다(실패 신호). `AskBackSource` 에 `previous_screen_action` 칸이 없어 model-runtime 이 원본을 다시 만들 때 state 를 v2 규칙으로 고른다(원본이 확인 다음 턴의 REASK·CONFIRM 이면 학습 때 state 와 다를 수 있다. 측정하지 않았다).

## 되돌리는 조건
계약이 설명 요청 원본이나 화면 절차를 다른 곳(예: model-runtime 의 세션 상태)에 두게 바꾸거나, 안내 방식(한도마다/한 번)을 정하면 이 ADR 을 대체한다.
