# 0016. 이미지 선언(잡·노출·입력)의 원본 파일과 노출·나가는 호출 선언

## 상태
승인(2026-11-11, 영역 작업자 판단, 계약 9.0.0 반영, 변경 요청 survey-service-005 의 답).

## 맥락
이미지 라벨 `io.openit.jobs`(JobsDeclaration), `io.openit.exposure`(Exposure), `io.openit.inputs`(ContainerInputs)가 deploy 와 platform 의 입력이다. 입구 생성기(platform ADR 0003)는 노출 선언과 계약 작업의 `security` 를 곱해 라우트를 만들고 허용 작업이 하나도 없는 접두어는 시작하지 않는다.

## 결정
- 원본은 영역 폴더의 `jobs.json`, `exposure.json`, `inputs.json` 이다. `Dockerfile` 은 `ARG JOBS`, `ARG EXPOSURE`, `ARG INPUTS` 를 받아 라벨로 달 뿐 내용을 복사하지 않는다(deploy build 가 파일을 한 줄 JSON 으로 넘긴다). 시험(`tests/unit/test_image_declaration.py`)이 세 파일을 계약 타입으로 검증하고 서로·코드와 어긋나지 않는지 본다. 이미지 스모크는 라벨이 파일과 같은지 본다.
- `inputs.json`: 실행 사용자 10001(Dockerfile 의 `USER`), 환경 입력은 `SurveyServiceEnv` 의 모든 칸(이름, 필수 여부, 종류가 스키마와 같다: `SecretFilePath` 는 `SECRET_FILE`, `ConfigFilePath` 는 `FILE_PATH`, 그 밖은 `VALUE`. 시험이 계약에서 읽어 견준다), 쓰는 경로 없음(읽기 전용 루트에서 DB 는 밖이고 서비스는 파일을 쓰지 않는다), 추가 권한·sysctl 없음, 프로세스는 서비스 진입점 `/app/.venv/bin/python -m survey_service`(Dockerfile 의 `CMD` 와 같다)와 잡마다 `/app/.venv/bin/python -m survey_service.jobs <잡>` 이다. 잡 호출 모양: deploy 는 선언된 argv 뒤에 `--requested-at <RFC 3339>` 를 덧붙인다(시각은 스케줄러가 정하므로 선언에 못 박지 못한다, ADR 0010).
- `exposure.json` 의 경로는 계약 `survey-service.yaml` 의 작업 `security` 와 맞춘다: 기기(`DEVICE_MTLS`)는 `/v1/questionnaires`(GET), `/v1/sessions`(GET·POST). 사람(`HUMAN_OIDC`)은 직원·의사·관리자 작업의 접두어 `/v1/questionnaires`, `/v1/start-codes`, `/v1/sessions`(POST, 개입), `/v1/staff-alerts`, `/v1/push-config`, `/v1/push-subscriptions`, `/v1/results`, `/v1/cases`, `/v1/deidentified-traces`, `/v1/question-set-versions`. 외부 기계 호출자(`EXTERNAL_MACHINE_TOKEN`)는 `/v1/results`(GET, 병원 시스템)와 `/v1/risk-signals`(POST, 위험 감지기). 영역 사이 기계 호출(`MACHINE_TOKEN`)은 `/v1/case-exports`(GET, model-lab). 건강·지표 경로는 입구로 내보내지 않으므로 선언하지 않는다. 접두어가 경로 구간 단위로 걸려 `/v1/sessions` 의 기기 선언이 직원 전용 개입 작업을 기기에게 열지 않고(그 작업의 `security` 에 기기가 없다), `/v1/cases` 가 `/v1/case-exports` 에 걸리지 않는다.
- egress 는 `model-runtime`(추출·응답), `platform`(발급자: JWKS, 토큰 엔드포인트, ADR 0014)이다. **웹 푸시 서비스는 이 파일에 선언하지 않는다.** 푸시 서비스의 호스트는 브라우저가 구독 때 정하는 설치처·브라우저 값(FCM, Mozilla, Apple 등)이라 영역 리포의 정적 파일에 못 박을 수 없고 계약 `ExternalEgressTarget` 은 호스트와 포트를 요구한다. 설치처가 허용할 푸시 서비스 호스트 목록은 deploy 가 설치 설정에서 읽어 라벨의 `egress` 에 더한다(헤드가 할 일로 보고에 올렸다). 서비스는 그 터널 밖으로 푸시를 보내지 않는다(`link_push` 는 `OPENIT_EGRESS_PROXY` 로만 나간다).

## 왜
- 계약 `Exposure` 는 경로와 대상만 정하고 역할의 정본은 작업 `security` 다(platform-003). 접두어를 작업 `security` 와 어긋나게 선언하면 입구가 시작하지 않는다(platform ADR 0003). 시험이 같은 규칙으로 선언의 모든 경로가 허용 작업을 하나 이상 가지는지, 계약의 모든 공개 작업이 그 대상의 경로에 닿는지 본다.
- 원본을 한 곳(파일)에 두고 Dockerfile 이 인자만 받으면 같은 선언이 두 곳에 있어 어긋나는 일이 없다.

## 검토한 대안과 버리는 이유
- 푸시 서비스 호스트를 `exposure.json` 에 고정: 설치처마다 다르고 브라우저마다 달라 틀리거나 모자란다.
- 작업 경로를 하나씩 선언: 계약에 작업이 늘 때마다 파일을 고쳐야 한다. 접두어 선언과 시험의 일치 점검이면 충분하다.
- 서비스가 푸시 서비스를 터널 없이 직접 호출: D128 을 어긴다.

## 결과
얻는 것: 선언이 계약과 코드에 맞는지 시험이 지킨다. 감수하는 것: 푸시 호스트 선언은 deploy 의 설치 설정 몫이다. platform 의 실제 라우트 생성과는 이 환경에서 맞춰 보지 못했다(영역 시험은 같은 규칙의 요약 구현으로 본다).

## 되돌리는 조건
계약이 푸시 서비스를 서비스 이름이나 설치처 값으로 정하면 따른다.
