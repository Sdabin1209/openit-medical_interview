# 0014. 기계 호출자는 JWT 접근 토큰(client credentials)과 호출자 표로 인증한다

## 상태
승인(2026-11-11, 영역 작업자 판단, 계약 9.0.0 반영). 8.0.0 의 고정 토큰 파일 비교를 대체한다.

## 맥락
이 서비스는 기계 호출자 셋(병원 시스템 result-reader, 위험 감지기 risk-detector, model-lab case-reader)에게 불리고, 기계 호출자 하나로서 model-runtime 을 부른다(inference-caller). 계약 9.0.0 은 기계 토큰을 Keycloak client credentials(RFC 6749 4.4)로 받은 JWT 접근 토큰(RFC 9068)으로 정했다. 클라이언트 ID 는 `machine-<호출자 이름>`, 읽는 클레임은 `MachineIdentityClaims`(`aud` 는 받는 서비스, 역할은 `realm_access.roles` 의 `MachineRole`)다. `OPENIT_MACHINE_TOKENS_FILE` 은 `MachineTokenTable`(호출자 이름, 역할, 클라이언트 비밀 파일 경로. 비밀은 없다)이다.

## 결정
**받는 쪽.** 사람 토큰과 같은 코드로 서명(JWKS)·iss·aud·exp·iat·typ·alg 를 확인한다(`Authenticator._claims`). 어느 종류인지는 값이 계약 스키마 중 어느 것에 맞는지로 가른다: `MachineIdentityClaims` 에 맞으면 기계(client_id 가 `machine-<이름>` 이고 역할이 `MachineRole`), 아니면 `UserIdentityClaims` 에 맞으면 사람, 둘 다 아니면 401. 기계 호출자의 권한은 **호출자 표의 역할과 토큰의 `realm_access.roles` 가 모두 허용한 역할(교집합)** 이다. 토큰의 `client_id` 에서 `machine-` 을 뗀 이름으로 표에서 찾고, 표에 없는 호출자는 역할이 비어 403 이다. 표의 `client_secret_file` 은 읽지 않는다. 토큰은 맞는데 이 작업의 역할이 없으면 403, 토큰이 틀리면 401 이다(D58).

**보내는 쪽.** `link_model_client` 는 `MachineTokenSource` 로 client credentials 토큰을 받는다(클라이언트 `machine-survey-service`, 비밀은 `OPENIT_MODEL_RUNTIME_CLIENT_SECRET_FILE`). 토큰 엔드포인트는 발급자 디스커버리 문서(`<발급자>/.well-known/openid-configuration` 의 `token_endpoint`, OpenID Connect Discovery 1.0 4)에서 얻고 한 번 읽은 뒤 기억한다. 토큰은 `expires_in` 만료 30초 전(수명이 짧으면 수명의 절반 전)까지 쓰고 그 뒤에 다시 받는다. 만료 때 동시에 부르는 호출이 발급자를 여러 번 두드리지 않게 잠근다. model-runtime 이 401 로 답하면 토큰을 버려 다음 호출이 새로 받는다. 클라이언트 인증은 HTTP 기본 인증이고 ID·비밀을 먼저 폼 인코딩한다(RFC 6749 2.3.1). 비밀 파일은 받을 때마다 읽어 회전을 따른다. 발급자로 나가는 모든 호출(디스커버리, 토큰, JWKS)은 `OPENIT_EGRESS_PROXY` 의 CONNECT 터널을 지난다(이전 구현은 JWKS 호출이 터널 밖이었다. 고쳤다). 선언은 `exposure.json` 의 egress `platform`(ADR 0016).

## 왜
- 계약 `machine_token` 설명이 둘을 정한다: 받는 쪽은 `realm_access.roles` 로 권한을 가르고, `OPENIT_MACHINE_TOKENS_FILE` 은 '이 서비스를 부르는 기계 호출자 표'다. 표는 platform 이 Keycloak 기계 클라이언트와 서비스 계정 역할을 만드는 같은 입력이므로 정상이면 두 쪽의 역할은 같다. 어긋난다면 IdP 설정이 틀렸거나 표가 낡은 것이고 그때 권한이 넓어지지 않는 쪽(교집합)이 최소 권한 원칙(D122)에 맞다.
- 종류를 스키마로 가르면 코드에 계약에 없는 거부 조건이 생기지 않는다(D117). 경로나 접두어 규칙을 코드가 따로 갖지 않는다.
- RFC 9068 은 자원 서버가 같은 검증을 하게 하고 RFC 6749 4.4 는 기계 호출자가 비밀로 토큰을 받게 한다. 토큰을 캐시하는 것은 요청마다 발급자를 부르지 않기 위한 표준 관행이다.
- 30초와 수명의 절반은 측정하지 않은 선택이다(만료 직전 토큰이 도중에 거절되는 것을 피하는 여유).

## 검토한 대안과 버리는 이유
- 토큰의 역할만 보고 표는 이름 확인용: 표를 읽는 이유가 약해지고 IdP 가 표보다 넓게 역할을 주면 그대로 통과한다.
- 표의 역할만 보고 토큰 역할은 무시: 계약이 `realm_access.roles` 로 가른다고 한 것과 어긋나고 IdP 에서 역할을 회수해도 서비스가 따르지 않는다.
- 토큰 엔드포인트 주소를 환경 입력으로 받기: 계약 Env 에 없고 발급자에서 얻으면 한 곳(발급자)만 설정하면 된다.
- 요청마다 토큰 받기: 발급자가 모든 환자 턴의 경로에 들어와 병목이 된다.

## 결과
얻는 것: 고정 비밀 파일 비교가 없어지고 토큰에 만료가 생긴다. 사람과 기계가 같은 검증 코드를 쓴다. 감수하는 것: 사람 토큰이 기계 작업에, 기계 토큰이 사람 작업에 오면 이전의 401 이 아니라 403 이다(둘 다 열리지 않는다). 기계 클라이언트에 사람 역할(`UserRole`)을 준 IdP 설정이면 그 토큰이 사람으로 읽힌다(그 설정은 platform 의 몫이다). 실제 Keycloak 과는 이 환경에서 연동하지 못했다(시험은 서명한 시험 토큰과 가짜 발급자). Keycloak 이 기본 인증의 폼 인코딩을 어떻게 읽는지도 확인하지 못했다.

## 되돌리는 조건
계약이 기계 토큰을 JWT 가 아닌 것으로 바꾸거나 표의 역할이 정본이라고 정하면 새 ADR 로 바꾼다.
