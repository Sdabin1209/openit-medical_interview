# 0006. 접근 토큰 검증(RFC 9068 프로파일)과 JWKS 캐시, 알 수 없는 역할 거르기

## 상태
승인(2026-11-10, 영역 작업자 판단)

## 맥락
사람 호출은 OIDC(Keycloak) JWT 접근 토큰이다. 계약 README 의 검증 프로파일을 서비스가 지켜야 한다.

## 결정
PyJWT 로 서명(JWKS 의 공개 키), iss, aud(서비스 이름), exp, iat 를 확인하고 JOSE 헤더의 typ(at+jwt)와 alg(none 거절), 클레임 sub·client_id·jti 는 계약 모델(AccessTokenHeader, UserIdentityClaims)로 확인한다. JWKS 는 캐시하고 모르는 kid 가 오면 60초에 한 번만 다시 읽는다. 클레임의 realm_access.roles 에서 계약의 UserRole 에 없는 역할은 검증 전에 버린다.

## 왜
RFC 9068 4(자원 서버의 검증), RFC 7517(JWKS). 60초는 키 회전을 반영하면서 가짜 kid 로 IdP 를 두드리지 못하게 묶는 선택이며 측정하지 않았다. 역할을 거르는 이유: Keycloak 은 offline_access 같은 기본 역할도 realm_access.roles 에 넣는데 계약 모델은 UserRole 만 받는다(변경 요청 survey-service-003). 버려도 권한은 늘지 않는다(요구 역할은 UserRole 에서만 고른다).

## 검토한 대안과 버리는 이유
- 모든 클레임을 계약 모델로 엄격히 검증: 실제 토큰이 항상 401 이 된다.
- 캐시 없이 매번 JWKS: IdP 가 병목이 된다.

## 결과
얻는 것: 계약의 프로파일을 지키고 실제 IdP 토큰을 받는다. 감수하는 것: 계약과 실제 토큰의 어긋남을 코드가 흡수한다. 실제 Keycloak 과는 이 환경에서 연동하지 못했다(시험은 서명한 시험 토큰).

## 되돌리는 조건
계약이 역할 목록을 열린 문자열로 바꾸면 거르기를 지운다.
