# 0002. 시작 코드 실패 시도 한도(기기당 5분에 10번)와 코드 충돌 처리

## 상태
승인(2026-11-10, 영역 작업자 판단)

## 맥락
시작 코드는 6자리 숫자(100만 가지)라 환자 자리의 키패드 앞에서 무작위로 맞히는 시도를 막아야 한다. 계약은 한도가 있어야 하고 넘으면 429 와 Retry-After 로 답하라고만 정하고(startSession) 값은 정하지 않는다.

## 결정
실패 시도(없는 코드, 만료, 다른 기기가 쓴 코드)를 기기별로 세어 300초 안에 10번이면 429 를 낸다. Retry-After 는 계약 RetryAfterSeconds 의 상한 120초로 자른다. 코드는 `secrets.randbelow` 로 만들고 살아 있는 코드와 겹치면(DB 의 기본 키) 최대 8번 다시 만든다.

## 왜
NIST SP 800-63B 5.2.2 가 실패 시도 한도를 요구하되 값은 정하지 않는다. 한도 값(10회, 300초)은 표준에서 나오지 않았고 측정하지 않았다. 100만 가지를 기기당 5분 10번으로 묶으면 코드 유효 시간(최대 600초) 안에 맞힐 확률이 10^-5 수준이라는 계산이 근거다. 난수는 추측 가능한 `random` 이 아니라 암호학적 난수(`secrets`, Python 문서의 보안용 난수 권고)다.

## 검토한 대안과 버리는 이유
- 코드 단위 한도: 환자가 코드를 바꿔 가며 시도하면 못 막는다.
- 전역 한도: 한 기기의 실패가 다른 기기를 막는다.
- 계정 잠금: 환자에게 계정이 없다.

## 결과
얻는 것: 무차별 대입을 기기 단위로 막는다. 감수하는 것: 같은 기기에서 직원이 시험으로 틀린 코드를 10번 넣으면 5분 막힌다. 기기 신원이 위조되면(게이트웨이 가정이 깨지면) 한도는 우회된다.

## 되돌리는 조건
값이 운영에서 너무 빡빡하거나 느슨하다고 측정되면 설정 입력으로 올리는 변경 요청을 낸다(지금은 계약 Env 에 이 입력이 없다).
