# 0003. 화면 구성, 서버 호출과 재시도

## 상태
승인(2026-11-10, kiosk-frontend 작업자)

## 맥락
키오스크는 survey-service 의 `listActiveQuestionnaires`, `startSession`, `submitTurn`, `endSession`, `getSessionState`, `requestStaffCall` 을 부른다. 시간 상한은 계약 `TimeBudgetTable`(요청 60초, 재시도 총 120초, 진행 표시 1초, 상태 읽기 2초)이 정한다. 기기 신원은 브라우저·OS 의 기기 인증서이고 화면 코드는 신원을 다루지 않는다.

## 결정
- 구조(루트 ADR 0003): `src/link/survey.ts` 만 서버와 통신한다. 컴포넌트는 `StartView`, `ConversationView`, `PausedView`, `EndView`, `IdleReset`, `speech` 이고 props 로만 데이터를 받는다. 컴포넌트 사이 연결은 `src/App.tsx`(조립)가 한다.
- 화면 이동은 react-router(`/` 시작, `/talk` 대화·멈춤, `/end` 끝). 서버 상태는 TanStack Query(문진표 목록, 멈춘 동안의 2초 읽기)이고 한 번 하는 쓰기는 `useMutation` 이다.
- 클라이언트: `openapi-fetch`(MIT)로 생성 타입(`src/contract/survey-service.d.ts`)에 맞춰 부른다. 받은 값은 서버가 한 번 검증했으므로 다시 검증하지 않는다(R7).
- 재시도: 응답 없음, 503, 409 `TURN_IN_PROGRESS` 만 다시 보낸다. `Retry-After`(없으면 2초)만큼 기다리고 총 120초 예산 안에서만 한다. 같은 `turn_id` 로 다시 보내므로 멱등이다. 429(시작 코드 시도 한도)는 자동으로 다시 보내지 않고 안내한다.
- 실패 신호(`failure_signal`)를 받은 뒤 환자가 다시 보내는 것은 새 `turn_id` 의 새 턴이다.
- 세션이 끝났거나 멈춘 것으로 409 `SESSION_NOT_ACTIVE` 를 받으면 `getSessionState` 를 한 번 읽어 화면을 맞춘다. 읽은 상태가 `EXPIRED` 이면 시작 화면으로 돌아간다([ADR 0004](0004-고령자-접근성과-유휴-초기화.md)).
- 2초 읽기는 멈춘 동안에만 한다(D66(6)).
- 계약 값은 `src/limits.ts` 에 이름을 붙이고 `tests/contract/limits.test.ts` 가 `contracts/components.yaml` 과 대조한다. 생성 타입에는 `maxLength`·`const` 가 담기지 않아서 이 대조 시험이 계약이 바뀔 때 깨지는 장치다.
- 시험: 이웃은 계약 타입으로 만든 가짜(`tests/fakes/survey-service.ts`)로 대신한다. 단위·계약 시험은 MSW, 브라우저 시험은 `page.route` 가 같은 가짜를 쓴다(ADR 0012).

## 왜
- 재전송 규칙이 계약 9.0.0 의 `submitTurn` 과 맞다(변경 요청 003의 결정): 서버는 실패 신호를 준 `turn_id` 를 기록하지 않아 같은 `turn_id` 의 재전송은 다시 처리된다. 그래서 (1) 연결 실패·503 은 응답을 못 받았거나 서버가 처리하지 않은 경우이므로 같은 `turn_id` 로 다시 보내도 한 번만 처리된다. (2) 응답으로 `failure_signal` 을 받았으면 그 `turn_id` 는 서버에 남지 않았으므로 같은 것을 다시 보내도 안전하지만, 이것은 환자가 고치거나 다시 말한 새 입력이므로 새 `turn_id` 로 보낸다(`turn_id` 는 환자 입력 한 번의 시도를 가리키는 값이다. 연결 문제로 다시 보내는 것만 같은 시도다). 어느 쪽도 계약의 다시 처리 규칙과 충돌하지 않는다. 시험: `tests/unit/app.test.tsx` 의 "실패 뒤 다시 보내면 새 turn_id", 가짜 서버는 실패 신호의 `turn_id` 를 기록하지 않는다.
- 재시도 조건은 계약의 멱등 규칙(같은 `turn_id`, 같은 기기·같은 코드)과 503·409 의 설명(`Retry-After`)에서 나왔다. 한 번 더 시도해도 같은 결과가 나는 것만 다시 보낸다.
- `openapi-fetch` 는 `openapi-typescript` 와 같은 저자가 만든 짝이고 경로·본문 타입이 생성 타입에서 나온다.
- 2초 읽기를 멈춘 동안에만 하는 것은 계약 설명이 "직원이 정지를 풀었는지 안다" 는 용도를 적었기 때문이다.

## 검토한 대안과 버리는 이유
- **fetch 를 직접 쓰고 타입을 손으로 쓰기:** 계약 타입을 손으로 옮기지 않는다는 규칙(브리프)과 어긋난다.
- **ACTIVE 동안에도 2초마다 읽기:** 위험 신호로 인한 멈춤을 바로 알 수 있다. 계약 9.0.0 은 이 읽기를 활동으로 세지 않아 유휴 계산에는 영향이 없지만, 계약이 적은 용도는 정지가 풀렸는지 아는 것이고 ACTIVE 중 읽기는 이득이 작다고 판단했다(측정하지 않았다). 다음 턴의 409 로 알아낸다.
- **재시도 간격을 지수 백오프로:** `Retry-After` 가 있으면 서버 값을 따르는 것이 표준(RFC 9110 10.2.3)이다. 없을 때의 2초는 측정하지 않은 값이며 총 시간은 계약 예산이 막는다.

## 결과
- 얻는 것: 연결이 흔들려도 같은 턴이 한 번만 처리된다. 컴포넌트는 서버를 모른다.
- 감수하는 것: ACTIVE 중 위험 신호로 멈춘 세션을 환자의 다음 입력 때에야 안다. 2초 폴링과 재시도 간격 2초는 측정하지 않았다.

## 되돌리는 조건
계약이 ACTIVE 중 읽기를 정의하면 그에 맞춘다. 재시도 값이 측정으로 달라지면 새 ADR 이 이것을 대체한다.
