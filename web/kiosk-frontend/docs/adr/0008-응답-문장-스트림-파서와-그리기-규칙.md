# 0008. 응답 문장 스트림: 파서 선택과 그리기 규칙

## 상태
승인(2026-11-11, kiosk-frontend 작업자). 계약 9.2.0 의 `startSessionStream`, `submitTurnStream` 을 구현한다. [0003](0003-화면-구성과-재시도.md) 의 서버 호출 중 시작과 턴 부분을 대체하고 나머지(재시도 조건의 나머지, 예산, 2초 읽기)는 그대로다.

## 맥락
환자가 느끼는 응답 시간은 첫 글자가 보이는 때로 정한다(계약 README "응답 문장 스트림"). 서비스는 LoRA-B 문장을 Server-Sent Events 로 흘리고(`delta` 0개 이상 뒤 `result` 또는 `error` 하나), 화면은 조각을 받는 즉시 이어 그리고 `result` 의 문장으로 바꾸며, 문장이 없는 `result` 나 `error` 면 그린 조각을 지우고 JSON 작업의 실패와 같게 다룬다(7항). 두 작업은 POST 이고 기기 인증서(mTLS)는 브라우저가 제시한다. 작업 응답은 `text/event-stream` 문자열로 생성되어 이벤트 data 스키마(`SessionStartStreamEvent`, `TurnStreamEvent`)는 작업 문서에서 생성되지 않는다.

## 결정
- 전송: `fetch` POST 로 열고 `response.body` 를 `ReadableStream` 리더로 읽는다. 브라우저 `EventSource` 는 GET 만 되고 요청 본문을 못 보내서 쓰지 않는다(WHATWG HTML 9.2).
- 파서: `eventsource-parser`(MIT, 직접 의존). 청크를 `TextDecoder`(`stream: true`)로 풀어 `feed` 한다. 버전은 `package-lock.json` 에만 있다.
- 이벤트 해석: data 의 `event` 칸으로 가른다. `delta` 는 글을 이어 붙이고, `result`·`error` 는 마지막 이벤트라 읽기를 멈추고 본문을 닫는다.
- 그리기 규칙(`link/survey.ts` 가 `SentenceSink` 로 화면 문장 전체를 알린다):
  1. `delta` → 이어 붙인 글 전체를 알린다. 대화 화면은 이전 문장 자리에 이 글을 보이고(`aria-busy` 로 조각마다 읽어 주지 않게 한다), 세션 시작은 아직 대화 화면이 없어 시작 화면의 아래에 미리 보인다.
  2. `result` 에 문장(`response_text`)이 있으면 그 글로 바꾼다.
  3. 문장 없는 `result`(`failure_signal`), `error`, `result` 없이 끝난 스트림, 읽다가 난 오류 → 빈 글을 알려 조각을 지우고 JSON 작업의 실패와 같게 던지거나 돌려준다. 문장 없는 `result` 는 기존 `failure_signal` 처리(발화 유지, 새 `turn_id`)를 탄다.
- 재시도: [0003](0003-화면-구성과-재시도.md) 의 규칙을 스트림에 그대로 건다. 열기 전 실패(JSON 문제 상세)와 `error` 이벤트는 같은 `SurveyError`(상태, 사유, `retry_after_seconds` 는 `Retry-After` 와 같이 취급)로 던진다. 다시 보낼 수 있는 것은 응답 없음(끊긴 스트림 포함, 상태 0), 503, 409 `TURN_IN_PROGRESS`, 409 `SESSION_START_IN_PROGRESS` 다. 같은 `turn_id`·같은 시작 코드로 보내고 `Retry-After`(없으면 2초)만큼 기다리며 총 120초 예산 안에서만 한다. 재시도나 시간 상한을 늘리지 않았다.
- 시간: 요청 상한 `KioskRequestLimitSeconds`(60초)는 `AbortSignal.timeout` 하나를 `fetch` 에 건 것이라 헤더뿐 아니라 마지막 이벤트까지의 본문 읽기에도 걸린다(계약 8항). 조각 사이 상한은 두지 않는다.
- 음성 합성: 문장이 확정된 뒤(세션의 문장이 `result` 로 바뀐 때) 한 번만 읽는다. 조각 단위로 읽지 않는다. 읽는 코드는 바꾸지 않았다(세션 문장이 바뀔 때 읽는 기존 효과).
- 이벤트 data 의 타입은 `redocly.yaml` 의 `components` 항목(admin-console 의 선례, 변경 요청 admin-console-003)이 공유 값 문서에서 생성한 `src/contract/components.d.ts` 의 `SessionStartStreamEvent`, `TurnStreamEvent` 를 쓴다. 같은 뜻의 타입을 손으로 다시 정의하지 않는다(D117). 생성물은 고치지 않는다.

## 왜
- `eventsource-parser` 는 WHATWG 이벤트 스트림 해석(줄 끝 CR/LF/CRLF, 주석, 여러 `data` 줄, 청크 경계에 걸친 줄, BOM)을 이를 구현한 라이브러리이고(규격 준수 여부는 이 영역의 시험이 청크 경계에서만 확인한다) MIT 라 배포물에 넣을 수 있다(루트 규칙: 허용형 라이선스). 의존이 작고 `fetch` 의 본문과 맞물리는 `feed` 인터페이스라 우리 코드는 읽기 루프와 이벤트 해석만 쓴다.
- `TextDecoder` 의 `stream: true` 는 한 글자의 UTF-8 바이트가 청크 경계에서 잘리는 경우를 위한 것이다(WHATWG Encoding). 시험이 4바이트 청크로 확인한다.
- 문장 없는 `result` 와 `error` 에서 조각을 지우는 것은 계약 7항이 정했고, 지우지 않으면 서버가 기록하지 않은 턴(D86)의 문장이 화면에 남아 환자가 다음 질문으로 오해한다.
- 같은 요청으로 다시 보내는 규칙은 계약 3항(끊긴 뒤의 재전송은 JSON 작업의 규칙)과 [0003](0003-화면-구성과-재시도.md) 에서 나왔다. `retry_after_seconds` 는 계약이 `Retry-After` 와 같은 뜻으로 정했다.
- 읽기를 마지막 이벤트에서 멈추는 것은 스트림이 유한하고 `id`·재개가 없다고 계약이 적었기 때문이다.

## 검토한 대안과 버리는 이유
- **`EventSource`:** GET 만 가능하고 본문·사용자 헤더를 못 보낸다.
- **같은 작업에 Accept 협상:** 계약이 생성 타입을 깨서 작업을 나눴다(계약 README).
- **`@microsoft/fetch-event-source`:** 같은 목적이지만 자동 재연결(`Last-Event-ID`)과 가시성 처리를 내장하는데, 이 계약은 재개가 없고 재시도 규칙을 우리가 정했다. 내장 재시도가 우리 예산·`turn_id` 규칙과 겹친다.
- **손으로 만든 파서:** 줄 끝 처리와 청크 경계가 규격에 있어 시험을 직접 쌓아야 한다. 표준 구현이 있다.
- **조각마다 음성 합성:** 문장이 `result` 로 바뀔 수 있고(고정 문장) 지워질 수 있어 읽은 소리를 되돌릴 수 없다.
- **세션 시작 조각을 보이지 않고 `result` 뒤에만 그리기:** 계약 7항은 시작에도 같은 규칙이다. 대화 화면은 세션 ID 가 있어야 열려 시작 화면에 미리 보인다.

## 결과
- 얻는 것: 첫 글자가 보이는 때가 응답 시간이 된다. 실패 때 조각이 남지 않는다. 재시도는 JSON 때와 같은 한도 안이다.
- 감수하는 것: 계약의 공유 값 문서 전체가 생성되어(`components.d.ts`) 쓰지 않는 스키마도 타입으로 들어온다. 계약이 바뀌면 `npm run check:contract` 와 가짜 서버의 타입이 먼저 깨진다. 조각 단위 전달은 Playwright 의 `page.route` 로 시험할 수 없어(본문을 한 번에 낸다) 단위 시험(MSW 의 `ReadableStream`)이 본다. 게이트웨이·입구가 버퍼링하지 않는지는 배치의 일이며 이 영역이 확인하지 못했다. 조각 수와 도착 간격은 측정하지 않았다.
- 서버의 JSON 작업 `submitTurn`, `startSession` 은 화면이 더 부르지 않는다.

## 되돌리는 조건
계약이 스트림 작업을 바꾸거나 없애면 새 ADR 이 대체한다. `eventsource-parser` 가 유지되지 않거나 라이선스가 바뀌면 대체 파서로 바꾼다.
