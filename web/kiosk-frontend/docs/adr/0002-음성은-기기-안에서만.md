# 0002. 음성은 기기 안에서만 처리한다

## 상태
승인(2026-11-10, kiosk-frontend 작업자)

## 맥락
브리프는 음성 인식·합성을 기기 안에서만 하고 외부로 보내지 않는다고 한다(UD-12, D88 U3). 브라우저 표준은 Web Speech API(`SpeechRecognition`, `speechSynthesis`)다. 그런데 Chromium 계열의 기본 인식은 소리를 서버로 보내 처리하는 구현이 있다(MDN `SpeechRecognition.processLocally`). 합성도 원격 목소리(`SpeechSynthesisVoice.localService === false`)는 글을 서버로 보낸다.

## 결정
- 인식: `SpeechRecognition.available({ langs, processLocally: true })` 가 `available` 일 때만 음성 입력을 켠다. 켠 뒤에는 `processLocally = true` 로 시작한다. `available` 이 없거나 다른 값(`downloadable` 등)이면 음성 입력을 끄고 글자 입력만 남긴다. 언어 팩 내려받기(`install`)는 부르지 않는다.
- 합성: `localService` 이고 한국어인 목소리가 있을 때만 읽는다. 없으면 글자만 보인다("다시 듣기" 버튼도 숨긴다).
- 전송 차단: nginx 의 CSP `connect-src 'self'` 로 이 화면의 스크립트가 같은 출처 밖으로 연결하지 못하게 한다(`nginx/security-headers.inc`).
- 시험: 단위 시험이 두 경우(기기 안 가능, 불가)를 대역으로 본다. 브라우저 시험은 Web Speech API 를 대역으로 바꾼다(아래 결과).

## 왜
- 확인하지 못하면 켜지 않는 쪽이 UD-12 를 지킨다. 음성이 안 되어도 글자 입력과 직원 호출이 남아 문진은 이어진다.
- `processLocally` 는 W3C Web Speech API 커뮤니티 그룹 명세의 항목이고 Chrome 139 이상이 낸다(MDN 의 호환성 표). 표준 경로라 환경 분기를 두지 않는다.

## 검토한 대안과 버리는 이유
- **서버 쪽 음성 인식(Whisper 등)으로 보내기:** 소리가 기기 밖으로 나간다. UD-12 위반.
- **`available` 이 없으면 기본 인식을 쓰기:** 외부 전송 여부를 확인할 수 없다.
- **`install` 로 언어 팩 내려받기:** 기기 안 처리에는 필요하지만 화면이 네트워크로 모델을 받는 일이고 CSP `connect-src` 와 충돌한다. 설치는 기기 준비 작업(배포)의 몫으로 본다. 이 결정이 맞는지는 deploy 와 정할 일이다(확인하지 못함).

## 결과
- 얻는 것: 외부 전송이 없다는 주장이 코드와 시험으로 뒷받침된다.
- 감수하는 것: 기기 안 인식이 준비되지 않은 키오스크는 글자 입력만 된다(고령자에게는 불편). 실제 키오스크 Chrome 에서 `available` 이 어떤 값을 내는지는 확인하지 못했다.
- 확인한 것: Playwright 공식 이미지(v1.65, headless Chromium)에서 `SpeechRecognition.available()` 을 부르면 렌더러가 죽는다(`Target crashed`, 같은 호출만 따로 돌려 재현). 그래서 브라우저 시험은 `tests/e2e/speech-stub.ts` 의 대역을 쓴다. 이 결과는 headless 환경에 한정된 관찰이고 일반 Chrome 의 동작을 말하지 않는다.

## 되돌리는 조건
브라우저가 소리를 서버로 보내지 않는다는 것을 표준으로 보장하거나, 사용자가 외부 인식을 허용하면 대체한다.
