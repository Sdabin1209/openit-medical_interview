# 0005. 문진표 선택은 서버가 요구할 때만 보인다

## 상태
확정(2026-11-11, 계약 9.0.0, 변경 요청 kiosk-frontend-001 의 결정). 이전 동작(활성 문진표가 둘 이상이면 언제나 선택)을 대체한다.

## 맥락
문진표는 시작 코드에 묶인 것, 없으면 요청의 것, 없으면 기기 배치표의 것으로 정해진다. 키오스크는 코드에 문진표가 묶였는지, 기기 배치가 있는지 알 수 없다. 이전 구현은 활성 문진표가 둘 이상이면 언제나 환자에게 고르게 해서, 이미 정해진 설치처에서도 환자가 불필요한 선택을 했다.

## 결정
- 키오스크는 처음에 `questionnaire_id` 없이 `startSession` 을 보낸다(같은 기기·같은 코드의 재전송은 멱등).
- 서버가 422 와 `ProblemReason` `QUESTIONNAIRE_REQUIRED` 로 답하면(이 응답은 시작 코드를 쓰지 않은 것으로 한다) 그때만 문진표 선택 화면을 보이고, 고른 `questionnaire_id` 를 더해 같은 코드로 다시 보낸다.
- 선택 화면의 목록은 `listActiveQuestionnaires` 다. 선택을 요구받았는데 목록이 비어 있으면 고를 것이 없으므로 연결 안내(UNAVAILABLE)를 보인다.
- 선택 요구는 오류 안내가 아니라 화면 단계(`StartView` 의 `choose`)로 처리한다. 코드는 지우지 않는다.

## 왜
- 코드 묶임과 기기 배치는 서버만 아는 사실이고 계약 `startSession` 의 설명이 이 순서를 정했다. 화면이 추측하지 않고 서버의 답(422 사유)에 따르면 판단이 한 곳에 있다(구조 규칙 4, 같은 사실을 두 곳에서 판단하지 않는다).
- 첫 요청이 멱등이고 422 가 코드를 쓰지 않으므로 다시 보내도 안전하다. 표준의 근거는 RFC 9110 15.5.21(422: 문법은 맞지만 처리할 수 없는 내용)이다.

## 검토한 대안과 버리는 이유
- **이전 구현(둘 이상이면 언제나 선택):** 정해진 설치처의 환자에게 불필요한 선택을 시킨다.
- **`listActiveQuestionnaires` 가 기기 배치 여부를 알리기:** 코드 묶임은 알 수 없어 부분 해결이다(변경 요청 001 의 2안).

## 결과
- 얻는 것: 선택이 필요한 경우에만 환자가 고른다. 문진표가 정해진 설치처에서는 선택 화면이 없다.
- 감수하는 것: 선택이 필요하면 요청이 한 번 더 간다(측정하지 않았다).

## 되돌리는 조건
계약이 선택 필요 여부를 알리는 방법을 바꾸면 그에 맞춘다.
