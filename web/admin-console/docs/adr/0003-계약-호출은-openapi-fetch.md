# 0003. 계약 호출은 openapi-fetch

## 상태
승인(2026-11-10, 영역 작업자)

## 맥락
화면은 두 서비스의 작업 약 25개를 부른다. 경로·본문·응답 타입을 손으로 옮기면 계약과 어긋나고, "계약 타입은 생성 명령으로만 만든다"(ADR 0020)에 어긋난다.

## 결정
`openapi-fetch`(MIT, `openapi-typescript` 와 같은 프로젝트)의 클라이언트를 `src/link/http.ts` 에 둔다. 두 계약의 `paths` 타입으로 각각 만든다. 오류 응답(RFC 9457)은 `ApiError`(상태 코드, `ProblemDetails`)로 바꿔 던진다. 서버 상태는 TanStack Query 훅(`src/link/*.ts`)이 맡고, 컴포넌트는 훅을 모르고 props 만 받는다.

## 왜
- 경로 문자열과 본문이 계약 타입으로 검사된다(잘못된 경로·칸은 tsc 가 막는다).
- 받은 값을 다시 검증하지 않는다(R7). 받는 쪽이 하는 것은 오류 응답을 `ApiError` 로 바꾸는 일뿐이다.

## 검토한 대안과 버리는 이유
- **fetch 직접 + 손으로 만든 타입:** 계약과 어긋난다.
- **orval, openapi-generator:** 코드를 생성한다. 이미 `openapi-typescript` 를 쓰므로 같은 도구 가족이 의존이 적다.

## 결과
- **얻는 것:** 계약이 바뀌면 `npm run generate:contract` 뒤 tsc 가 영향 받는 호출을 알려 준다.
- **감수하는 것:** 의존 하나 추가(`npm install openapi-fetch`, 버전은 잠금 파일). 쓰기 요청의 `Idempotency-Key` 는 계약이 필수로 정한 것이라 훅이 성공하기 전에는 같은 키를 다시 쓴다. 이 때문에 첫 시도가 실패한 뒤 사용자가 입력을 바꿔 다시 보내도 키가 같다. 서버가 실패한 요청을 저장하지 않는다는 가정이며 확인하지 못했다.
- 결과 상세(`getResult`)는 읽을 때마다 서버가 접근 기록을 남기므로(계약) 창 초점·재연결로 다시 읽지 않게 했다. 확인 표시 뒤에는 응답으로 화면을 고치고 다시 읽지 않는다.

## 되돌리는 조건
openapi-fetch 가 유지되지 않으면 얇은 fetch 래퍼로 바꾸고 새 ADR 을 쓴다.
