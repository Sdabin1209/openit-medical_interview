# 0006. 화면 구성과 입력 방식

## 상태
승인(2026-11-10, 영역 작업자)

## 맥락
ADR 0003(루트)이 컴포넌트는 contract 와 자기 폴더만 import 하고 서버는 link 만 부른다고 정했다(경계 점검). design.md 2절의 컴포넌트는 link_survey, link_model, start_code_view, result_view, alert_view, question_set_view, failure_review_view, release_view 다.

## 결정
- `src/link/survey.ts`, `src/link/model.ts`, `src/link/alerts.ts`, `src/link/session.ts`, `src/link/http.ts` 가 link 다. 화면 컴포넌트는 `src/components/<이름>/` 에 `StartCodeView`, `AlertView`, `ResultList`·`ResultDetail`(result_view), `QuestionSetView`, `FailureReviewView`, `ReleaseView` 와 공용 틀 `Layout` 이다. 링크(라우터)는 조립이 render prop 으로 넘긴다. 컴포넌트는 라우터를 모른다.
- 조립은 `src/App.tsx`, `src/Pages.tsx`, `src/AlertsContext.tsx` 다(경계 점검의 app 층은 `src/*.tsx` 직접 파일).
- 컴포넌트끼리 import 할 수 없어 확인 대화상자(Radix Dialog)는 쓰는 컴포넌트마다 자기 안에 둔다(세 곳). 공용 부품 폴더를 새로 만들어 경계 규칙을 넓히는 대신 작은 중복을 택했다.
- 입력 제약(길이, 글자 모양)은 화면이 다시 구현하지 않는다. 필수 입력만 화면이 검사하고, 계약 제약은 서버가 검사해 칸별 사유(`ProblemDetails.errors`)를 화면이 보인다(코드 안에 스키마에 없는 거부 조건을 두지 않는다, D117).
- 실패 사례 검토의 기대 출력(`ActionExtraction`)은 JSON 으로 고친다. 모델 출력으로 시작값을 채운다. 구조화된 편집기는 만들지 않았다(검토자가 어떤 칸을 자주 고치는지 알지 못한다). 문항 세트는 JSON 파일로 올린다(계약 `QuestionSetUpload`).
- 시작 코드와 결과는 `window.print()` 와 인쇄 스타일(`@media print` 에서 `.no-print` 숨김)로 출력한다.

## 왜
경계 규칙이 영역 구조 규칙 3·4 에서 나온다. 입력 제약을 서버가 한 곳에서만 검사하는 것이 R7 과 D117 이다.

## 검토한 대안과 버리는 이유
- **`src/ui` 공용 폴더:** 경계 규칙과 시험(boundaries)을 바꿔야 하고 규칙 3 에 어긋난다.
- **화면에도 pattern 검사:** 계약과 이중 구현이 되어 어긋난다. 사용자는 서버 사유를 칸 옆에서 본다.

## 결과
- **감수하는 것:** 서버 왕복 뒤에야 형식 오류를 안다. JSON 편집은 비전문가에게 불편할 수 있다. 사용성은 사람에게 보이지 않았다(확인하지 못함).

## 되돌리는 조건
검토자·작성자가 JSON 편집을 불편해하면 구조화 편집기를 새 ADR 로 더한다.
