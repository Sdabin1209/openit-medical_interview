# 0007. 계약 타입 생성에 공유 값 문서(components.yaml)를 포함한다

## 상태
승인(2026-11-11, 영역 작업자). 변경 요청 admin-console-003 의 처리(계약 README 9.0.0: 계약 변경 없음, 생성기 범위 문제).

## 맥락
`StaffAlertEvent`, `AlertEventName`, `AlertStreamHeartbeatSeconds`, `UserRole` 은 어떤 작업도 `$ref` 로 참조하지 않는다(알림 스트림 이벤트는 `x-event-data-schema` 확장, 역할은 `security` 요구의 이름). `openapi-typescript` 는 작업이 닿는 스키마만이 아니라 문서의 `components.schemas` 를 낸다. 그러나 두 서비스 문서에는 이 스키마들이 `$ref` 로만 들어와 있어 생성 타입에 없었고, 화면이 손으로 옮기고 `tests/contract` 가 계약 파일과 대조했다.

## 결정
`redocly.yaml` 의 `apis` 에 `contracts/components.yaml`(`paths: {}` 인 OpenAPI 3.1 문서, 공유 값 라이브러리)를 세 번째 입력으로 더해 `src/contract/components.d.ts` 를 만든다. `generate:contract`·`check:contract` 가 이것까지 다룬다. 손으로 쓴 `UserRole`·`StaffAlertEvent`·`AlertEventName` 타입과 그것을 계약 파일과 대조하던 시험은 지우고 생성 타입을 쓴다.

## 왜
- 표준 생성기의 표준 설정(Redocly 설정의 `apis`)만 쓰고 계약을 고치지 않는다. 생성물이 `components.schemas` 전부라 새 스키마가 생겨도 손을 대지 않는다.
- 타입이 계약에서 나오므로 계약 값이 바뀌면 `tsc` 와 `check:contract` 가 막는다. 파일 내용을 정규식으로 읽는 시험보다 정확하다.

## 검토한 대안과 버리는 이유
- **계약의 openapi 에 `$ref` 를 더하기:** 계약을 고쳐야 하고 헤드 소유다. 변경 요청이 필요한 일을 생성기 설정으로 풀 수 있다.
- **손 사본 + 대조 시험(이전 방식):** 사본이 남고 대조가 정규식이라 깨지기 쉽다. "계약 타입은 생성 명령으로만"(ADR 0020)에 어긋난다.
- **`x-event-data-schema` 를 따라가는 생성기 플러그인:** 표준이 아닌 도구를 만든다.

## 결과
- **얻는 것:** 손 사본 0. 생성 파일이 하나 늘었다(약 2700줄, 화면이 안 쓰는 스키마도 들어 있다. 번들에는 타입만 쓰여 들어가지 않는다).
- **감수하는 것:** 값(런타임에 필요한 것)은 타입에서 얻을 수 없다. `HEARTBEAT_SECONDS` 는 `AlertStreamHeartbeatSeconds`(리터럴 15) 타입의 값으로 적고, 역할·이벤트 이름의 실행 시점 목록은 `Record<UserRole, true>`·`Record<AlertEventName, true>` 로 둔다. 키가 계약과 하나라도 다르면 `tsc` 가 막는다. 값을 한 번 적는 것은 남지만 어긋나면 컴파일이 실패한다.

## 되돌리는 조건
계약이 이 스키마들을 작업에서 `$ref` 로 참조하면 이 입력은 필요 없다. 생성기가 값을 내는 방식(예: enum 상수)을 지원하면 `Record` 를 지운다.
