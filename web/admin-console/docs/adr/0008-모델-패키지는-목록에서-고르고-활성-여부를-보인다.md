# 0008. 모델 패키지는 목록에서 고르고, 활성 여부를 보인다

## 상태
승인(2026-11-11, 영역 작업자). 변경 요청 admin-console-002·004 의 처리(계약 9.0.0: `listModelPackages`, `QuestionSetVersion.is_active`).

## 맥락
승인자는 digest(`sha256:` 과 64자리)를 어디선가 받아 붙여 넣어야 평가 보고서를 볼 수 있었고, 문항 세트 목록은 어느 버전이 활성인지 알려주지 않았다.

## 결정
- 모델 패키지 화면은 `listModelPackages`(쪽 나누기, 커서)로 게시된 패키지를 표로 보이고 행의 버튼으로 고른 패키지의 평가 보고서(`getModelPackage`)를 보인다. digest 입력 칸은 없다. 표에 게시한 때와 활성 여부(`is_active`)를 보인다. 보고 있는 패키지가 이미 활성이면 승인 버튼 대신 "이 패키지는 지금 활성이다"를 보인다. 활성화·롤백이 끝나면 목록을 다시 읽는다.
- 문항 세트 표에 활성 여부(`is_active`)를 보이고 이미 활성인 버전의 활성화 버튼은 비활성으로 둔다. 활성화가 끝나면 목록을 다시 읽는다.

## 왜
- 활성 여부와 목록은 서버만 안다. 화면이 digest 를 외우거나 추측하면 오타(404)와 잘못된 패키지 승인이 생긴다. 계약이 준 값을 그대로 보이는 것이 가장 단순하다.
- 이미 활성인 것의 활성화는 계약상 멱등이라 해가 없지만, 같은 일을 다시 시키는 버튼을 눌리게 둘 이유가 없다. 서버가 최종 판단하므로(멱등) 화면의 막음은 편의다.
- 목록의 쪽 나누기는 계약의 커서 방식(`next_cursor`)을 `useInfiniteQuery` 로 따르며 다른 목록 화면과 같다.

## 검토한 대안과 버리는 이유
- **digest 입력을 남기고 목록을 보조로 두기:** 같은 일을 하는 두 입구가 생기고 계약이 허용하는 입력은 목록의 값뿐이다.
- **활성 여부를 `getModelStatus` 의 digest 와 화면에서 대조:** 서버가 `is_active` 를 주므로 대조는 중복이고 어긋날 수 있다.

## 결과
- **얻는 것:** 승인할 후보를 화면에서 찾을 수 있고 활성 표시가 서버 값이다.
- **감수하는 것:** 목록은 `limit` 를 화면이 정하지 않고 서버 기본값을 쓴다(측정하지 않았다). 목록에 없는 digest 를 보고 있으면 활성 여부를 알 수 없어 승인 버튼은 막지 않는다(서버가 멱등으로 답한다). 실제 model-runtime 의 목록과는 이 작업에서 만나지 않았다(가짜 서버로 시험).

## 되돌리는 조건
목록이 매우 길어져 한 화면에서 고르기 어려우면 검색·필터를 계약에 요청한다.
