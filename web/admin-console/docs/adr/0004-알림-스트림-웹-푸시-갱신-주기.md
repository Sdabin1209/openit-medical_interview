# 0004. 알림 스트림, 웹 푸시, 갱신 주기

## 상태
승인(2026-11-10, 영역 작업자). 값은 측정하지 않았다.

## 맥락
계약 `streamStaffAlerts` 는 SSE(이벤트 alert, resolved, heartbeat, resync)이고 이벤트가 없으면 15초마다 heartbeat 를 보낸다. 웹 푸시는 `getPushConfig`(VAPID 공개키, RFC 8292)와 `registerPushSubscription`(구독)으로 하고 전달은 표준(RFC 8030, 8291)이다.

## 결정
- SSE 는 브라우저 `EventSource` 로 받는다. 재연결과 `Last-Event-ID` 는 브라우저가 한다(WHATWG HTML 의 EventSource). 목록(`listStaffAlerts`)이 바탕이고 스트림 이벤트는 그 위에 덮어쓴다. `resync` 와 다시 이어진 연결에서는 목록을 다시 읽는다.
- **heartbeat 3번(45초) 조용하면 연결을 버리고 새로 연다.** 근거: 계약이 heartbeat 를 "브라우저가 죽은 연결을 알아채게 한다"고 적었다. EventSource 는 반쯤 끊긴 연결을 스스로 알아채지 못한다. 3 배는 한두 번의 지연을 견디려고 고른 값이고 표준이 아니다. 측정하지 않았다.
- 응답 코드 오류(401, 403)로 브라우저가 EventSource 를 포기(`CLOSED`)하면 "연결 끊김"과 다시 연결 버튼을 보인다.
- 알림 스트림은 직원·의사일 때만 앱 전체에서 하나 연다(메뉴의 열린 알림 수와 알림 화면이 같은 연결).
- 웹 푸시는 사용자가 버튼을 눌러 켠다: 알림 권한 요청 → 서비스 워커(`/sw.js`) 등록 → VAPID 공개키로 구독(`userVisibleOnly`) → 서버에 구독 등록. 서비스 워커는 계약 `WebPushPayload`(kind, alert_id, raised_at, 환자 정보 없음)로 알림을 띄우고 눌렀을 때 `/alerts` 를 연다. 권한 요청은 사용자 동작 안에서만 한다(브라우저 권고).
- 적재 상태는 `LOADING` 인 동안 3초마다 읽고 `READY`, `FAILED` 에서 멈춘다. 3초는 측정하지 않은 값이다(적재 시간 미측정, 사람이 기다리며 보는 단위).

## 왜
EventSource 는 SSE 의 표준 클라이언트이고 재연결 규칙이 내장이다. 푸시 구독은 Push API 와 Notifications API 의 표준 흐름이다.

## 검토한 대안과 버리는 이유
- **fetch 스트림으로 직접 SSE 파싱:** `Authorization` 헤더가 필요 없는 구성(쿠키)에서는 EventSource 로 충분하다.
- **폴링만:** 위험 알림이 늦다. 스트림이 계약에 있다.
- **헤더 없이 heartbeat 감시 없음:** 반쯤 끊긴 연결에서 알림이 조용히 멈춘다(안전과 닿는 알림).

## 결과
- **얻는 것:** 끊김이 화면에 보이고 회복한다. 푸시는 화면이 닫혀도 직원에게 간다.
- **감수하는 것:** 이 작업에서 실제 푸시 서비스로 구독·전달을 시험하지 못했다(헤드리스 브라우저에 푸시 서비스가 없다). 구독 절차는 가짜 `serviceWorker` 로 단위 시험했고, 서비스 워커 `sw.js` 는 린트만 했다. 게이트웨이의 응답 시간 제한이 스트림을 끊는지도 확인하지 못했다(변경 요청 005).

## 되돌리는 조건
heartbeat 간격이 계약에서 바뀌면 `HEARTBEAT_SECONDS` 와 시험이 같이 바뀐다(계약 대조 시험이 있다). 측정으로 더 나은 값이 나오면 새 ADR.
